## 한 줄 결론

큰 구조(D1·D2·D5, workers.dev/preview 비활성화, Access 단일 앱)는 문서와 일치한다. 다만 **D3의 "진입점은 하나뿐"이라는 보장이 성립하지 않는 지점이 남아 있고(High)**, **D4의 "OTP는 기본 제공"이 현재 문서와 반대(High)**, **Verification 2·5·6이 그대로는 실행/판정 불가(Medium)** 가 주요 문제다. Access 앱을 호스트 단위 self-hosted로만 만든 선택 자체는 유효하지만, 지금은 Worker 단위 Access destination이라는 더 강한 옵션이 존재하므로 그 부재가 리스크다.

## High

### H1. D3 "Worker로 들어오는 경로는 `zzik.qus0in.dev` 하나뿐" — 문서상 보장되지 않는다 (line 31–35, 118, 124)

ADR은 `workers_dev: false`, `preview_urls: false`로 진입점을 하나로 만들었다고 단정한다. 그러나 공식 문서는 두 가지를 분명히 말한다.

- `workers.dev` 문서(2026-11-06): "Disabling your `workers.dev` route does **not** disable Version URLs, Preview URLs, or Deployment URLs."
- Version URLs 문서(2026-09-22): Version URL은 `<version-prefix>-<worker>.<subdomain>.workers.dev` 형식이고, "If Version URLs are enabled, the URL is **public**", `preview_urls: false`로 끌 수 있다. 또한 `wrangler versions upload --preview-alias`로 별칭 URL(`staging-zzik.<sub>.workers.dev`)이 생긴다.

즉 `preview_urls: false`를 명시한 것은 옳지만(그래서 Version URL은 기본적으로 닫힘), **D3의 결론은 "config 두 줄"이라는 사실에 근거하지 않고 "URL 계열이 존재하지 않는다"는 더 강한 주장**이다. `wrangler versions upload`, 새 Previews(브랜치) 기능, Deployment URL 계열은 호스트 단위 self-hosted Access 앱(`zzik.qus0in.dev`)의 보호 범위 밖이다. 이 URL들이 하나라도 열리면 Access를 통째로 우회해 앱 HTML이 공개된다. ADR이 스스로 "누군가 다시 켜면 곧바로 공개된다"고 적은 리스크(124)의 실제 트리거가 이것이다.

권고(문서 수정 방향):
1. D3 문장을 "현재 config로 workers.dev·version URL이 닫혀 있다"로 낮추고, "URL 계열 전체가 존재하지 않는다"는 단정은 삭제.
2. **Worker 단위 Access destination을 백스톱으로 추가** — 현재 Access는 `type: "worker"`(+`worker_id`) destination을 지원하며, 이는 "routes, Custom Domains, `workers.dev` hostname, and previews"를 한 번에 보호한다(공식 문서 명시). 호스트 단위 self-hosted 앱은 이 위에 얹으면 되고, Access 앱 수는 여전히 1개다(정책 1개 유지). 이게 D3의 "config 실수 한 번이면 공개" 리스크를 구조적으로 없앤다.
3. 대안으로 계정 수준 **"Protect all Workers"(`all_workers` / `all_preview_workers`)** 를 켜는 것도 가능. 단 이 경우 "Make this Worker public" 바이패스가 실수로 생기면 반대로 공개되므로, D4 표에 "bypass 없음" 검증 항목을 추가해야 한다.
4. 어느 쪽을 택하든 `wrangler versions upload`를 쓰지 않는다는 규칙(또는 그 출력 URL이 차단됨을 확인하는 검증)을 명시.

### H2. D4 "Identity provider: One-time PIN (기본 제공)" — 사실과 반대 (line 48, 110, 구현 순서 2)

현재 문서(OTP, 2026-08-31): "New Zero Trust organizations use the **Cloudflare identity provider** as their default login method. **OTP is no longer added automatically**, but you can set it up at any time." 즉 새 조직에서 One-time PIN IdP는 기본 제공이 아니며, `Zero Trust > Integrations > Identity providers > Add new identity provider > One-time PIN`으로 **명시적으로 추가**해야 한다.

파급:
- D4 표의 "기본 제공" 표기는 틀렸고, 구현 순서 2("대시보드에서 Access 앱과 정책을 만든다")에 **IdP 추가 단계가 빠져 있다.** 이 상태로 앱만 만들면 로그인 수단이 없어 검증 4·5가 막힌다(기본 Cloudflare IdP로는 이메일 코드 로그인이 되지만, 그건 ADR이 설계한 것과 다른 구성이고 "설정 없이 동작"이라는 근거도 사라진다).
- Alternatives 표(110)의 "One-time PIN은 설정 없이 Gmail 주소로 바로 동작한다"도 같은 이유로 수정 필요.

권고: D4 표에 `Identity provider | One-time PIN — Zero Trust > Integrations > Identity providers에서 신규 추가(기본 아님)` 명기, 구현 순서에 "2-1. OTP IdP 추가" 삽입, 그리고 "OTP IdP를 추가하지 않으면 로그인 불가"를 전제/검증에 반영.

## Medium

### M1. Verification 2의 기대값(`Location` = `https://<team>.cloudflareaccess.com/cdn-cgi/access/login/...`)이 부정확 (line 138)

미인증 요청의 302는 보통 **보호 대상 호스트 자신**의 `/cdn-cgi/access/login/<app-host>?redirect_url=...`로 향하고, team domain(`<team>.cloudflareaccess.com`)은 IdP 인증·전역 세션·App Launcher 단계에서 등장한다. 문서 근거: 로그아웃 URL이 `<application-domain>/cdn-cgi/access/logout`과 `<team>.cloudflareaccess.com/cdn-cgi/access/logout` 두 형태로 병존한다는 설명(session-management)에서도 app domain 쪽 `/cdn-cgi/` 경로가 1차 인터페이스임을 알 수 있다.

문제: 이 기대값을 그대로 쓰면 **정상 배포에서도 검증이 실패**하고, 반대로 team domain으로 리다이렉트되는 이상 동작을 정상으로 오인할 수 있다.

권고: 단언을 `302` + `Location`에 `cdn-cgi/access/login`이 포함되는지로 완화하고, 호스트는 "app host 또는 team domain 중 하나"로 기록. 추가로 `-sI`(HEAD) 대신 `-s -D - -o /dev/null`(GET)로 확인해 HEAD 처리 차이를 배제.

### M2. Verification에 "실제 보호 대상 아티팩트" 검증이 없다 (line 138, 142)

Verification 2는 `/`(HTML)만, 6은 로그인 후 deep path만 본다. 정작 유출되면 곤란한 것은 `dist/assets/*.js|css`와 SPA 폴백 결과물인데, 이 경로들에 대한 미인증 검증이 없다. (`not_found_handling: single-page-application` + 내부 asset router 조합은 "Access가 자산까지 보호한다"는 문서 서술에 의존하고 있고, 실측 항목이 없다.)

권고 추가:
- 미인증 상태에서 실제 번들 파일 1개: `curl -s -o /dev/null -w '%{http_code}' https://zzik.qus0in.dev/assets/<실제파일>.js` → 302
- 브라우저형 내비게이션 흉내: `curl -s -o /dev/null -w '%{http_code}' -H 'Sec-Fetch-Mode: navigate' https://zzik.qus0in.dev/any/path` → 302 (쿠키 없음)
- 위 모든 응답 본문에 `Hello Young-In` 문자열이 없음을 grep으로 확인.

### M3. Verification 6이 실행 불가 (line 142)

"로그인한 상태에서" deep path 200 확인은 curl로는 `CF_Authorization` 쿠키(그리고 `CF_Binding` 사용 시 바인딩 쿠키)가 필요하다. 절차서에 쿠키 확보 방법이 없어 재현이 안 된다.

권고: 브라우저 수동 확인으로 명시하거나, `curl -H "cookie: CF_Authorization=$TOKEN"` 형태로 토큰 확보 절차(DevTools → Application → Cookies)를 함께 적는다.

### M4. Verification 5의 판정 기준이 관측 불가 (line 141)

"PIN이 오지 않아 통과할 수 없다"는 결론 자체는 문서와 일치한다 — OTP 문서: "By design, blocked users will not receive an email. The login page will always say **A code has been emailed to you**, regardless of whether or not an email was sent." 그리고 Access는 **코드를 입력한 뒤에야** 인증 시도를 로그에 남긴다.

문제: UI가 항상 같은 문구를 띄우므로 "메일이 안 왔다"만으로는 판정이 불가능하고(지연/스팸 필터와 구분 안 됨), "Access 로그에서 허용/차단 기록 확인"도 코드 입력 전에는 로그가 없다.

권고: (a) 허용되지 않은 이메일로 코드 요청 → 메일 미수신 확인, (b) 임의의 코드 입력 → `That account does not have access.` 표시 확인, (c) 미인증 curl로 앱 HTML 미노출 확인을 **세 가지 모두** 요구. 그리고 Access Authentication 로그에는 "코드 입력 후" 이벤트만 남는다는 점을 각주로.

### M5. Access 앱 설정 대조 범위가 좁다 (line 143)

Verification 7은 "정책 1개, Include 이메일 1개, Bypass 없음"만 본다. 실제 사고는 **도메인 오타/추가 도메인/Instant auth/추가 정책**에서 난다. 특히 H1에서 제안한 Worker 단위 destination을 쓰면 "도메인 목록" 개념이 달라지므로 대조 항목을 명시해야 한다.

권고: 대조 항목을 ① Application domain 목록이 정확히 `["zzik.qus0in.dev"]`(경로·와일드카드·추가 도메인 없음) ② 정책은 Allow 1개, Include = Emails 1개 ③ Bypass/Service Auth 0개 ④ **AUD 값과 team domain을 ADR에 기록**(후속 JWT 검증 작업의 입력값) ⑤ "Make this Worker public"/bypass 없음(계정 수준 Access를 켠 경우)으로 확장.

### M6. "현재 wrangler 권한으로 배포할 수 있다"(line 12, 117)는 미검증 전제 — Custom Domain 권한

Custom Domain은 Cloudflare가 DNS 레코드와 Advanced Certificate를 **대신 생성**하는 방식이다. 문서는 "Cloudflare will create DNS records and issue necessary certificates on your behalf"라고만 하고, 토큰에 필요한 권한 조합을 명시하지 않는다. 실무상 Custom Domain 생성은 Workers Routes 계열 권한으로 처리되지만, 계정/토큰 구성에 따라 zone DNS·SSL 권한이 요구될 수 있고 그 경우 `wrangler deploy`가 인증 오류로 실패한다.

현재 ADR은 이 지점을 "미확인 전제"에 넣지 않고 Consequences에서 단정한다(line 117). 최소한 **전제 4번**으로 분리해 "첫 `wrangler deploy`에서 Custom Domain 생성이 성공하는지(권한 오류 없음) 확인"을 추가하고, 실패 시 대안(DNS write 권한이 있는 좁은 토큰 발급, 또는 임시로 workers.dev 사용 후 도메인 연결)을 적어두는 편이 안전하다.

### M7. 로컬 검증이 실제 라우팅을 재현하지 않는다 (line 125, 137)

`pnpm dev`(vite)와 `pnpm preview`(vite preview)는 Workers asset router를 재현하지 않는다. 즉 Verification 1로는 SPA 폴백(`not_found_handling`)·404 처리·`/assets/*` 경로 동작을 확인할 수 없고, 그 동작은 프로덕션에서만 처음 드러난다. ADR은 preview URL을 끈 대가로 "로컬에서만 확인 가능"이라고 적었는데, 그 로컬이 실제 배포 동작과 다르다.

권고: 로컬 검증에 `wrangler dev`(dist를 assets로 서빙)를 추가하고, deep path 폴백과 404를 여기서 확인. `vite dev`는 UI 확인용으로만 표기.

## Low

### L1. 기존 DNS 레코드 전제가 부정확 (line 16)
문서는 "You cannot create a Custom Domain on a hostname with an **existing CNAME** DNS record"로 CNAME을 특정한다. ADR은 "기존 DNS 레코드가 없다. 있으면 충돌한다"로 일반화해, A/AAAA/TXT만 있는 경우까지 충돌로 단정한다(과잉이지만 안전한 쪽). 전제 확인 절차에 "레코드 유형별 확인(CNAME 존재 시 확실한 충돌, 그 외 유형은 실제 시도로 판정)"을 적으면 정확해진다.

### L2. Custom Domain 삭제 시 인증서 잔존 — 정리 절차 없음
문서: "When you delete a Custom Domain, the associated Advanced Certificate is **not** automatically deleted." 롤백/재구성 시 SSL/TLS > Edge Certificates에 잔여 인증서가 남는다. Consequences나 후속 과제에 정리 절차 한 줄 필요.

### L3. HTTP(80) 경로·HSTS 미검증 (line 138–142)
검증이 모두 `https://`만 본다. `http://zzik.qus0in.dev`가 평문으로 서빙되는지, Access가 그 요청도 막는지, HTTPS 강제(Always Use HTTPS / HSTS)가 켜져 있는지 확인 항목이 없다. 1인용 앱이라 위험도는 낮지만 "진입점 하나"를 주장하는 ADR이면 스킴도 함께 닫아야 일관된다.

### L4. Host/SNI 불일치 우회 시나리오 미검증
"Access는 호스트 이름 기준으로 막는다"는 전제만 있고, `Host` 헤더를 보호 호스트로 위조한 채 다른 엣지 엔드포인트로 붙는 형태(예: workers.dev 호스트로 접속하며 `Host: zzik.qus0in.dev`)를 시도하는 검증이 없다. Cloudflare가 SNI/Host 정합성을 검사하므로 실제 우회 가능성은 낮다고 보지만, D3가 "우회 차단"을 표제로 단 ADR이므로 "시도했고 차단됨"을 한 줄 남길 가치가 있다. (H1의 Worker 단위 Access를 켜면 이 시나리오도 함께 닫힌다.)

### L5. Session duration 24h는 "기본값"과 동일 (line 44, 126)
문서상 global/application session duration 기본값이 24시간이다. 표에 "24h"만 적으면 "의도적으로 설정한 값"인지 "기본값 방치"인지 구분되지 않아, 나중에 대시보드 대조 시 판정이 흔들린다. "24h(기본값과 동일, 명시적으로 확인함)"로 표기.

### L6. `compatibility_date` 재현성 (line 79)
`"2026-11-11"`은 ADR 작성일과 같다. 문서 예시도 "today's date"를 쓰지만, 장기 재현성 측면에서는 배포 시점에 고정하고 이후 올릴 때 ADR에 사유를 남기는 규칙이 낫다. 또한 `assets.directory`는 문서 표기가 `"./dist/"`이므로 트레일링 슬래시로 통일(동작 차이는 없음).

### L7. "정적 자산 요청 무료", "Zero Trust Free 50석" — 사실 확인됨 (line 119)
문제 없음. 다만 "무료"의 근거(스크립트 미호출 시 요청 미과금)를 한 줄 붙이면 나중에 Worker 스크립트를 추가할 때(D1의 후속 과제) 비용 가정이 바뀐다는 점을 독자가 놓치지 않는다.

## 사실관계 확인 결과 (문제 없음 — 그대로 유지 가능)

- D1: `assets.directory` + `assets.not_found_handling: "single-page-application"` 조합, `main` 없는 assets-only Worker, 미매치 시 `index.html` 200 응답 — 문서와 일치.
- D2: `routes: [{ pattern, custom_domain: true }]` 문법, 경로 없는 호스트 전체 매칭, DNS·인증서 자동 생성, route 방식의 더미 DNS 레코드 불필요 — 모두 일치. (1단계 서브도메인은 Universal SSL, Custom Domain은 Advanced Certificate 자동 발급, 별도 ACM 구독 불필요.)
- D3: `workers_dev: false` / `preview_urls: false` 키 이름·동작(키 이름은 여전히 `preview_urls`) 일치. `routes`가 있으면 `workers_dev`가 false로 추론된다는 점도 문서와 일치(명시한 것은 더 나은 선택).
- D4: self-hosted 앱 + Allow 정책 1개 = deny-by-default, Bypass/Service Auth 미생성 판단 — 일치.
- D3/D4 핵심 전제: "Workers static assets는 내부 router Worker 뒤에서 실행되지만 Access가 앱과 자산을 계속 보호한다" — Cloudflare Access for Workers 문서에 명시됨. 즉 assets-only 구성이 Access 보호를 무력화하지 않는다는 ADR의 판단은 맞다.
- Alternatives: Pages의 `*.pages.dev`·브랜치 preview 도메인 상시 존재, route 방식의 proxied DNS 선행 필요, Google IdP의 GCP OAuth 클라이언트 필요 — 모두 타당.
- Verification 3(workers.dev 404/오류 확인): `workers_dev: false`면 실제로 서빙되지 않음. 단 계정 workers.dev 서브도메인이 미등록이면 NXDOMAIN이므로 "404 또는 DNS 미해석"으로 기대값을 넓히는 편이 정확(Low).

## 우선순위 요약 (권고 반영 순서)

1. **H1** — D3 문장 약화 + Worker 단위 Access destination(또는 계정 수준 Protect all Workers) 백스톱 추가. 보안 코어.
2. **H2** — OTP IdP는 기본 아님. D4 표·구현 순서·Alternatives 수정.
3. **M1·M2·M3·M4** — Verification 재작성(리다이렉트 기대값, 자산 경로, 쿠키 확보, OTP 판정 3종).
4. **M5·M6** — 대조 항목 확장(AUD/team domain 기록 포함), Custom Domain 권한을 미확인 전제로 승격.
5. **M7, L1–L6** — 로컬 검증 도구 교정, 문서 정밀도 보강.

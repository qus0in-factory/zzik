## High

### H1. Cloudflare API 토큰의 노출면이 ADR 서술보다 넓다 — Keychain ACL `-T /usr/bin/security`는 사실상 무제한 (line 79, 92–93, 378–379, 447)

세 가지가 겹친다.

1. **권한 범위**: `Account / Workers KV Storage / Edit`은 계정의 **모든 namespace에 대해 읽기·쓰기·삭제**다(ADR도 93·447에서 인정). 즉 이 토큰 하나로 이 계정 KV에 저장된 다른 프로젝트 값(있다면 비밀 포함)까지 읽힌다. 읽기 권한이라는 점이 "쓰기만"이라는 서술보다 넓다.
2. **보관 방식**: U4의 `security add-generic-password ... -T /usr/bin/security -w`. `-T`는 "이 애플리케이션이 접근할 때 프롬프트를 생략한다"는 ACL 항목인데, 수집기가 `security`를 **자식 프로세스로 실행**하므로 요청 주체는 `security`다. 결과적으로 **사용자 권한으로 도는 임의의 프로세스가 `security find-generic-password -s zzik-usage-collector -w`를 실행하면 프롬프트 없이 토큰을 얻는다.** Keychain은 여기서 실질적 방어가 아니다(파일 0600과 동등하거나, 오히려 "숨겨져 있다"는 착각만 준다).
3. **무인 실행**: launchd가 5분마다 이 자격 증명을 **자동으로** 사용한다. ADR은 "이 Mac에는 이미 더 넓은 wrangler OAuth 로그인이 있으므로 추가 위험은 작다"(93)고 하는데, wrangler OAuth는 대화형이고 만료되며 데몬이 상시 쓰지 않는다. **상시·무인·계정 전 KV 권한**은 질적으로 다른 노출이다. 게다가 이 랩톱이 침해되면 (a) 토큰으로 KV를 읽고 (b) KV에 값을 덮어써 대시보드에 거짓 값을 흘릴 수 있다.

권고(택1, 문서에 결정과 근거를 남길 것):
- **(권장) Keychain을 쓰지 않고 0600 파일**로 둔다. `~/Library/Application Support/zzik/cloudflare-api-token`(0700/0600, tmp→rename). 이미 `usage-state.json`과 같은 보호 수준이고, "Keychain이므로 안전하다"는 잘못된 인상을 없앤다.
- Keychain을 유지하려면 **ACL을 `security`가 아니라 실제 소비자에 묶어야** 한다. `security`를 경유하는 한 불가능하므로, Node에서 Keychain을 직접 읽는 경로(native addon) 없이는 이 항목은 "ACL 없음"과 같다고 명시하고 리스크를 수용한다.
- 토큰 자체에 **만료일**을 설정하고(대시보드 지원), 회전 주기(예: 90일)를 운영 스킬에 넣는다. 현재는 "삭제"(폐기 절차, line 383)만 있고 만료·교체가 없다.
- `Workers KV Storage / Edit` 외 권한이 없는지 V14에서 **권한 화면을 캡처/기록**하는 수준으로 구체화(현재 "권한이 ... 하나다"만 있음).

부수 확인: 93의 "namespace 단위로 좁힐 수 없다"는 **사실로 맞다**(Cloudflare 토큰 권한은 계정/존 단위). 다만 그 사실이 곧 "추가 위험이 작다"는 결론을 지지하지는 않는다.

### H2. `run_worker_first` 배열형은 자동 navigation 감지를 끈다 — D6의 서술과 "자산은 스크립트를 안 부른다" 주장이 부정확 (line 147, 161–162, 416, 479)

공식 문서(Static Assets → Advanced routing control)는 배열형에 대해 이렇게 말한다:

> "This approach **disables the automatic `Sec-Fetch-Mode: navigate` detection** and gives you explicit control over which requests should be handled by your Worker script vs served as static assets."
> (지원: Wrangler v4.20.0+, 이 레포 4.159 ✓)

따라서 D6 line 161의 "**`/api/`로 시작하지 않는 요청이 스크립트에 도달하면(자산이 없고 내비게이션 요청도 아닌 경우)** `env.ASSETS.fetch`로 넘겨"는 조건절 자체가 성립하지 않는다. 배열형에서는 "내비게이션 요청"이라는 별도 분기가 없어지므로:

- `/any/path`(자산 없음)는 **Worker가 호출되고** → `ASSETS.fetch` → SPA 폴백 200이 된다(ADR이 의도한 결과). 즉 동작은 맞지만 **근거 문장이 틀렸고**, 이 경로가 실제로 스크립트 호출로 집계된다.
- 그 결과 line 162의 "정적 자산 요청은 스크립트를 부르지 않으므로 0.1의 비용 가정이 유지된다"는 **"존재하는 자산 파일"에만 참**이다. 딥링크·`favicon.ico` miss·`/api` 오타 경로는 스크립트 호출이 된다(1인 사용이라 비용은 무의미하지만, 서술은 정정해야 한다).

추가로 문서만으로는 "배열형에서 자산 미매치 + run_worker_first 미매치"가 (a) 자산 서빙으로 직행하는지 (b) Worker를 부르는지가 **명확하지 않다**. ADR은 전제 5로 `wrangler dev` 확인을 걸어 둔 점은 좋다. 다만 V5가 기대값을 단정하므로, **두 경우 모두를 기록하는 형태**로 바꾸고 D6의 폴백 코드는 (b)일 때만 필요하다는 주석을 달아야 한다. 폴백이 죽은 코드가 되면 V5가 "위임했다"를 검증할 수 없으므로, 검증 항목도 "결과가 index.html 200"으로 낮추는 편이 정확하다.

0.1 보호 범위 관점(질문 항목): 스크립트가 생겨도 **Access는 자산과 앱을 계속 보호한다**(공식: "Workers with Static Assets execute behind an internal router Worker. Access still protects the application and its assets"). 그리고 `run_worker_first`를 실수로 빼면 `/api/usage`는 자산 미매치 → SPA 폴백 HTML 200이 되어 **데이터가 새지 않는 방향으로 실패**한다. 이 fail-safe 성질은 ADR에 장점으로 명시할 가치가 있다(현재 없음). 반대로 `run_worker_first`를 `["/*"]`로 넓히면 모든 자산이 스크립트 호출이 되고, 라우터가 인증을 잘못 걸면 UI 전체가 401이 된다(Alternatives line 416이 이 방향을 이미 배제 ✓).

### M2. 429 백오프: 상한 3,600초가 Retry-After를 깎아 서버 지시를 위반한다 (line 129)

"대기 = max(Retry-After, 300 × 2^(n−1)), 상한 3,600초" — 상한이 **최종 대기값**에 걸리므로 `Retry-After: 7200`이면 3,600초로 잘려 **지시받은 시각보다 1시간 일찍 재시도**하고 다시 429를 받는다. 무한 반복의 씨앗이다.

권고:
- 상한은 **지수항에만** 적용: `wait = max(RetryAfterSec, min(300 × 2^(n−1), 3600))`, 그리고 `RetryAfterSec`은 (말이 안 되는 값만) 별도 상한(예: 24h)으로 클램프.
- 첫 실패의 base 300초는 **주기(300초)와 같아서 사실상 백오프가 아니다**. biseo가 `floorMs 600000`(10분)을 둔 이유이므로, base를 2×interval(600초)로 올리거나 `wait = max(RA, 2×interval×2^(n−1))`로 두는 편이 낫다.
- `n`의 정의(연속 실패 횟수, 성공 시 0)와 **`retryAt`이 게이트(`nextAllowedAt`)와 같은 값인지** 명시. 현재 게이트와 `retryAt`이 두 필드로 갈라져 있어 어느 쪽이 우선인지 불명확하다.
- `Retry-After: 0`/음수/HTTP-date 과거값 처리 규칙(→ 즉시 재시도가 아니라 최소 1주기)도 한 줄 필요.

### M3. JWKS 처리: 인스턴스화 위치·캐시·키 회전 정책이 없다 (line 171, 321)

공식 문서 사실:
- 서명키는 **6주마다 자동 회전**, 회전된 이전 키는 **7일간 유효**.
- 권장: 하드코딩 금지, `public_cert` 캐시 의존 금지, `kid`로 매칭.
- Cloudflare의 Workers 예시 코드는 `createRemoteJWKSet`을 **핸들러 안에서** 만드는데, 이러면 요청마다 JWKS를 새로 받아 캐시가 없다(공식 예시의 약점).

ADR은 "키 조회 함수를 인자로 받는다(운영: 원격 JWKS, 테스트: 로컬 키)"(321)로 테스트 용이성만 확보하고, **운영 캐시 정책이 비어 있다.** 권고:
- `createRemoteJWKSet` 인스턴스를 **모듈 스코프**에 1회 생성(isolate 재사용). `cacheMaxAge`(jose 기본 10분) 이내로 두고, 회전 유예 7일보다 훨씬 짧게 유지.
- JWKS 조회 실패 시의 상태 코드 결정: 401(검증 실패)과 구분해 **503 `{error:"jwks_unavailable"}`** 같은 별도 결과로 두고, 인증 실패로 오분류해 세션을 로그아웃시키지 않도록.
- `algorithms: ['RS256']` **명시적 핀**, `clockTolerance: '60s'` 추가(24h 토큰 + 랩톱 절전 복귀 시 시계 오차).
- `kid` 불일치(회전 직후) 시 1회 재조회 허용 여부를 정한다(캐시 강제 무효화는 공격 표면이 되므로 쿨다운 필요).

### M4. `ctx.access`를 검토하지 않았고, 그 이유(static assets에서는 전달되지 않음)를 적어야 한다 (line 169, 321, 415–417)

Access for Workers 문서 2026-11-02:
> "Workers with Static Assets execute behind an internal router Worker. Access still protects the application and its assets. **However, the router does not pass `ctx.access` to the user Worker.**"

그리고 "JWT를 직접 파싱/검증할 필요가 없다"는 `ctx.access` 안내도 같은 문서에 있다. 즉 이 구성(assets + `main`)에서 **`ctx.access`를 쓰면 항상 `undefined`가 되어 전부 401**이 된다. ADR은 `jose`를 택했지만 Alternatives에 이 대안이 없어, 후속 리뷰어가 "왜 `ctx.access`를 안 썼나"를 물으면 근거가 없다. 또 `jose` 선택이 **static assets 때문에 강제된 선택**이라는 점은 유지보수에 중요하다.

권고: Alternatives에 "`ctx.access` 사용 — static assets 라우터가 `ctx.access`를 전달하지 않아 불가"를 추가하고, `worker/infra/jose-access-verifier.ts` 상단에 같은 이유를 주석으로 남긴다.

### M5. 토큰 만료 대비 수집 공백의 "실효성"이 정량화되지 않았고, 장기 stale 표시 정책이 없다 (line 84–88, 443, 458)

판단 자체(갱신하지 않음)는 타당하다. refresh token 회전으로 Claude Code 세션을 깨뜨리는 위험이 훨씬 크다. 다만 실효성 평가에 필요한 숫자와 정책이 빠져 있다:

- **정량화 없음**: access token TTL(전제 1·7에서 확인 예정) 대비 5분 주기 288회/일 중 몇 %가 `token_expired`가 되는지. "며칠 관측"(V15)은 **사후** 관측이고, 설계 시점 추정이 없다. 최소한 "TTL이 8시간이면 Claude Code를 하루 1회 실행하는 사용자 기준 일 8시간(≈33%)이 인증 필요 상태" 같은 계산을 적어야 이 결정의 대가가 보인다.
- **장기 stale 정책 없음**: `fetchedAt`이 24시간 또는 7일 넘게 오래된 값을 **계속 정상 카드처럼** 보여 줄지 결정이 없다. `resets_at`이 전부 과거가 되어 "리셋 시각 지남"만 남는 화면이 일주일 지속될 수 있다. 권고: `fetchedAt` 기준 24h 초과 시 카드 숫자를 흐리게 + "N일 전 값" 강제, 7일 초과 시 "값 숨김(수집기 상태만 표시)" 같은 단계 규칙을 D4/D9에 추가.
- **E2E 검증 없음**: V1~V15 중 `token_expired`/`auth_required`/`no_credentials`를 **실제 수집기 실행으로** 만들어 보는 항목이 없다(V3 단위 테스트만). 만료 토큰을 흉내 내는 검증(예: `usage-state.json`의 `expiresAt`을 과거로 둔 `--dry-run` 또는 테스트용 자격 증명 경로 주입)을 V 항목으로 추가.
- **토큰 이벤트 로그 없음**: `token_expired`→`ok`로 복귀할 때 "언제 갱신됐는지"를 로그 한 줄로 남기면 V15 관측이 쉬워진다(현재 로그는 실행당 한 줄에 status만).

### M6. 프론트·테스트 경로 규칙이 현 main 및 0.2.1 명세와 불일치 (line 266–271, 287–292, 297, 451)

현 main의 실제 상태:

## Low

### L1. `rawText` 64KB 초과를 `upstream_error`로 강등 (line 118)
성공한 응답을 실패로 표시하면 사용자는 upstream 장애로 오해한다. `status: "ok"`, `rawText: null`, `rawTruncated: true`(+ 키 목록만 남김) 권장. KV 값 상한은 25MiB이므로 64KB는 자체 정책임을 명시.

### L2. 게이트로 건너뛴 실행에서 `httpStatus`가 null이 되어 마지막 실제 상태 코드를 잃는다 (line 109, 128)
`httpStatus`(마지막 실제 호출)와 `lastHttpStatus`(마지막 관측값)를 분리하거나, `httpStatus`는 유지하고 `skipped: true`를 추가.

### L3. KV PUT 실패 시 로컬 상태가 먼저 저장된다 (line 68)
순서가 "로컬 상태 저장 → KV PUT"이라 PUT 실패 시 로컬 `fetchedAt`/`nextAllowedAt`만 앞서 나간다. 다음 실행에서 KV와 로컬이 어긋나지만 곧 수렴하므로 경미. 다만 `--dry-run`이 상태를 쓰지 않는다는 점(line 69)과 "게이트는 상태를 쓴다"를 명확히 구분해 적을 것.

### L4. "리셋 지남"의 집계 규칙이 없다 (line 122, 230)
0.2는 "흐리게 표시"만 정한다. 100%인데 `resets_at`이 과거인 항목이 **전체 상태 배지를 `한도 도달`로 끌지** 결정이 필요하다(0.2.1 명세 C5는 "집계에서 제외"로 결정). 같은 규칙을 0.2에도 명시해 프론트 domain 테스트로 고정.

### L5. `jose` 도입 세부 (line 259, 321)
- 버전 고정(`jose@^6`)과 Workers에서 `nodejs_compat` 불필요함을 한 줄 확인.
- 번들 크기 증가(수십 KB)는 무시 가능하지만 0.1의 "assets-only, 의존성 없음" 전제가 바뀌는 것이므로 Consequences에 이미 있음 ✓.

### L6. `tests/arch/layers.test.ts`의 `.mjs` 처리 (line 288, 307)
`.mjs`는 import 문이 정적이므로 정규식으로 긁을 수 있지만, JSDoc `import('../../shared/usage-contract.ts')`까지 검사하면 오탐이 난다. "허용 예외: JSDoc 타입 참조" 규칙을 명시.

### L7. `collector`의 JSDoc 타입은 실제로 검사되지 않는다 (line 296)
`shared/usage-contract.ts`를 `import('...')`로 참조해도 `tsc --checkJs`가 돌지 않으면 계약 위반을 못 잡는다(설치본에서는 `shared/`도 없다). 런타임 문제는 없지만 "타입으로 계약을 강제한다"는 서술은 과하다. `tsc -p tsconfig.collector.json --checkJs --noEmit`를 CI/`pnpm test`에 넣거나, 서술을 "문서화 목적"으로 낮출 것.

### L8. 320px 검증 수단 미지정 (line 249, 482)
`document.documentElement.scrollWidth`는 jsdom에서 항상 0이라 단위 테스트로 불가(ADR이 "단위 테스트하지 않는 것"에 넣은 것은 ✓). V7은 **실제 브라우저**에서 수행한다고 명시하고, 사용할 뷰포트/브라우저를 적을 것.

### L9. 상태 enum과 HTTP 매핑의 일관성 (line 106, 189–197)
`status` enum에 `snapshot_corrupt`/`storage_unavailable`이 없는데 502/503 응답은 있다. 봉투 status는 수집기 상태, HTTP 오류는 Worker 상태라는 구분을 표에 한 줄로 명시(현재 표는 Worker 응답만 나열).

### L10. `GET /api/usage` 이외 메서드에 대한 405와 401의 우선순위 (line 196, 478)
"검증이 먼저"라는 서술은 V5에만 있다. D8 표에도 순서를 적어 테스트가 흔들리지 않게(권장: 인증 → 메서드 → 라우트).

## 우선순위 (권고 반영 순서)

1. **H1** — API 토큰 보관(0600 파일 또는 ACL 한계 명시) + 만료/교체 절차. 보안 코어.
2. **H2** — D6 폴백 서술 정정(배열형은 navigation 감지 없음), 비용 주장 범위 축소, V5를 "관측+기대" 형태로.
3. **M1** — 실제 값 기입 + Worker destination 선행 조건 명시. (이거 없으면 배포 시 `/api/usage` 500)
4. **M2** — 백오프 상한을 지수항에만, base를 2×interval로, `retryAt`/게이트 단일화.
5. **M3·M4** — JWKS 모듈 스코프/캐시/실패 코드/alg 핀, `ctx.access` 불가 사유 기록.
6. **M6** — 경로 규칙 단일화(vitest include·tsconfig 포함).
7. **M5·M7** — 만료 공백 정량화·장기 stale 정책·`token_expired` E2E, 수동 단계 표 보강.
8. **L1–L10** — 문서 정밀도.

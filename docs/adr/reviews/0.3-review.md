- 리뷰어: ds (독립 리뷰, 파일 수정 없음)
- 대상: `docs/adr/0.3-chatgpt-usage.md` (428줄, Proposed)

## 한 줄 결론

구조(WHAM 직접 호출, 토큰 갱신은 Codex 소유, 제공자별 KV·상태·게이트 격리, 제공자 화이트리스트 기반 API)는 옳다. 다만 **U1 실측으로 "파일이 실제로 갱신되는지"가 여전히 미확정**이고(High), **401/403을 `auth_required` 하나로 뭉쳐 복구 경로가 끊긴다**(High), **D2와 D4가 `account_id` 처리에서 서로 모순**되며(Medium), **원문 저장 결정에 첫 실측 확인 게이트가 없다**(High). JWT `exp` 판정 자체는 사실관계가 맞고, 실측으로 **토큰 수명 240시간(10일)** 을 확인했다.

---

## High

### H1. U1을 실행해도 "Codex가 `auth.json`을 갱신하는가"가 해결되지 않는다 — 기능 전체가 여기에 걸려 있다 (line 33, 62–76, 307)

실측 결과(아래 U1 표):
- `auth.json`은 존재하고 0600, `auth_mode`는 `chatgpt`, `tokens.access_token`은 `exp`가 있는 JWT.
- 그런데 `~/.codex/config.toml`에 **`cli_auth_credentials_store` 키가 아예 없다**. ADR U1은 "값을 확인한다. 저장 방식이 파일이 아니면 `"file"`로 바꾸고 …"이라고만 쓰고, **키가 없을 때의 판정 기준이 없다.**
- 더 나쁜 신호: `auth.json`의 mtime이 access token의 `iat`과 같은 시점(약 7.4일 전)이다. 즉 **발급 이후 파일이 다시 쓰인 흔적이 없다.** "Codex가 refresh 때 auth.json을 갱신한다"는 이 설계의 유일한 전제가 아직 관측되지 않았다.

전제 5는 "keyring이나 auto로 동작 중이면 auth.json이 갱신되지 않는 낡은 사본일 수 있다"고 정확히 짚었지만, U1의 절차가 그 판정을 내리지 못한다.

권고:
- U1을 두 단계로 나눈다. (a) 키 부재 시 **"파일 모드로 단정하지 않는다"** 를 명시하고 `cli_auth_credentials_store = "file"`을 명시 설정한다(설정 변경이 재로그인을 요구할 수 있음은 U5가 이미 커버). (b) **Codex를 1회 실행한 뒤 `auth.json`의 mtime·`last_refresh`·access token `exp`가 함께 전진하는지 확인**한다. 전진하지 않으면 D1의 전환 조건(app-server)을 기다리지 말고 **0.3을 보류**하는 것이 맞다.
- 이 확인을 "구현 중"이 아니라 **구현 착수 전 게이트**로 올린다(현재는 구현 순서 1번이 U1이지만, 실패 시의 결정이 문서에 없다).

### H2. 401/403을 `auth_required` 하나로 뭉쳐 복구 경로가 끊긴다 (line 75, 111, 119–121)

ADR은 두 가지를 동시에 말한다.
- D4: `403`이고 본문이 JSON이 아니면 "`chatgpt.com` 앞단의 차단 페이지일 수 있고 **재로그인으로 풀리지 않는다**" → `upstream_error`.
- D2: `401`과 JSON `403`은 `auth_required`, 게이트 1시간.
- 화면(U4): `auth_required` → "이 Mac에서 Codex를 실행하면 갱신된다".

문제: **`ChatGPT-Account-Id` 헤더가 필요해서 오는 401/JSON 403**(전제 1의 실패 모드)도 `auth_required`로 분류되어 **"Codex를 실행하라"는 잘못된 안내**가 뜨고, 실행해도 절대 풀리지 않으며 1시간 게이트만 반복된다. 운영자는 원인을 알 수 없다(로그에도 상태 코드만 남는다).

권고:
- 토큰은 유효한데(`exp` 미래) 서버가 401/403을 주는 경우를 **별도 상태로 분리**한다. 예: `auth_rejected`(또는 `auth_required`에 `reason` 필드 추가). 봉투에 `httpStatus`는 이미 있으므로, 게이트 판단을 "`exp` 미래 + 401/403 = 1회만 재시도 후 `auth_rejected`"로 나눈다.
- 안내 문구를 상태별로 분리: `token_expired` → "Codex 실행", `auth_rejected` → "Codex 재로그인(U5) 또는 WHAM 요구 헤더 확인(전제 1)".
- 비-JSON 403(차단 페이지)에 대해서도 "재로그인으로 풀리지 않는다"만 있고 **다음 행동이 없다**. 최소한 진단 1회(`cf-ray`, `content-type`, 본문 해시)를 남기고, UA/세션 토큰 옵션을 후속 결정으로 명시한다. 이 경로가 열리면 기능이 조용히 죽는다(Consequences 373에 리스크로만 적혀 있다).

### H3. 원문 저장(D5)에 "첫 실측 확인 게이트"가 없다 — 연구 권고와 반대 방향으로 확정했다 (line 143, 350, 377)

- `docs/research/chatgpt-usage.md` §4-3, §4-치안: "**전체 raw는 비밀·식별자 유무 확인 후 보존**한다", "인증 헤더/응답의 개인 식별 필드는 KV·로그에 쓰지 않는다".
- ADR D5는 "식별자가 있더라도 가공하지 않는다. namespace는 비공개이고 Access+JWT 뒤이며 보는 사람이 주인 한 명"이라고 **선확정**했다.
- 문제는 순서다. V5(첫 실측)는 "키 경로와 식별자 키가 있는지 **적는다**"고만 하고, **식별자가 나왔을 때 무엇을 할지**를 정하지 않는다. 그러면 첫 실행에서부터 원문(이메일/계정 ID 후보 포함)이 KV와 브라우저에 들어간다. 되돌리려면 KV 삭제·재수집이 필요하다.

권고:
- V5에 **결정 게이트**를 넣는다: "식별자로 보이는 키가 있으면 KV 저장 전에 (a) 그대로 저장 + ADR에 수용 기록, (b) 해당 키만 마스킹한 사본을 KV에, 원문은 로컬 상태 파일에만 — 중 하나를 고른다." 최소한 (a)를 고를 경우 **근거를 ADR 본문에 명시**하고, 로그·fixture·상태 파일에는 절대 남기지 않는다는 규칙(D6)을 유지한다.
- "보는 사람이 데이터의 주인 한 명"이라는 근거는 맞지만, **KV는 계정의 다른 자동화·토큰(0.2 D3의 KV Edit 권한)으로도 읽힌다**는 점을 함께 적어야 Risk 평가가 정확해진다.

## Medium

### M1. `exp` 판정에 안전 마진이 없고, 실측 수명이 ADR 가정과 크게 다르다 (line 70–73, 375)

- 실측: `exp − iat = 240시간(10일)`, 현재 `exp`까지 약 62시간. ADR은 "수명 T는 전제 4로 잰다"고만 두어 **10일 규모**라는 사실이 반영되지 않았다. 공백 위험은 ADR이 암시한 것보다 작고, 대신 "10일 넘게 Codex를 안 쓰면 만료"가 실제 경계다. V12의 전환 조건 판정에 이 수치를 넣어야 한다.
- 안전 마진 없음: `exp`가 1분 뒤인 토큰으로 호출하면 401 → `auth_required` 1시간 게이트에 스스로 걸린다. `exp - now < 60초`면 호출하지 않고 `token_expired`로 두는 규칙(또는 마진 5분)을 명시한다.
- `exp` 비교는 로컬 시계 기준이다. 절전 복귀·NTP 보정 직후 오차로 조기 `token_expired`가 날 수 있으니 마진이 겸사 겸사 완충이 된다.
- 권고: `T = exp − iat`(실측 240h)을 ADR에 기록하고, 만료 판정 마진과 함께 D2에 상수로 적는다.

### M2. D2와 D4가 `account_id`에서 정면으로 모순된다 (line 66 vs 111)

- D2: "`refresh_token`, `id_token`, `OPENAI_API_KEY`, `account_id`는 **쓰지 않고 어디에도 넘기지 않는다**."
- D4: "`ChatGPT-Account-Id`는 … 전제 1에서 필요하다고 확인되면 어댑터 옵션으로 켠다. **값은 `auth.json`에서 읽어 헤더로만 흐른다.**"
- D9의 자격 증명 포트 산출물도 `{ token, expiresAt }`로 적혀 있어(275) account id가 흐를 통로가 없다.

권고: 자격 증명 포트 반환을 `{ token, expiresAt, accountId?: string|null }`로 확장하고, `accountId`는 **봉투·로그·KV에 절대 넣지 않는다**(헤더로만)는 규칙과 테스트를 함께 적는다. 또는 전제 1이 "헤더 불필요"로 확정되면 D4의 문장을 삭제한다. 어느 쪽이든 **둘 중 하나로 통일**해야 한다.

### M3. `runCycle` 도입 시 중복 실행 가드와 주기 예산이 명시되지 않는다 (line 93–100)

현재 `collector/main.mjs`의 `startResident`에는 `inFlight` 가드가 있어 밀린 주기를 건너뛴다(코드 97–118). ADR은 `runCycle`을 넣으면서 이 가드를 언급하지 않는다. 제공자가 2개가 되면 한 주기 시간이 대략 2배(wrangler 프로세스 2회 기동 포함)가 되므로, **가드는 runCycle 전체를 감싸야** 한다(제공자별로 걸면 두 제공자가 겹쳐 돌 수 있다).

또한:
- ADR은 "순차 실행으로 wrangler OAuth 갱신 충돌을 피한다"고 하는데, **주기 안에서 두 번 wrangler를 띄우는 것 자체**가 새 실패 지점이다. `runCycle`이 첫 제공자에서 60초 이상 잡히면 두 번째가 밀린다 → "한 주기 예산(예: 240초) 초과 시 다음 주기로 넘김"을 정한다.
- PM2 상주 모드에서는 예외를 삼키므로 `autorestart`가 걸리지 않는다(현 코드 확인). `--once` 경로의 종료 코드 합산(최대값)은 PM2와 무관함을 명시해 두면 운영자가 오해하지 않는다.

### M4. arch 테스트와 충돌할 수 있다 — `collector/domain`의 외부 import 허용 목록 (line 240–241, 273)

현재 CI의 `tests/arch/layers.test.ts`는 **domain이 외부 패키지를 import하면 위반**이며, 예외는 `node:crypto` 하나뿐이다. D9는 `jwt-exp.mjs`를 `collector/domain`에 두는데, base64url 디코딩을 `node:buffer`의 `Buffer`로 import하면 **CI가 실패**한다.

권고: D9에 "`jwt-exp.mjs`는 전역 `atob`/`Buffer`만 쓰고 import를 추가하지 않는다"를 명시하거나, arch 예외 목록에 `node:buffer`를 의도적으로 추가하고 이유를 적는다. 어느 쪽이든 **D2 구현 전에 정해져 있어야** 한다(지금은 구현자가 CI에서 처음 알게 된다).

### M5. `USAGE_KEY` 삭제가 진행 중인 `0.2/query`와 충돌한다 (line 138)

`shared/usage-contract.ts`에서 `USAGE_KEY`를 지우면, `0.2/query` 브랜치가 그 상수를 import하는 순간 rebase 충돌이 난다. 0.2에서 이미 `hono` 고정·arch 통합으로 병합 비용을 치렀으니, 같은 실수를 반복하지 않도록:
- `USAGE_KEY`를 **deprecated 별칭**(`USAGE_KV_KEYS.claude`)으로 남기고 0.3 후속 과제에서 삭제한다. 또는
- 0.3 계약 변경을 `0.2/query` 병합 **후**로 미루고(구간 B와 같이) 그때 삭제한다.

### M6. 상태 파일 마이그레이션의 경계 조건이 비어 있다 (line 98)

"`usage-state.claude.json`이 없으면 기존 파일을 읽고, 쓰기는 새 이름으로"는 좋다. 다만 (a) 둘 다 존재할 때 어느 쪽이 정본인지, (b) 구 파일을 언제 지우는지, (c) 구 파일이 남아 있는 동안 구버전 프로세스가 동시에 돌면 어떻게 되는지가 없다. PM2 재시작 전후로 구·신 프로세스가 겹칠 수 있으므로 "신 파일이 있으면 구 파일은 읽지도 쓰지도 않는다"를 한 줄로 못박고, 삭제는 수동 단계에 넣는다.

### M7. 제공자 값 조회는 `includes`/`hasOwn`으로 — prototype 키 방어 (line 181)

"제공자 값은 `USAGE_PROVIDERS`에 있는 것만 받는다"는 맞지만, 구현이 `USAGE_KV_KEYS[provider]`처럼 **맨 인덱스 접근**이면 `provider=__proto__`·`constructor` 같은 값이 `Object.prototype`을 반환해 `KV.get(undefined)` 같은 이상 동작으로 이어질 수 있다(Hono의 `:provider`는 퍼센트 디코딩을 하므로 `%5f%5fproto%5f%5f`도 들어온다).

권고: D7에 "`USAGE_PROVIDERS.includes(provider)`로 먼저 거르고, 키는 통과한 뒤에만 `Object.hasOwn(USAGE_KV_KEYS, provider)`로 얻는다"를 명시하고 단위 테스트(`/api/usage/__proto__`, `/api/usage/%2e%2e`, `/api/usage/claude%2F../codex` → 404)에 넣는다. 경로 주입 자체는 화이트리스트로 이미 막히지만, 이건 **구현 형태에 따라 뚫리는 종류**라 문서에 적어야 한다.

### M8. "biseo가 이 Mac, 이 계정에서 운영된 실적이 있다"는 근거가 문서에 없다 (line 20, 57)

조사 문서는 "실제 인증값을 사용한 HTTP 조회는 실행하지 않았다"(research 3줄)고 명시하고, biseo의 **코드**를 근거로 제시한다. 이 Mac·이 계정에서 WHAM이 200을 준 관측 기록은 없다. ADR이 이 문장을 근거로 D1을 정당화하므로, "biseo 코드가 이 방식을 썼다(이 Mac에서의 실호출 기록은 미확인)"로 낮추고 전제 1의 무게를 올려야 한다.

## Low

### L1. `--dry-run` 키 경로 깊이 4가 실제 구조를 놓칠 수 있다 (line 150)
`rate_limit.primary_window.used_percent`는 깊이 3이라 통과하지만, 응답에 `data.rate_limits.by_id[x].window.used_percent` 같은 중첩이 있으면 4에서 잘려 **창 객체를 못 찾는다**. 깊이를 6으로 올리거나, 잘린 경로가 있으면 `…`로 표시해 "더 깊은 키가 있다"를 알 수 있게 한다.

### L2. V7의 `wrangler kv key get` 인자 확인 (line 416)
현재 0.2 문서/스킬은 `wrangler kv key get usage:claude --remote` 형태를 쓴다. V7은 `--namespace-id`를 붙였는데, wrangler 4.159에서 이 조합이 유효한지 배포 전에 한 번 확인해 두는 편이 좋다(실패하면 검증 항목이 실행 불가가 된다).

### L3. `tokenExpiresAt`의 의미가 제공자마다 다르다 (line 142)
Claude는 자격 증명 JSON의 `expiresAt`(ms), Codex는 JWT `exp`(초→ms)다. 봉투 필드 설명에 "제공자별 출처"를 한 줄 적고, 프론트에서 이 값을 "갱신 안내 시각"으로 쓸 때의 의미 차이를 명시한다.

### L4. `redirect: 'error'`의 부작용 (line 109)
`chatgpt.com`이 307로 리전/로그인 리다이렉트를 주면 `network_error`로 떨어진다(분류 표의 "리다이렉트 → network_error"와 일치하지만, 원인 진단이 어렵다). 응답이 리다이렉트일 때 `Location`의 **호스트만** 로그에 남기는 진단을 추가하면 좋다(쿼리·경로는 토큰이 붙을 수 있어 금지).

### L5. 자격 증명 파일 권한 확인 (line 64, 307)
현재 `auth.json`은 0600으로 정상이다. 수집기가 시작 시 **권한이 0600보다 넓으면 경고 로그 한 줄**(토큰 값 없이)을 남기면 회귀를 조기에 잡는다. `auth.lock`이 존재하는 것도 확인했으니, "Codex가 잠금을 잡고 쓰는 중일 수 있음"을 D2의 재시도 근거로 인용하면 좋다.

### L6. `ZZIK_PROVIDERS` 파싱 규칙 (line 82)
알 수 없는 값(`codex2`), 빈 문자열, 공백, 대문자가 들어왔을 때 "무시+경고"인지 "기동 실패"인지 정한다. 조용히 무시하면 제공자가 사라진 것을 모른다(로그 경고 필수).

### L7. 프론트 320px는 계획은 맞지만 검증 수단이 약하다 (line 223–227, 426)
`flex-wrap` + `break-all` + 1열은 타당하다. 다만 jsdom 단위 테스트는 className만 보므로 실제 오버플로는 못 잡는다(0.2.1과 동일 한계). V10이 "실제 브라우저 기기 모드"로 적혀 있는 것은 ✓. 추가로 **요약 칩의 링크 텍스트가 길어질 때**(`ChatGPT · 인증 필요`) 320px에서 칩이 잘리지 않는지, 그리고 `id="usage-codex"` 앵커 이동 시 고정 헤더에 제목이 가리지 않는지(`scroll-margin-top`)를 항목에 넣는다.

### L8. 완전성 불변식의 정의를 한 단계 더 (line 168)
"모든 최상위 키가 카드의 출처이거나 기타 항목에 있다"는 좋다. 여기에 **"창 객체로 분류된 키의 비-창 필드도 기타 항목에 있다"** 를 명시적 테스트로 고정해야 `limit_reached` 같은 필드가 조용히 사라지지 않는다(D6 문장에는 있으나 불변식 문장에는 없다).

## 확인된 정상 항목 (그대로 유지 가능)

- **WHAM 사실관계**: 엔드포인트 `GET https://chatgpt.com/backend-api/wham/usage`, `Authorization: Bearer <tokens.access_token>`, 추가 헤더 없이 동작했다는 biseo 근거, 401/403→auth_required, `rate_limit.{primary,secondary}_window`·`limit_reached`·`used_percent`·`reset_at`(Unix 초)·`reset_after_seconds`·`limit_window_seconds` — 조사 문서와 일치.
- **JWT `exp` 판정 방식**: 서명 미검증, `exp`만 사용, payload의 다른 클레임 폐기, JWT 아님/exp 없음 → 만료 미상 후 서버 판정. 적절하고 실측으로 성립 확인(U1).
- **토큰 갱신을 수집기가 하지 않는 결정**: refresh 회전 충돌 회피, 갱신 소유자 단일화 — 0.2 D3와 일관. 대안(직접 refresh) 배제 이유도 타당.
- **제공자 격리 구조**: 제공자별 KV 키·상태 파일·게이트, `runCycle` 예외 격리, 순차 실행, 로그 provider 필드, `ZZIK_PROVIDERS` 토글 — 설계가 명확하고 테스트 표(D10)도 대응된다.
- **Worker API 보안 설계**: 화이트리스트, 요청 문자열로 KV 키 조립 금지, 봉투 `provider` 불일치 → 502, 판정 순서(config→auth→path→method→store), 미인증 시 경로와 무관하게 401(제공자 존재 여부 비노출) — 좋다.
- **`/api/usage` 별칭 유지**: 배포 순서 역전 시 기존 화면 보호 ✓.
- **원문 보존 + 완전성 불변식 + 미확인 구조 대응 3단계**: 구조 변경에 견고한 접근. 정규화를 프론트 domain에 두어 재배포 범위를 줄인 판단도 옳다.
- **`reset_after_seconds`를 `fetchedAt` 기준으로 계산**: 화면 시각 기준이 아니라는 점이 0.2의 stale 설계와 일치.
- **`limit_reached`를 집계에 반영**, 리셋 지난 항목 집계 제외(0.2.1 C5 재사용) ✓.
- **U4/U5/U6 운영 절차**: Codex 실행 → 재로그인(device code, 다른 기기 승인) → 제공자 끄기까지 단계가 구분되어 있다.
- **KV 쓰기 예산 계산**: 576/일 < 1,000/일 ✓, 제공자 4개 초과 시 재검토 조건 명시 ✓.
- **새 패키지·새 비밀·Access 변경 없음** ✓ (0.2 운영 제약 준수).

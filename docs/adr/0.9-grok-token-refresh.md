# ADR 0.9 초안: Grok 토큰 갱신 소유권

상태: **조사 초안·결정 대기** — 이슈 [#74](https://github.com/qus0in-factory/zzik/issues/74). 작성일 2026-11-14. 이 문서는 수집기 자체 갱신을 승인하거나 구현하지 않는다. ADR 0.6 D2의 OpenCode 갱신 소유권·수집기 읽기 전용 원칙을 유지한다.

## 1. 결론과 권장안

**OpenCode의 refresh token을 수집기가 복사해 독립적으로 갱신하는 방식은 권하지 않는다.** xAI의 refresh token 회전과 구 토큰 무효화가 보고됐으며, OpenCode와 다른 갱신 주체가 같은 토큰을 사용하면 한쪽의 다음 갱신이 실패해 재로그인이 필요할 수 있다. 최신 OpenCode의 잠금은 그 경로를 사용하는 참여자만 보호한다. 수집기에 별도 상태 파일이나 자체 잠금만 추가해도 이 경쟁은 사라지지 않는다. 근거와 버전 차이는 3·4절에 구분한다.

당장은 읽기 전용 수집과 `token_expired` 표시를 유지한다. 무인 연속 수집이 필요하면 **OpenCode가 갱신·저장까지 소유하는 상태 전용 인터페이스**를 먼저 검토한다. 지원 여부·설치 버전·부작용을 별도 확인하고 승인받기 전에는 모델 요청, 로그인 CLI, 직접 refresh나 DB 쓰기로 대신하지 않는다. 만료 임박·수집 중단 알림은 별도 후속 후보이며 이번에는 구현하지 않는다.

## 2. 조사 범위와 현재 동작

- 기준: zzik dev `49d3cea`(v0.6.10), 작업 브랜치 `0.7/grok-refresh`. 공개 OpenCode 소스는 upstream dev **`cbe71595e1f370ff91b3081872b96bbe56519c41`**에 고정해 읽었다. 이 SHA가 운영 Mac의 설치 버전이라는 뜻은 아니다. 설치 바이너리와의 대응은 미확인이다.
- terra explorer의 공개 소스 조사와 sol의 SHA 고정 소스 확인을 대조했다. 실제 OAuth 교환, OpenCode 실행·DB 읽기/쓰기, 계정/토큰 파일 접근, 로그인 유발 CLI, 운영 수집기·배포 변경은 하지 않았다. 토큰·계정 값이나 응답 원문은 문서에 포함하지 않았다.
- 현재 `collector/infra/usage/opencode-db-credentials.mjs:11,30,81`은 xAI credential을 `readOnly:true`로 읽고, 결과로 access와 expires만 전달한다. JSON 행 자체는 파싱하지만 refresh·계정 값을 포트나 로그로 내보내지 않는다. 별도 refresh 포트는 없다.
- `collector/domain/usage/credential-choice.mjs:37`은 만료 60초 전부터 만료로 간주하고, `collector/app/usage/run-once.mjs:105`는 `token_expired`로 usage 호출을 생략한다. OpenCode가 해당 자격 증명을 갱신하지 않으면 수집만으로 복구되지 않는 것이 현재 정책이다. [ADR 0.6 D2](0.6-grok-ollama-opencode-usage.md#d2-읽기-전용-자격-증명)

## 3. 확인한 xAI OAuth 흐름과 수명

### 공개 구현으로 확인한 사실

현재 OpenCode의 xAI 플러그인은 device OAuth에 `offline_access`를 요청한다. refresh는 `POST https://auth.x.ai/oauth2/token`에 form-urlencoded로 `grant_type=refresh_token`, 기존 refresh, 공개 클라이언트 식별자를 보낸다. 응답 access를 사용하고, **새 refresh가 있으면 교체하며 생략됐으면 기존 refresh를 유지한다.** 이 코드는 교체를 지원한다는 근거이며, 모든 서버 응답이 반드시 회전한다는 보장 자체는 아니다. [고정 소스 xai.ts:18–22,109–123,194–211](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/core/src/plugin/provider/xai.ts#L109-L123)

| 항목 | 확인 결과 | 해석 |
|---|---|---|
| access 유효 기간 | 응답 `expires_in` 우선, 없으면 JWT `exp`, 둘 다 없으면 클라이언트의 1시간 fallback | 응답마다 판단한다. 1시간은 서버 수명 보장이 아니다 |
| 약 6시간 access 수명 | zzik #74 및 OpenCode 1.18.1 사용자 보고에서 관측 | 보편적·고정 TTL로 단정하지 않는다 |
| refresh 회전 | OpenCode 사용자 보고는 새 토큰 발급 후 구 토큰 revoked·`invalid_grant`를 명시 | 동시 사용을 안전하다고 가정할 수 없다 |
| refresh 자체 만료 | 확인한 Token 스키마에는 refresh 만료 필드가 없고, 별도 TTL 저장·계산도 없다 | **정확한 절대/유휴 만료 기간 미확인.** 무기한이라고 해석하지 않는다 |
| 회전 유예·재사용 정책 | xAI의 해당 클라이언트에 대한 보장 미확인 | 재사용 시 토큰 하나만 무효인지 가족 전체가 폐기되는지도 단정하지 않는다 |

access 계산은 [고정 소스 xai.ts:214–223](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/core/src/plugin/provider/xai.ts#L214-L223), 6시간·revoked 보고는 [OpenCode #37059](https://github.com/anomalyco/opencode/issues/37059)에 근거한다. 이 보고는 구버전 사용자의 관측이며 이번 조사에서 재현하지 않았다.

xAI 공식 [Grok Build enterprise 문서의 Authentication 절](https://docs.x.ai/build/enterprise#authentication)은 browser/device 인증을 refresh 가능으로 설명한다. 확인한 문서에는 SuperGrok/OpenCode 공유 세션의 refresh TTL·회전 유예·동시 갱신 안전성 계약이 없으므로 이 부분은 미확인으로 남긴다. enterprise OIDC 설정을 해당 공유 자격 증명의 보장으로 확대하지 않는다.

### 언제 갱신하는가

고정 SHA의 `Integration.connection.resolve`는 credential이 만료 임박일 때 해당 integration의 refresh 구현을 `Credential.refresh`로 실행한다. 기본 마진은 5분이다. 이 소스 경로는 **사용 시 갱신**을 확인해 주지만, OpenCode 프로세스가 떠 있기만 하면 항상 자동 갱신된다는 근거는 아니다. 별도의 상시 keepalive나 LLM 호출을 수집기가 실행하도록 제안하지 않는다. [integration.ts:699–713](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/core/src/integration.ts#L699-L713), [credential.ts:32–34](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/core/src/credential.ts#L32-L34)

## 4. 수집기가 갱신할 때 OpenCode 로그인이 깨질 수 있는가

**가능하다. 항상 깨진다고 단정할 수는 없지만, 회전하는 동일 refresh를 공유하는 독립 갱신은 안전하지 않다.** 다음은 소스와 회전 보고에 근거한 실패 시나리오이며 이번에 실행한 실험은 아니다.

1. 수집기와 OpenCode가 동일 refresh를 읽는다.
2. 수집기가 교환을 성공시켜 새 refresh를 받는다. 구 refresh가 무효화되는 서버 정책이면 OpenCode가 들고 있는 값은 더 이상 갱신에 쓸 수 없다.
3. 새 값을 수집기 전용 파일에만 저장하면 OpenCode DB는 낡는다. 다음 OpenCode 갱신은 실패할 수 있다. 기존 access가 당장 계속 동작할 수는 있어도 갱신 체인은 안전하지 않다.
4. OpenCode DB까지 직접 쓰더라도 다른 프로세스가 이미 교환 중이면 경쟁한다. SQLite 쓰기 트랜잭션만으로 네트워크 교환까지 직렬화되지는 않는다. 서버 교환 성공 뒤 로컬 저장 실패·타임아웃도 회복이 불확실하다. 결과가 불명확한 교환을 같은 refresh로 무조건 재시도하면 위험하다.

**버전 차이:** 1.18.1의 [#37059](https://github.com/anomalyco/opencode/issues/37059)는 프로세스 간 조정 부재를 보고했다. V2의 [#50759](https://github.com/anomalyco/opencode/issues/50759)도 당시 전역 credential과 location별 갱신의 경쟁을 보고했다. 이를 현재 upstream 전체에 그대로 적용해서는 안 된다.

확인한 최신 SHA의 `Credential.refresh`에는 credential별 진행 중 작업 공유와 프로세스 간 파일 잠금이 있다. 잠금 안에서 행과 만료 조건을 다시 확인하고, 교환 중 다른 값으로 바뀌면 저장된 값을 우선하며, 그 외에는 새 값을 저장한다. 교환 timeout은 30초다. [credential.ts:142–181](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/core/src/credential.ts#L142-L181), [저장·재조회·경쟁 테스트](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/core/test/credential-refresh.test.ts#L21-L99)

이 보호는 OpenCode의 동일 잠금·저장 프로토콜을 사용하는 참여자 사이에서 유효하다. 수집기가 임의의 다른 잠금을 잡거나 DB를 직접 수정하면 자동으로 참여하지 않는다. 위 테스트는 로컬 동작 근거이고 xAI의 서버 정책·실제 설치 버전의 보장은 아니다.

## 5. 대안 평가

| 방안 | 장점 | 한계·권고 |
|---|---|---|
| 현행 읽기 전용 | 로그인 소유권을 건드리지 않음 | OpenCode 미사용 시 만료로 수집 중단. **현재 권고** |
| 만료 임박·만료 알림 | 토큰 교환 없이 사용자에게 중단 이유 전달 | 별도 상태 전이·중복 억제 설계 필요. #63의 한도 알림만으로 이 기능이 구현됐다고 보지 않는다 |
| OpenCode 소유 갱신 위임 | 잠금·교환·저장을 한 소유자가 수행 | 설치 버전과 안전한 상태 전용 API가 먼저 필요. [refresh 트리거 제안 #38687](https://github.com/anomalyco/opencode/issues/38687)은 있었지만 지원된다고 가정하지 않는다. 확인한 credential HTTP handler에는 전용 refresh가 없다. [고정 handler 소스](https://github.com/anomalyco/opencode/blob/cbe71595e1f370ff91b3081872b96bbe56519c41/packages/server/src/handlers/credential.ts#L13-L71) |
| 공유 refresh를 수집기 전용 저장소에 복사 | DB 쓰기 없이 자체 갱신 가능해 보임 | 같은 회전 체인이므로 분리되지 않음. **비권고** |
| 독립 OAuth 로그인·수집기 전용 저장소 | 공유 체인 의존성을 줄일 가능성 | 실제로 독립 세션인지·다중 로그인 상호 폐기 정책·수집 범위 확인 필요. 별도 사용자 승인과 안전한 검증 전에는 보장할 수 없음 |
| 수집기가 OpenCode DB를 갱신 | 기존 사용처와 최신 토큰 공유 가능해 보임 | 내부 잠금·스키마·캐시·로그아웃 변경과 결합됨. 단순 SQL update는 부족하며 현재 읽기 전용 정책 예외가 필요. **비권고** |

## 6. 후속 판단 게이트

- 실제 설치 버전이 어떤 refresh·잠금 구현을 포함하는지 자격 증명 접근 없이 확인한다.
- xAI/공식 클라이언트의 해당 OAuth 세션에 대한 refresh 절대·유휴 만료, 회전·재사용·다중 세션 정책 근거를 확보한다. 현재 미확인 값을 TTL 상수로 만들지 않는다.
- 위임을 추진한다면 OpenCode가 credential 선택·잠금·재조회·교환·저장을 소유하고 외부에는 성공/실패만 반환하는 지원 인터페이스를 먼저 확인한다. 내부 SDK import나 모델 요청은 안전한 갱신 API와 동등하지 않다.
- 실제 갱신·독립 로그인·OpenCode DB 변경 검증은 **별도 승인 후** 진행한다. 그 전에는 합성 토큰·가짜 서버에서 회전 경쟁, 교환 성공 뒤 저장 실패, 불명확한 timeout, 계정 전환·삭제, 재시작과 중복 실행을 검증하는 설계만 가능하다.

이번 변경은 ADR 한 파일뿐이다. 코드·설정·의존성 변경이 없어 테스트·빌드는 실행하지 않았고, 문서 diff·링크 대조와 비밀값 미포함을 확인한다. dev 병합·push는 하지 않는다.

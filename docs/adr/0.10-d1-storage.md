# ADR 0.10: Neon Postgres → Cloudflare D1

상태: **승인**. 이슈 [#93](https://github.com/qus0in-factory/zzik/issues/93). 날짜 2026-11-16.

작성: z-grok. 코드 기준은 리뷰 시점의 `dev`이며, 차트 훅은 #92 이후다. 구현 지시에 이 문서의 줄 번호를 쓰지 않는다.

입력: `/tmp/design-d1-storage.md`, `/tmp/design-d1-collector.md`, `/tmp/grok-review-d1-collector.md`(지적 1–8), `/tmp/sol-review-d1-storage.md`(R1–R10, C1–C2), `/tmp/astra-review-d1.md`(F1–F9, 필수 결정 1–10, patch A–G), `/tmp/fable-review-adr-0.10.md`(필수 수정 14건, S1·S2·S5와 추가 결정). 저장소 초안의 P0–P4라는 단계 이름은 이 문서에서 쓰지 않는다. 사용자 문장의 “P4”는 **PG 코드·드라이버 제거**이고, 여기서는 단계 **G**다. 저장소 초안의 “P4 = 180초 단축”은 단계 **F**다.

비밀(DB URL, 토큰, 이메일, 계정 id, 데이터베이스 id, R2 버킷 이름)은 적지 않는다.

## 1. 맥락

zzik의 사용량 저장소는 Neon Postgres 하나다 (ADR 0.5 P3). 수집기는 제공자 6명을 900초마다 순서로 돌리고, 스냅샷은 매번, 이벤트는 값이 바뀌거나 6시간 하트비트일 때만 남긴다. 이벤트는 30일 뒤 지운다. Worker는 `DB_URL`이 없으면 503 `storage_unavailable`을 내고, 이 응답은 Access 설정 오류 500과 다르다. 이력 API는 원문 `rawText`를 브라우저에 내리지 않는다. 커서와 id는 10진 문자열이다.

D1으로 옮기는 이유는 제공자별 수집 간격을 180초까지 줄이기 위해서다. 180초 × 30일 = 제공자당 최대 14,400이벤트다. 브라우저 캐시 상한 4,000, 동기화 예산 80, 15분 창 120, 쪽 크기 50으로는 30일 원시를 받을 수 없다. 24시간과 7일(최대 3,360)은 그 예산 안에 있다.

Workers는 Paid다. D1 한 데이터베이스의 하드 한도는 10GB다. 포함량은 계정 합산이다. 계정 잔여는 재지 않았다. 추가 요금이 0이라고 확정하지 않는다.

PoC(2026-11-16, 합성 데이터, 독립 D1, 측정 뒤 삭제)는 REST `{batch:[{sql,params},...]}`가 중간 실패를 통째로 롤백하고, 같은 operation 재전송이 행을 늘리지 않으며, 다른 payload는 거절되고, 오래된 `write_seq`가 스냅샷을 되돌리지 않음을 보였다. 그 PoC 표는 최종 DDL이 아니다. outbox 강제 종료와 TCP 절단은 재현하지 않았다. 구현 게이트로 남긴다.

이슈 #93 본문에 dual-write 동안 PG로 롤백한다는 문장이 남아 있다. 이 ADR의 단일 전환이 우선이다. 문서 반영 때 이슈 본문을 고친다.

## 3. 쓰기 계약 CollectorD1Write v1

```ts
type CollectorD1WriteV1 = {
  version: 1
  operationId: string      // 수용 때 UUID v4 한 번. 재전송에 바꾸지 않음
  provider: UsageProvider
  writeSeq: number         // 제공자별 1..MAX_SAFE_INTEGER. event id도 runAt도 아님
  envelopeJson: string     // buildEnvelope + redaction의 바이트. 재전송은 같은 바이트
  payloadSha256: string    // sha256Hex(UTF-8 JSON.stringify([1, operationId, provider, writeSeq, envelopeJson, emitEvent]))
  emitEvent: boolean       // 수용 때 고정한 changed || heartbeat
}
```

`payloadSha256`는 변경 판정용 `rawSha256`과 다르다. 시도 횟수와 전송 시각은 해시에 넣지 않는다.

원격 ack는 HTTP 2xx이고 최상위 `success`와 **모든 statement success**가 참일 때다. 타임아웃, 5xx, 잘못된 JSON, 최상위만 성공인 응답은 커밋 여부를 모른다고 보고 같은 operation을 다시 보낸다. provider API는 다시 부르지 않는다.

batch 순서:

1. receipt insert. 같은 `operation_id`와 같은 `payload_sha256`이면 기존 해시를 유지하고 `created_at_ms`는 바꾸지 않는다. 같은 id에 다른 해시면 `payload_sha256`을 NULL로 갱신하려다 NOT NULL에 걸려 batch 전체가 실패한다. `INSERT OR IGNORE`로 다른 payload를 삼키지 않는다. 같은 `(provider, write_seq)`의 다른 operation은 UNIQUE로 실패한다.
2. snapshot upsert. 조건은 `excluded.write_seq > usage_snapshot.write_seq`뿐이다. 치환할 때 envelope, status, run_at, fetched_at, raw_sha256, collector_version, operation_id, write_seq, updated_at을 함께 바꾼다.
3. `emitEvent`일 때만 event insert. `ON CONFLICT(operation_id) DO NOTHING`. 스냅샷이 이미 더 새 seq여도 이 operation의 이벤트가 없으면 3번을 실행한다. NULL `operation_id`끼리는 이 충돌에 걸리지 않는다. 백필 행을 수집기 sender가 다시 보내면 두 번째 이벤트가 생긴다. 그래서 백필 전에는 ledger outbox가 0이어야 하고, 역이관이 끝난 outbox는 지운다.

어느 문장이든 실패하면 1–3은 모두 취소된다. 정리는 이 batch에 넣지 않는다. 이벤트 삭제와 receipt 삭제는 서로 다른 HTTP이고, 제공자마다 500행 서브쿼리다. 한 번이라도 실패하면 `lastPruneAt`은 전진하지 않는다.

백필 행의 `write_seq`는 0, `operation_id`는 NULL이다. PG에는 `operation_id` 열이 없으므로 백필이 그 값을 복사하지 않는다. 수집기 upsert를 백필에 재사용하지 않는다. `0 > 0`이 거짓이라 두 번째 스냅샷 복사가 무시된다. receipt가 하나라도 있거나, 스냅샷 `write_seq` 최댓값이 0보다 크거나, ledger outbox가 비어 있지 않으면 백필은 중단한다. 그 전제에서만 백필 도구가 스냅샷을 덮어쓰고, 어느 쪽이 최신인지는 `run_at` ms로 본다. 이 비교는 백필 도구 안에만 있다.

## 4. 스키마와 id

D1 SQL의 정본은 `worker/migrations/*.sql`이다. 적용은 `wrangler d1 migrations apply`만. drizzle-kit으로 D1 HTTP에 연결하지 않는다. Worker와 수집기는 기동 때 migrate하지 않는다. PG 스키마는 G 전까지 지금 그대로 남는다. 이 ADR은 PG에 열을 더하지 않고, Neon 마이그레이션을 추가하지 않는다.

### 4.1 id와 정수

이벤트 id, 커서의 id, 버킷의 `source_event_id`, 체크포인트, export 고수위, 이관 도구의 max/min은 **정규화된 10진 문자열**이다. 앞자리 0은 없다. 기존 커서 정규식(`[1-9]\d{0,18}`)을 유지한다.

조회는 `CAST(id AS TEXT)`. 범위 비교와 명시적 INSERT의 id는 바인딩한 문자열에 `CAST(? AS INTEGER)`를 적용한다. Drizzle `integer`의 mode는 `number | timestamp | timestamp_ms | boolean`뿐이라 id 열에 mode `bigint`를 쓰지 않는다. D1 바인딩은 JS `BigInt`를 받지 않는다. `write_seq`와 epoch ms는 안전 정수인지 확인한 뒤 Number로 넣는다. 안전 정수 밖이면 그 제공자를 멈춘다.

`usage_event.id`는 `INTEGER PRIMARY KEY AUTOINCREMENT`. 이관은 기존 PG id를 명시 삽입하고, 다음 자동 번호가 그 최댓값보다 큰지 문자열로 확인한다. 지운 id는 재사용하지 않는다. 브라우저 중복 제거 키가 id이기 때문이다.

### 4.2 표

봉투는 `TEXT NOT NULL`이고 `json_valid`와 `json_type = 'object'`다. 배열, 스칼라, JSON 문자열로 한 번 더 감싼 값은 거절한다. 시각은 UTC epoch 밀리초 `INTEGER`다. `fetched_at`만 NULL을 허용한다. 초 단위 unixepoch와 SQL `strftime` ISO는 쓰지 않는다. 읽기 경계에서 `new Date(ms).toISOString()`로 커서 문자열을 만든다.

D1에 새로 만드는 표는 `STRICT`로 두고, 각 정수 열에 `typeof(col) = 'integer'` CHECK를 둔다. STRICT를 이 환경의 D1이 거부하면 마이그레이션 게이트가 실패한다. CHECK만 남기는 약화는 별도 승인이다. S3(CHECK를 승인 대안으로 내리는 안)은 채택하지 않았다.

`usage_snapshot`에 `write_seq INTEGER NOT NULL DEFAULT 0`, `operation_id TEXT NULL`.

`usage_event.operation_id`는 D1에서 `TEXT NULL UNIQUE`다. 백필은 NULL. NULL을 금지하는 CHECK는 걸지 않는다. 새 수집기 이벤트는 애플리케이션이 UUID를 넣는다. 빈 문자열은 거부한다. **PG `usage_event`에는 이 열을 만들지 않는다.** `write_seq`도 PG에 만들지 않는다. 역이관의 재실행은 해시 비교와 “같은 id면 건너뛰고, 해시가 다르면 중단”으로 한다.

```
usage_write_receipt
  operation_id   TEXT NOT NULL PRIMARY KEY
  provider       TEXT NOT NULL
  write_seq      INTEGER NOT NULL
  payload_sha256 TEXT NOT NULL
  created_at_ms  INTEGER NOT NULL
  UNIQUE (provider, write_seq)
```

`usage_bucket_checkpoint`는 제공자·스캔 버전·세대당 한 행이다. `last_processed_id`는 10진 문자열이다. 대표점의 id와 다를 수 있다. 그 id의 이벤트 행이 없으면 이 행에 `stalled_at_ms`(또는 사유 열)를 쓰고 그 제공자 버킷 cron은 멈춘다 (§4.3). 요청 경로가 이 표를 갱신하지 않는다.

`usage_bucket_boundary`는 행 종류가 둘이다. 한 키로 평평 대표의 치환과 실패 점의 보존을 같이 할 수 없다.

- `flat`: 버킷당 1행. 키는 `(provider, scan_version, data_generation, bucket_start_ms)`. 같은 버킷의 뒤 평평 표본이 이 행을 치환한다.
- `point`: 실패·값 모름·공백·리셋·계열 변화·`usedPercent` 변화당 1행. 키는 `(provider, scan_version, data_generation, source_event_id)`. 이웃 성공에 흡수하지 않는다. `source_event_id`는 10진 문자열이다.

`row_kind`는 `'flat'` 또는 `'point'`만 허용한다. 부분 UNIQUE 두 개로 위 키를 강제한다. 이 표는 D1에만 둔다. 수집기 관측 batch에 넣지 않는다. 역이관으로 PG에 복사하지 않는다. 버려도 남은 이벤트에서 cron이 다시 만든다. PG에는 버킷 표를 만들지 않는다. Neon 마이그레이션이 없다. 읽기 플래그가 postgres인 동안의 30일 경로는 원시 이벤트를 요청 안에서 §7.1과 같은 규칙으로 접는다. 간격 900에서는 그 행이 원시 상한 안이다.

`usage_export_log`가 export 고수위의 정본이다. R2 객체 목록을 정본으로 쓰지 않는다.

```
usage_export_log
  ran_at_ms            INTEGER NOT NULL
  object_key           TEXT NOT NULL
  event_high_water_id  TEXT NOT NULL
  receipt_cut_ms       INTEGER NOT NULL
  data_generation      INTEGER NOT NULL
  bytes                INTEGER NOT NULL
  ok                   INTEGER NOT NULL
```

`event_high_water_id`와 매니페스트의 id는 10진 문자열이다. `ok`는 0 또는 1이다.

### 4.3 인덱스와 정리

```
CREATE INDEX usage_event_provider_run_at
  ON usage_event (provider, run_at, id);
CREATE INDEX usage_write_receipt_created_at
  ON usage_write_receipt (created_at_ms);
```

이벤트 정리는 `provider = ? AND run_at < ?`라 복합 인덱스의 선두가 provider여도 탄다. `run_at` 단독 인덱스는 두지 않는다. 측정이 한 문장을 30초에 붙이면 그때 다시 연다.

receipt 컷오프는 `nowMs - 35 * 86_400_000`. 이벤트 컷오프는 `nowMs - retentionDays * 86_400_000`. 달력 보정이 아니다. 경계 행은 자기 `run_at_ms`가 이벤트 컷오프보다 오래되면 이벤트와 함께 지운다. 체크포인트의 `last_processed_id`는 과거로 되돌리지 않는다. 그 id가 가리키는 행이 없으면 그 제공자 체크포인트 행에 `stalled_at_ms`(또는 사유 열)를 쓰고 멈춘다. 수집기가 하루 1회 export 로그를 읽는 REST 호출(§6.1)에서 이 열도 읽어 기존 Discord로 알린다. 빈 체크포인트에서 다시 세지 않는다.

### 4.4 이관 해시

`migration_row_sha256`는 이벤트와 스냅샷 모두에 대해 **키 정렬 canonical envelope 전체**를 포함한다. 입력 튜플은 `id|provider|run_at_ms|status|raw_sha256|canonical_envelope`다. `raw_sha256`만으로 통과시키지 않는다. 열의 provider, status, runAt ms가 봉투 필드와 다르면 실패다. 로그에는 해시와 개수만 남긴다. 원문은 메모리에만 둔다.

같은 id의 역이관은 해시를 먼저 비교한다. 같으면 건너뛴다. 다르면 트랜잭션을 중단한다. `ON CONFLICT DO NOTHING`으로 내용이 다른 행을 삼키지 않는다.

백필 전에 PG `run_at`의 마이크로초를 검사한다. 밀리초로 자르면 정렬이 timestamptz 정렬과 달라지는 쌍이 하나라도 있으면 이관을 중단한다. 개수만 보고한다. 잘린 ms만 맞다고 통과시키지 않는다. 현 수집기는 JS ISO 밀리초를 쓰므로 이 검사는 통과할 가능성이 높다. 실측으로 미세초가 있다고 보고한 것은 아니다.

## 5. 수집기

로컬 ledger는 `ZZIK_STATE_DIR/collector-ledger.sqlite`다. `node:sqlite`의 `DatabaseSync`를 infra에 둔다. 운영 Node는 v24.22.1에 고정한다. 이 API는 release candidate다. 부모 디렉터리 0700, DB·WAL·SHM 0600, umask 077, WAL, `synchronous=FULL`. 토큰, refresh token, 이메일, 원문 자격은 넣지 않는다. 이미 가린 봉투와 gate만 넣는다. 네트워크를 기다리는 동안 로컬 트랜잭션을 열어 두지 않는다.

표: `provider_state(provider PK, state_json, revision, next_seq, acked_seq, last_started_at_ms, next_due_ms)`, `outbox(operation_id PK, provider, write_seq, payload_json, payload_sha256, created_at_ms, attempts, next_attempt_at_ms, alert_json, UNIQUE(provider, write_seq))`, import 마커.

수집기는 export 파일을 만들지 않는다. `ZZIK_STORE=d1`에서만, 하루 한 번 D1 REST로 `usage_export_log`의 마지막 `ok`와 체크포인트 stall 열을 읽는다 (§6). 그 코드는 B2다.

### 5.1 기동

| 상태 | 동작 |
|---|---|
| 마커 없음, 기존 JSON 있음 | 한 트랜잭션으로 가져오고 마커를 쓴다. 대상은 provider별 gate, previous, alerts, lastEventAt, lastRun과 `usage-prune.json`의 `lastPruneAt`. 롤백이 마커를 지운 뒤의 재전환도 이 행이다 |
| 마커 있음, ledger를 열 수 없거나 비어 있음 | 중단. 빈 정상 DB로 만들지 않는다. 수집을 시작하지 않는다 |
| 마커가 rolled-back | 그 ledger를 열지 않는다. JSON이 있으면 위 첫 행으로 다시 가져온다. JSON이 없으면 중단한다 |
| 마커 없음, JSON 없음 | 최초 기동 |

`lastPruneAt`가 없거나 시각이 깨져 있으면 그 주기의 prune를 건너뛰고 보고한 뒤, 다음 24시간에 기존 규칙으로 실행한다. 첫 D1 주기에서 바로 지우지 않는다.

다음 `write_seq`는 `max(로컬 next, 미전송 max, 원격 snapshot write_seq) + 1`이다. 첫 전환(빈 D1, 백필 직후, 로컬 next가 없음)만 1이다. 재전환은 이 식이다. 미전송 `(provider, write_seq, operation_id, payloadSha256)`이 receipt와 다르면 재번호 없이 중단한다. 같은 operation·같은 hash는 ack로 지운다. 안전 정수 상한이면 중단한다.

PM2 `instances: 1`에 더해 프로세스 수명 동안의 단독 잠금으로 이중 기동을 막는다. 두 번째 프로세스는 78로 끝난다.

### 5.2 수용과 ack

1. 제공자 잠금 → 영속 gate → 허용할 때만 provider API/CLI → 기존 봉투.
2. 직전 수용 `runAt`보다 이른 새 `runAt`은 그 한 건을 버린다. seq와 이벤트를 발급하지 않는다. `clock_skew`를 남긴다. 다음 due는 `max(now, 직전 runAt) + interval`이다. heartbeat 판정은 이 폐기 **다음**에 온다. 같은 제공자에서 연속 3회면 그 제공자만 멈추고 Discord로 알린다. 프로세스 전체를 한 번의 NTP 1초 후퇴로 내리지 않는다.
3. 로컬 트랜잭션에서 seq, operation, 봉투 바이트, `emitEvent`, hash, 알림 목록을 함께 쓴다. `lastStartedAt`과 `nextDue`는 이 트랜잭션이 다시 계산하지 않고, 이미 정한 값을 기록만 한다.
4. sender는 제공자 안에서 FIFO, 제공자 사이는 round-robin이다. 성공하면 `remoteCommitted` previous, `remoteCommittedLastEventAt`, `acked_seq`를 전진하고 그 operation을 지운다.
5. 원격이 실패해도 새 관측을 수용할 수 있다. `remoteCommitted`는 전진하지 않는다. `kvOk`는 원격 ack일 때만 참이다. 큐 수용을 `{ok:true}`로 보고하지 않는다.

`lastStartedAt`은 실제 upstream 호출이 시작된 시각만 갱신한다. 다음 upstream은 `lastStartedAt + intervalSec` 이전에 시작하지 않는다. gate 때문에 upstream을 건너뛴 tick은 `lastStartedAt`을 움직이지 않는다. `nextDue`는 자격 확인용 로컬 tick이다. 한 제공자의 inFlight는 1이라 로컬 tick과 upstream은 겹치지 않는다. 호출이 끝나 이미 due가 지났으면 후보에 한 번만 다시 넣는다. 과거 tick을 몰아서 실행하지 않는다. sleep 복귀도 제공자당 한 번이다. 개별 타임아웃(API 10초, Antigravity 15초와 종료 유예, Ollama 3초)은 유지한다. sender 타임아웃은 15초다. 전역 240초 예산은 D1 모드에서 제거한다. Postgres 모드는 기존 직렬 주기와 240초 예산을 유지한다.

`changed`와 하트비트는 직전 **수용 체인**의 관측과 비교해 operation에 고정한다. 비교 대상은 직전 수용 관측(captured previous·capturedLastEventAt)이다. 체인이 끊기면 §5.3대로 둘 다 `remoteCommitted`로 되돌린 뒤 수용한다. 실패 봉투의 carry(`previous`)는 마지막으로 수용한 성공 관측이다. `lastRun.tokenExpiresAt`은 토큰 갱신 판정의 입력으로 남는다.

알림: 수용 트랜잭션에서 `diff`를 한 번만 계산해 operation에 붙이고 baseline을 그 시점에 전진한다. 그 operation의 **첫** 원격 ack에서, 관측 나이가 그 제공자의 interval 이하일 때만 그 목록을 한 번 보낸다. 재전송은 diff를 다시 하지 않는다. 나이가 interval을 넘긴 재생과 7일 따라잡기에는 알림을 붙이지 않는다. ollama를 180초로 둔 뒤에는 D1 재시도 한 번(기준 5초, 상한 300초)만으로도 나이가 interval을 넘겨 알림이 빠질 수 있다. 그 누락은 F의 기대 동작이다 (§11 F). webhook의 exactly-once는 범위 밖이다. 기존 인증 gate, `expiresAt`가 바뀌면 인증 대기를 푸는 동작, provider 429와 Cloudflare 429의 분리는 유지한다. Cloudflare 429는 provider `failCount`를 올리지 않는다. Retry-After가 더 길면 그것을 따른다.

### 5.3 장애

| 상황 | 동작 |
|---|---|
| provider 응답 후 로컬 수용 전에 종료 | 그 관측은 없다. 다음 due에 다시 수집한다. provider 호출의 exactly-once는 없다 |
| 로컬 수용 후 HTTP 전에 종료 | 같은 operation을 보낸다 |
| D1 커밋 후 ack 전에 종료 | 같은 operation·hash·seq를 다시 보낸다 |
| 400 (SQL, 제약, 다른 payload) | 그 제공자 큐를 멈춘다. 다른 제공자는 계속한다. Discord. 운영자가 그 operation을 버리고 재개하기 **전에** captured previous와 capturedLastEventAt을 `remoteCommitted`로 되돌린다. 버린 operation 바로 뒤의 미전송 operation 하나는 N-1 기준으로 `emitEvent`와 `payloadSha256`을 다시 고정한다(receipt가 없을 때만) |
| 401/403 (D1) | **새 수집과 sender를 모두 멈춘다.** 큐는 지우지 않는다. Discord. 토큰을 갈아 끼운 뒤에만 재개한다. provider 인증 gate와 별개의 이유 코드다 |
| 429 (D1) | Retry-After 이상, sender 전역 대기. provider gate를 열지 않는다 |
| 타임아웃, 5xx | 같은 operation. 기준 5초, 지수 상한 300초, full jitter. 더 긴 Retry-After가 우선 |
| disk full, 로컬 커밋 실패 | 새 provider 호출을 멈춘다. 큐를 덮거나 버리지 않는다. 상주 프로세스는 유지하고 상태 실패로 보고한다 |
| 큐 256MiB 또는 25,000건 또는 최장 7일 | 새 수집을 멈추고 Discord. 7일을 넘긴 operation은 자동 전송하지 않고 격리한다. 조용히 지우거나 만료 이력을 다시 넣지 않는다 |
| 격리분을 보내지 않고 수집을 재개 | captured previous와 capturedLastEventAt을 **둘 다** `remoteCommitted`로 되돌린다. emit 기준만 되돌리지 않는다. 버린 operation 바로 뒤의 미전송 operation 하나는 N-1 기준으로 `emitEvent`와 `payloadSha256`을 다시 고정한다(receipt가 없을 때만) |
| 역이관 뒤 재전환 | 기동 import가 읽는 previous·lastEventAt은 롤백 절차가 쓴 JSON이다. 그 값은 `remoteCommitted`(PG에 들어간 마지막 관측)다 |

체인이 끊긴 뒤의 `changed` 정의: 버린 operation N이 N-1 대비 변화였고, 다음 수용 N+1의 봉투가 N과 같더라도, 비교 대상은 N-1이다. N+1이 N-1과 다르면 `emitEvent=true`다. N과 비교해 `emitEvent=false`로 고정하면 N-1에서 N+1로의 변화가 이력에서 빠진다. 버린 operation 바로 뒤에 이미 수용된 미전송 operation도 receipt가 없을 때만 같은 N-1로 `emitEvent`와 `payloadSha256`을 다시 고정한다. 400 폐기, 7일 격리 미전송 재개, 역이관 후 재전환이 이 규칙의 전부다.

상주 프로세스는 원격 미ack만으로 종료하지 않는다. 그 주기 stderr에는 제공자별 exit 3을 남긴다. 로컬 수용 실패는 exit 4에 해당하는 상태로 새 호출을 멈춘다.

SIGTERM/SIGINT는 **PG 모드와 D1 모드 모두**에서 즉시 `process.exit`하지 않는다. D 1단계가 멈추는 프로세스는 아직 PG 모드다. 새 관측을 막고, in-flight provider 호출과 PG 트랜잭션, D1 모드라면 sender의 현재 HTTP가 끝나기를 최대 30초 기다린 뒤 종료한다. 30초를 넘기면 로컬 트랜잭션 밖이라는 전제에서 종료하고, 미ack operation은 다음 기동이 같은 id로 보낸다. Antigravity 자식 프로세스가 남았는지는 운영 절차에서 확인한다. 이 유예는 B3에서 PG 경로에 들어간다.

### 5.4 Postgres 모드

`ZZIK_STORE` 미지정과 `postgres`는 G1 전까지 지금처럼 postgres 클라이언트 `max: 1`과 `runCycle` 직렬이다. 새 scheduler의 동시성 2를 이 모드에 켜지 않는다. 쓰기와 prune가 트랜잭션 중간에 겹치지 않게, PG 경로에는 한 번에 하나의 writer만 둔다. `kv`, `both`, `dual`, 그 외 값은 78이다. `DB_URL`은 G 전까지 수집기 Postgres 경로에 남는다. D1 모드의 실행 경로는 `DB_URL`을 열지 않는다. 검증·역이관 스크립트는 연다. 이 모드에는 outbox가 없다.

## 6. 자격, 회전, export

토큰 발급 화면에서 리소스가 데이터베이스 한 개로 줄어드는지 확인한다. 줄어들지 않아도 이 ADR은 D1 Write를 수용한다. 발급 결과(계정 단위인지, 데이터베이스 단위인지)만 운영 기록에 적고 값과 id는 적지 않는다. 운영 데이터베이스에 DELETE를 시험하지 않는다. PoC에 쓰인 Wrangler OAuth는 상주 토큰의 권한이 아니다.

회전은 90일과, 노출이 의심될 때다. 새 토큰을 env-file에 넣고 수집기를 재시작한다. `--update-env`나 `pm2 save`로 토큰을 PM2 환경에 복사하지 않는다. 재시작 뒤 receipt가 하나 생기는 것을 개수와 코드로만 확인한 다음 이전 토큰을 폐기한다. 로그 명령으로 환경을 덤프하지 않는다.

### 6.1 정기 export

수집기의 0600 파일과 “운영자가 같은 날 기기 밖으로 복사”는 두지 않는다. 정기 export는 **같은 계정의 비공개 R2**다. Worker Cron Trigger가 D1 바인딩으로 읽고 R2에 넣는다. 하루 1회다. 12시간 간격은 최악 RPO를 줄이는 선택지로 적기만 하고 택하지 않는다.

`wrangler.jsonc`에 `triggers.crons`와 `r2_buckets`를 더한다. 리뷰 시점의 파일에는 두 키가 없었다. 파일 전문은 비밀 때문에 이 개정에서 다시 열지 않았다. 핸들러는 `scheduled` 하나이고 `controller.cron` 문자열로 15분 버킷 writer와 하루 1회 export를 가른다. `fetch`만 있는 진입점에 scheduled를 더한다. R2 바인딩은 조립 루트에서 export 함수에만 주입한다. `fetch` 라우터의 인자에 넣지 않는다.

Access는 바꾸지 않는다. cron은 HTTP가 아니라서 Access 정책, 302, workers.dev 404와 무관하다. `workers_dev: false`, `preview_urls: false`를 유지한다. 프로덕션에 `/__scheduled` 수동 트리거를 만들지 않는다. 운영 검증은 첫 cron 뒤 R2 객체가 있고 바이트가 0보다 크며, `usage_export_log`의 그 회차 `ok`가 1인 것으로 한다. 값과 봉투는 출력하지 않는다.

R2 버킷 생성은 D1 생성과 같은 등급의 승인이다. 공개 접근과 custom domain은 없다. 버킷 이름과 계정 id는 문서에 적지 않는다. 객체 키는 날짜와 파트 번호만 둔다.

객체에는 가린 봉투와 receipt 해시만 있다. 토큰, 이메일, 원문 자격은 없다. 보존은 R2 lifecycle으로 **30일 이상**이며 코드가 객체를 지우지 않는다. lifecycle 규칙의 실제 삭제는 이번에 호출해 확인하지 않았다. 배포 게이트는 그 설정이 있는지만 본다.

증분이다. 30일 전량(측정 평균 약 0.11GB, 최악은 수 GB)을 한 번에 읽어 한 객체로 쓰지 않는다. Worker 메모리 128MB와 D1 결과 상한 50MB는 이전 리뷰가 공식 문서를 인용한 값이고, 이번에 다시 조회하지 않았다. 그 수치가 완화돼도 증분을 유지한다.

한 회차의 내용:

- `usage_event` 중 `id`가 직전 고수위보다 큰 행. id 오름차순. `CAST(id AS TEXT)`. 페이지는 1,000행을 넘지 않고, 누적 본문이 4MB에 닿으면 페이지를 끊는다.
- `usage_snapshot` 6행 전량.
- receipt는 `created_at_ms`가 직전 컷보다 큰 것만.
- 매니페스트 `{eventHighWaterId, receiptCutMs, dataGeneration, exportedAtMs}`. id는 10진 문자열이다.

한 파트가 5MiB를 넘기지 않게 페이지 경계에서 자른다. 5MiB는 멀티파트 최소 크기로 인용된 값이며 이번에 재확인하지 않았다. 멀티파트 API는 필수로 두지 않는다. 보통의 하루(180초·6제공자·전량 emit이면 2,880이벤트 × 평균 약 1.3KB ≈ 4MB)는 파트 하나다. 최악 봉투가 이어지면 파트가 여러 개다.

고수위 정본은 현재 `data_generation`의 마지막 `ok` 로그다. Time Travel이나 §6.2 복구로 세대가 바뀌면 그 세대의 ok 로그가 없을 때 고수위 0에서 다시 쓴다. 옛 세대의 고수위를 이어서 쓰지 않는다.

실패 감지: Worker에 Discord webhook 비밀을 넣지 않는다. 수집기가 하루 한 번, 이미 가진 D1 REST 자격으로 `usage_export_log`의 마지막 `ok` `ran_at_ms`와 제공자 체크포인트의 `stalled_at_ms`(§4.3)를 읽는다. 현재 시각과의 차이가 36시간을 넘거나, 그 읽기가 실패하거나, stall이 있으면 기존 Discord 경로로 알린다. 이 읽기는 B2에 두고 `ZZIK_STORE=d1`에서만 실행한다. PG 모드는 D1 자격 없이 읽지 않아 오경보를 내지 않는다. 새 토큰 종류는 없다. `lastPruneAt`과는 무관하다.

G 게이트의 “7일 export 성공”은 R2에 일자 객체 7개이고, 각 객체의 이벤트 고수위가 단조 증가하는 것이다.

비용은 공식 포함량 기준의 추정이다. 계정 잔여를 재지 않았고 0을 확정하지 않는다. R2 저장 10GB/월 포함. 증분 30–45일치는 평균 수백 MB다. 최악 봉투(약 131KB × 2,880/일 ≈ 380MB/일)가 30일이면 약 11GB로 포함량 근처다. Class A PUT는 월 1백만 포함이고 이 기능은 하루 수 회다. Cron은 Workers 요청으로 집계되며 월 수십 회다. 증분 D1 읽기는 하루 수천 `rows_read` 수준으로 본다. 복원 때 R2에서 로컬로 받는 이그레스 요금은 미확인이다.

### 6.2 복구

G 이후 D1을 복구할 때, 그리고 G 전에 Time Travel을 쓸 때:

1. 수집과 sender를 멈춘다.
2. R2 객체를 매니페스트 순으로 읽어 새 D1에 명시 id로 넣는다. 읽는 자격(`wrangler r2 object get`의 OAuth 또는 R2 읽기 토큰)은 이 복구 때만 발급하고 끝나면 폐기한다. 상주 토큰이 아니다. `sqlite_sequence`와 다음 자동 번호를 복원된 최대 id에 고정 여유(예: 10^6)를 더한 값으로 올린다. 그래도 유실 구간의 id 재사용을 배제하지 못하므로, 복구 절차는 `USAGE_HISTORY_SCAN_VERSION`을 올려 원시 캐시를 함께 무효화한다.
3. ledger에 남은 operation 중 receipt에 없는 것만 같은 id로 보낸다. 새 operation id를 만들어 중복 이벤트를 넣지 않는다.
4. `data_generation`을 올린다. 버킷 체크포인트는 그 세대부터 다시 만든다. export 고수위도 0부터 다시 센다. `scanVersion`은 스캔 규칙 버전으로 남겨 두고 복구 세대로 쓰지 않는다.
5. 브라우저 버킷 캐시 키는 `scanVersion`과 `data_generation`을 함께 본다. 원시 이력 캐시는 `scanVersion`만 보므로, 2번의 `USAGE_HISTORY_SCAN_VERSION` 인상이 그 캐시도 무효화한다.

Time Travel(Paid, 30일, 복구 추가 요금 없음)은 D1 파일 안의 시각 이동이다. ledger, 브라우저 캐시, PG, R2를 되돌리지 않는다. 앱 보존 30일·receipt 35일을 대신하지 않는다. 고수위를 올리기 전에는 writer와 cron을 켜지 않는다. 북마크 바이트가 10GB 한도에 들어가는지는 확인하지 않았다. 용량을 임의로 2배 하지 않는다.

RPO는 마지막 성공 R2 객체의 완료 시각부터 센다. 목표 24시간.

## 7. 30일 버킷

경로 `GET /api/usage-history/:provider/buckets`. `bucketSec=900`만 허용한다. `from`과 `until`은 기존 시각 정규식이고 둘 다 필수이며 `until > from`이다. 길이가 30일을 넘으면 400 `invalid_query`다. 저장소를 읽기 전에 거절한다. 알 수 없는 제공자는 404다. `claude/buckets`를 제공자 이름으로 보지 않는다. `Cache-Control: no-store`.

표본 원소는 기존 이력 표본과 같은 함수로 만든다. `rawText`는 넣지 않는다. `values: null`은 값 모름, `values: []`는 계열 소멸이다. 이 뜻은 유지한다.

정렬된 30일 창은 버킷 시작이 2,880개다. 경계가 900초 격자에 안 맞으면 2,881개 창에 걸칠 수 있다. “항상 ≤ 2,880점”은 쓰지 않는다. 점은 버킷 개수가 아니라 경계 개수다.

`anchor`는 원시 `usage_event`에서 `from` 직전 마지막 ok다. 경계 표에서 만들지 않는다. 그 이벤트가 보존 밖으로 지워졌으면 null이다.

### 7.1 무엇을 남기는가

이벤트를 id 오름차순으로 본다. 다음이면 **점을 남겨** 선이 끊기거나 값이 바뀌게 한다.

- status가 ok가 아니거나 `values`가 null이다 (실패·값 모름).
- 직전 이벤트와의 `run_at` 차이가 그 표본의 `intervalSec`의 2배를 넘는다 (공백). interval을 모르면 1,800초를 넘을 때다.
- 리셋 시각이 바뀌거나, 계열 집합이 바뀌거나, 계열 `usedPercent`가 바뀐다.

같은 900초 버킷 안에서, 위 조건에 걸리지 않는 연속 ok 표본은 마지막 시각의 점 하나로 바꾼다. 기존 차트 함수가 같은 값·같은 리셋의 중간 점을 빼는 것과 같다. 실패 점을 이웃 성공에 흡수하지 않는다. 구간의 마지막 성공만 남겨 앞의 실패를 지우는 초안 규칙은 폐기한다.

같은 버킷의 성공 값이 매번 같으면 15분 해상도로 접힌다. 값이 바뀌는 피크와 리셋과 실패는 점으로 남는다. 점이 많으면 한 응답이 4,000점을 넘기지 않고 `complete: false`로 자른다. 4요청이면 30일이 끝난다는 전제는 두지 않는다. 재요청은 기존 80/120 예산에 들어간다.

응답의 `samples.runAt`은 버킷 시작이 아니라 그 이벤트의 `run_at`이다. `[from, until)` 밖 점은 내지 않는다. 가장자리 버킷을 대표점 하나로 대체하지 않는다.

### 7.2 단일 writer

요청 경로에는 버킷 쓰기를 두지 않는다. 두 요청이 겹칠 때의 CAS는 D1 batch에서 뒤 문장을 건너뛰지 못한다. 조건부 UPDATE가 0행이어도 batch는 성공하고, 같은 batch의 경계 upsert는 이미 적용된다. 그래서 CAS로 “실패하면 쓰지 않는다”를 만들지 않는다 (S1).

writer는 15분 Cron 하나다. Cron이 겹쳐도 된다. 체크포인트 UPDATE는 `CAST(last_processed_id AS INTEGER) < CAST(? AS INTEGER)`일 때만 한다. 경계 upsert는 결정적이라 겹침 자체는 수렴하지만, 늦은 실행이 죽으면 `flat` 대표가 한 페이지 전 시각에 머물 수 있다. 요청은 경계 표의 `[from, until)`과, 체크포인트 이후의 원시 꼬리만 읽는다. 180초여도 15분 꼬리는 제공자당 5행 이하다. cron이 밀리면 꼬리가 길어진다. 요청은 그때도 체크포인트를 움직이지 않는다. 읽기가 8초를 넘기거나 점이 4,000을 넘으면 `complete: false`다. 그 잘림은 읽기 예산이지, 요청이 다시 이어서 쓰는 커서가 아니다.

cron 한 번의 상태:

1. `(provider, scan_version, data_generation)`의 `last_processed_id`를 읽는다.
2. 그 id의 이벤트 행을 **다시 읽어** 직전 상태(run_at, status, values)를 복원한다. 현재 버킷의 평평 대표는 이벤트 행이 아니라 경계 표 `flat` 행에서 복원한다. 페이지마다 메모리 상태를 다음 페이지로 넘긴다. 프로세스가 죽으면 다음 cron이 1번부터 한다. 체크포인트에 비교 키를 중복 저장하지 않는다. 행이 없으면 그 제공자 체크포인트 행에 `stalled_at_ms`(또는 사유 열)를 쓰고 멈춘다. 수집기가 하루 1회 export 로그를 읽는 REST 호출(§6.1)에서 이 열도 읽어 기존 Discord로 알린다. 빈 체크포인트에서 다시 세지 않는다.
3. `id`가 `last_processed_id`보다 큰 행을 `ORDER BY id`로 100행씩 본다. §7.1을 적용해 `flat`은 치환하고 `point`는 넣는다.
4. 그 페이지의 경계 upsert가 끝난 뒤에만 `last_processed_id`를 전진한다. 대표가 바뀌지 않은 페이지도 전진한다. 기대값 CAS와 `meta.changes` 판정은 두지 않는다.

`complete: true`는 그 요청의 응답이 범위 안 점을 4,000 이하로 다 담았다는 뜻이다. 고정 고수위까지 요청이 스캔했다는 뜻이 아니다. 스캔 고수위는 cron의 체크포인트다. 처리 도중 생긴 더 새 id는 다음 cron이다.

Paid에서 `db.batch()` 한 번은 statement 수와 관계없이 D1 쿼리 1회로 센다. cron은 행마다 호출하지 않는다. statement 하나의 바인딩은 100개 이하다. batch 30초 제한은 페이지를 100행으로 두어 피한다. `(provider, run_at, id)`로 `provider + id > ? ORDER BY id`의 `rows_read`를 측정한다. 반환 행 수와 rows_read는 다른 값이다. 이 측정이 나쁠 때 `run_at` 단독 인덱스를 더하는 결정은 이 ADR에 없다.

`scanVersion`이 다르면 그 버전만 읽는다. 이벤트 정리로 옛 경계 행을 지워도 체크포인트를 과거 id로 되돌리지 않는다. 이미 지운 이벤트를 다시 스캔하지 않는다. 운영자가 캐시를 버리려면 `data_generation`을 올려 새 키로 다시 만든다.

30일 응답은 `HistoryCacheRecord.samples`에 넣지 않는다. 원시 레코드의 원하는 시작은 최대 7일이다. 7일을 오래 비운 뒤의 원시 따라잡기는 기존 예산과 `complete: false` 재개를 그대로 쓴다. 180초 7일은 3,360이라 상한 4,000 안이다. 8일 이상을 원시 캐시에 넣지 않는다.

클라이언트 구현은 #92 이후의 캐시 교체 규칙을 기준으로 테스트한다. 저장소 초안의 훅 줄 번호를 구현 위치로 쓰지 않는다.

## 8. 용량

2026-11-16 읽기 전용 집계. `octet_length(envelope::text)`. 이벤트 1,299행. 제공자 평균을 14,400번씩 더하면 봉투 본체 111,254,400B ≈ 0.111GB다. compact JSON이나 D1 페이지와 같지 않다. 이 값을 설계 용량의 기준으로 둔다. 페이지 여유를 더하면 약 0.2GB다. receipt 35일 약 100,800행은 40MB 아래로 보고, 이벤트 10만 행 경보에는 넣지 않는다. ollama를 180초로 둬도 봉투가 약 500B로 거의 변하지 않으면 이벤트는 하트비트가 대부분이라 이 산식을 바꾸지 않는다.

원문 상한은 rawText 64KiB다. 저장되는 것은 그 문자열을 한 번 더 JSON으로 감싼 봉투다. 합성에서 원문 약 64KiB의 유효 JSON이 봉투 약 131KB가 됐다. 그 크기가 86,400행이면 11GB를 넘어 10GB 한도를 넘는다. “64KiB면 약 6.9GB”는 안전 상한이 아니므로 폐기한다. 이 합성은 운영 봉투가 그 크기라는 뜻이 아니다. 64KiB 원문 상한은 그대로 둔다. 새 봉투 상한을 이 ADR에서 도입하지 않는다.

경보 (Discord, 수집은 운영자가 멈출 때까지 유지):

- 이벤트 행 수 100,000.
- 이벤트 봉투 바이트 합 또는 D1 `file_size`가 8GB 이상.
- prune 마지막 성공이 36시간을 넘김.
- `usage_export_log`의 마지막 `ok`가 36시간을 넘거나, 그 하루 1회 읽기가 실패함.
- 제공자 체크포인트의 `stalled_at_ms`(또는 사유 열)가 있다. 위와 같은 하루 1회 읽기다.

30일 보존을 자동으로 줄이지 않는다. 한도에 닿는 변경은 별도 승인이다. 행 쓰기 월 100만은 포함 5,000만 안에 있다. 계정 잔여는 모르므로 요금 0을 확정하지 않는다. R2 추정은 §6.1이다.

큐: 3분 × 6 × 7일 = 20,160관측. 측정 평균이면 본체 약 26MB. 64KiB 원문이 연속이면 256MiB 제한이 먼저 걸린다. 그 제한은 조용한 유실을 막기 위한 정지선이다.

## 9. 대안

| 대안 | 왜 두지 않는가 |
|---|---|
| 인증 Worker ingest | 토큰에서 임의 SQL과 삭제를 뺄 수 있다. 사용자는 D1 Write와 삭제 위험을 수용하고, 회전·정지·R2 export로 보완하라고 정했다. Access 정책은 바꾸지 않는다 |
| dual-write | `write_seq`는 D1에만 있다. PG와 D1에 같은 관측을 쓰면 ack가 다시 갈라진다. Neon은 900초보다 짧은 쓰기를 견디지 못한다 |
| Postgres 모드에서도 동시성 2 | 공유 클라이언트 `max: 1`은 트랜잭션 전체를 잠그지 않는다. A가 커밋하면 B의 롤백이 B의 삽입을 지우지 못한다 |
| id를 Number 또는 Drizzle bigint 모드로 | mode에 bigint가 없고, D1은 BigInt 바인딩을 받지 않는다. Number는 2^53 밖에서 커서를 바꾼다 |
| 버킷 = 구간 마지막 성공 하나 | 구간의 실패가 선에서 사라지고 세그먼트가 이어진다. 실패 은폐를 금지했다 |
| 실패가 있으면 버킷 전체를 unknown | 구간의 성공 값까지 지운다. 경계만 남기는 쪽을 택했다 |
| 요청 경로의 체크포인트 CAS | D1 batch는 CAS가 0행이어도 같은 batch의 upsert를 남긴다. 15분 단일 writer로 경합을 없앤다 |
| 수집기 0600 파일과 수동 복사 | 토큰과 Mac에 RPO가 묶인다. R2 cron이 그 경로를 대체한다 |
| export 12시간 cron | 최악 RPO는 줄어든다. 이 개정은 하루 1회와 36시간 경보를 유지한다 |
| D1 export API로 전량 덤프 | 결과 크기와 메모리에 전량이 들어가지 않는다. 증분 페이지를 택했다 |
| PG `operation_id` 열과 Neon 마이그레이션 | 역이관은 최대 약 2만 행의 단일 트랜잭션과 해시 비교로 재실행된다. 열을 추가하지 않는다 |
| STRICT 없이 typeof CHECK만 | S3는 채택하지 않았다. STRICT와 CHECK를 같이 둔다. STRICT 거부는 게이트 실패다 |
| 원시 상한 14,400과 예산 해제 | 30일 cold load와 IndexedDB가 커진다. 24h·7d는 원시로 충분하다 |
| 수집 때 계열 표까지 쓰기 (ADR 0.7 H1) | 스캔 정본이 둘이 된다. 수집 batch가 커진다 |
| 이벤트 `run_at` 단독 인덱스 | 정리 질의는 provider가 선두다. 삽입마다 쓰기가 늘어난다 |
| 0.6.19 바이너리로 30일 차트까지 복구 | 14,400 표본은 그 바이너리의 4,000 상한에 걸린다. G 전 복귀 실행본은 버킷 경로가 있는 빌드다 |
| G 이후에도 PG 무손실 복귀 | 드라이버를 지운 뒤의 보장은 forward-fix와 R2 export다 |
| 보존 일수 자동 축소 | 사용자 결정인 30일 이력을 장애 대응이 바꾸면 안 된다 |
| Worker에 Discord 비밀을 두어 export 실패를 직접 알림 | 새 비밀을 넣지 않는다. 수집기가 export 로그를 읽어 기존 webhook으로 알린다 |

## 10. 결과와 리스크

- 수집기 저장 실패는 더 이상 “다음 주기에 그 표본이 사라짐”이 아니다. 수용된 관측은 7일 안에서 같은 operation으로 재전송된다. 그 대신 로컬 디스크와 ledger 무결성이 새 실패 지점이다.
- G 전 롤백은 플래그 한 장이 아니다. D1을 읽을 수 있고 역이관 트랜잭션이 커밋되어야 무손실이다. D1이 오래 불통이면 PG에 있는 마지막 시각까지의 화면으로 돌아가며, 그 이후는 비어 있다. 그 구간의 알림은 다시 보내지 않는다. R2 export가 있어도 G 전에는 역이관이 1차 경로다.
- 계획 정지의 관측 공백은 백필이 끝나는 시각까지다. 그 뒤 수집기는 D1에 쓰고, Worker 플래그가 바뀌기 전까지 화면만 그 백필 시각에 머문다. 호출하지 않은 구간은 catch-up으로 채워지지 않는다.
- 롤백 뒤 JSON만 갱신하고 마커를 남겨 두면, 재전환이 뒤처진 ledger의 previous로 `changed`를 계산한다. 마커 제거가 그 경로를 닫는다.
- D1 Write 토큰 유출은 임의 SQL과 데이터베이스 삭제다. 회전, 401/403 정지, R2 export가 보완이다. 토큰이 데이터베이스 한 개로 제한되는지는 발급 때 확인한다.
- 측정 평균 용량은 10GB의 약 2%다. 원문이 상한 근처에 붙으면 한도를 넘는다. 8GB 경보가 그 전에 울리게 한다.
- 64KiB REST p95는 표본 10개의 최댓값(494.82ms)과 같다. 운영 SLO로 쓰지 않는다. binding 지연은 원격 개발 경로다. custom domain 읽기 지연은 전환 뒤 상태 코드로 본다.
- REST 79요청에서 429는 0이었다. ceiling을 측정한 값이 아니다. 정상 부하는 약 2요청/분이다. catch-up 상한 1요청/초는 이 앱만 보면 300요청/5분이다. 계정의 다른 API와 합산된다.
- `node:sqlite`가 안정 채널로 바뀌기 전에 동작이 바뀔 수 있다. Node 고정이 그 위험을 묶는다.
- ollama 180초는 간격 분리와 쓰기 지속을 보여줄 뿐, 버킷 고밀도와 provider 429를 보여주지 않는다. 그 둘을 F 전체의 통과로 읽지 않는다.
- 이슈 #93 본문은 아직 dual-write다. 배포·수집기 스킬은 ADR §11을 가리키는 한 줄만 두었고, 절차 본문은 구현 때 맞춘다.

## 11. 이행 A–G

각 단계의 코드 배포와 설정 전환은 다른 승인이다. 수집기 재시작, `wrangler secret`, D1 생성, R2 버킷 생성, 플래그 변경, Neon 삭제는 그 단계의 사용자 승인 없이 하지 않는다. 배포 스킬의 쿠키 없는 302, workers.dev 404, 인증된 운영 화면 확인은 모든 배포에 남는다. skip은 통과가 아니다. 원격 opt-in을 건너뛰고 배포 게이트를 통과시키지 않는다.

담당: 수집기·ledger·scheduler·capability·quiesce·export 경보(REST로 로그를 읽고 Discord)는 **z-sol**. Worker 스키마·마이그레이션·읽기 저장소·버킷 라우트·바인딩·scheduled export·R2·복구 도구는 **z-ds**. 이관 SQL은 z-ds가 만들고, operation 대조와 ledger 상태 변환은 z-sol이 만든다. 해당 patch의 둘은 게이트에 서명한다.

**B1, B2, B3, C, D**는 핵심 경로다. 각 patch는 **교차 리뷰와 work-reviewer 두 관문을 통과한 뒤에만** 배포한다. 한 관문만 통과한 배포는 하지 않는다.

**A**, **E**, **export patch**는 선배포 예외다. A는 꺼진 스키마와 도구다. E는 버킷 읽기와 15분 writer이고 간격은 900이다. export patch는 비밀 없는 읽기와 R2 파생 쓰기다. 배포 순서는 export patch → E다. 15분 분기는 E 배포와 함께 활성화되며 별도 플래그는 없다. 예외는 D1이 서빙 저장소가 아닌 동안의 배포만 가리킨다. 302·404와 사용자 승인을 빼지는 않는다. A·E·export patch의 두 관문은 **D 착수 전에** 통과해 있어야 한다. 통과 기록이 없으면 D를 열지 않는다.

B를 한 patch로 두지 않는다. 각 B patch 뒤의 운영은 같다. PG 직렬, 900초, D1 쓰기 꺼짐.

### A. 계약, 스키마, 도구

선배포 예외. 배포 후: 운영은 Postgres 읽기·쓰기, 900초. D1 기능은 꺼져 있다. PG 스키마는 바꾸지 않는다. Neon 마이그레이션 승인과 `pnpm db:migrate` 단계는 없다.

게이트: 최종 DDL이 D1 마이그레이션 파일과 같다. receipt PK는 NOT NULL. STRICT와 typeof CHECK. JSON 객체 거부. 경계 표의 `flat`/`point` 키가 서로 치환되지 않는다. workerd의 D1 바인딩에서 id `9007199254740993`, 그 이웃, 부호 있는 64비트 최댓값이 10진 문자열로 왕복한다. node:sqlite만 통과한 것으로 이 게이트를 대체하지 않는다. 합성 PG에서 명시 id는 `OVERRIDING SYSTEM VALUE`로 **한 트랜잭션**에 들어가고, 커밋 뒤에 sequence를 `max(id)` 이상으로 올린 다음 기본 삽입이 `max+1`이다. sequence 변경은 그 트랜잭션이 롤백돼도 되돌아가지 않는다는 테스트를 포함한다. 삽입 커밋과 setval 사이에는 기본 삽입을 하지 않는다. 해시 불일치 역이관은 트랜잭션이 중단된다. 레이어 테스트, 기존 회귀, `pnpm test`, `TZ=UTC pnpm test`, `pnpm typecheck`, `pnpm typecheck:collector`, `pnpm build`.

롤백: 그 커밋을 되돌린다. 운영 D1 쓰기는 없다. PG에 되돌릴 새 열은 없다.

### B1. ledger, outbox

핵심 경로. 두 관문 후 배포. 배포 후: 운영은 Postgres 직렬, 900초. 상태 파일은 아직 ledger로 바꾸지 않는다. sender는 포트 뒤에 두고, postgres 모드에서는 호출하지 않는다.

게이트: 세 갈래 기동과 rolled-back 마커. `lastPruneAt` import. 빈 ledger와 깨진 ledger. disk full. 이중 기동. seq 충돌은 재번호 없이 중단. 큐 상한과 7일 격리. 격리 재개와 400 폐기가 previous와 lastEventAt을 둘 다 `remoteCommitted`로 되돌리는지. 그 다음 관측의 `changed`가 버린 N이 아니라 N-1과 비교되는지. 버린 operation 바로 뒤의 미전송 operation 하나가 receipt가 없을 때 N-1 기준으로 `emitEvent`와 `payloadSha256`을 다시 고정하는지. 400 폐기 게이트는 sender(B2) 없이 ledger 연산으로만 시험한다. 백필 도구의 outbox 0 거부는 C다.

롤백: 코드 되돌림. 운영 JSON은 그대로다.

### B2. writer

핵심 경로. 두 관문 후 배포. 배포 후: 운영은 계속 Postgres 직렬, 900초. D1 writer는 `ZZIK_STORE=d1`이 아니면 호출되지 않는다. export 로그와 체크포인트 stall의 하루 1회 REST 읽기와 Discord도 이 patch이고, `ZZIK_STORE=d1`에서만 실행한다.

게이트: 로컬 커밋 전·후, 원격 커밋 후 ack 전 종료. receipt → snapshot → 조건부 event. 같은 operation·같은 hash 재전송. 다른 hash. 작은 seq. emitEvent false. HTTP 200이어도 statement 실패면 미ack. prune는 관측 batch와 분리. 알림은 재시도 1회의 첫 ack에서 1번, 나이가 interval을 넘기면 0번. `kvOk`는 원격 ack일 때만. dry-run은 원격 I/O 0.

롤백: 코드 되돌림. 운영 쓰기는 아직 PG다.

### B3. scheduler, quiesce

핵심 경로. 두 관문 후 배포. 이 patch는 PG 모드의 종료를 바꾼다. SIGTERM 30초 유예가 PG 모드에도 적용된다. 동시성 2는 여전히 D1 모드에서만 켜진다.

게이트: Postgres 경로에서 제공자 둘의 쓰기가 겹치지 않는다. 합성으로 겹친 BEGIN이 롤백을 무력화하는 경우를 PG 모드 코드 경로에서 만들 수 없어야 한다. D1 모드만 동시 2, 같은 제공자 1, Antigravity CLI 1. `lastStartedAt`과 `nextDue`가 따로. 슬립은 1회. 시계 1초 후퇴는 그 관측만 폐기, 연속 3회는 그 제공자 정지. capability 없이 180은 거부. `ZZIK_INTERVAL_SEC_<PROVIDER>`만 그 제공자를 바꾼다. PG 모드 SIGTERM이 즉시 exit하지 않고 30초 안에 in-flight를 기다린다.

롤백: 코드 되돌림. 운영 간격은 900이다.

### C. 빈 D1에 스키마, 백필

핵심 경로. 두 관문 후 배포. 백필 도구가 운영 D1에 쓴다. 배포 후: Worker 플래그는 postgres. 수집기는 postgres, 900초, 직렬. C 직후 D1의 유일한 writer는 백필 도구다. export patch와 E 뒤에는 cron도 쓴다.

게이트: `jsonb`가 object가 아닌 행이 있으면 중단. 마이크로초 정렬 검사. 봉투를 포함한 `migration_row_sha256`, 개수, min/max id를 문자열로. 스냅샷 `write_seq` 0, `operation_id` NULL, receipt 0, ledger outbox 0. 하나라도 아니면 백필 거부. 백필 도구의 ledger outbox 0 검사는 이 patch(C)에 있다. `sqlite_sequence`가 최대 id 이상. 최종 DDL로 실 D1에서 중간 실패, 마지막 실패, 다른 payload, 오래된 seq를 다시 실행한다. 단언은 행 수, seq, HTTP 상태, 안전한 code. 토큰과 원문은 출력하지 않는다. 역이관 리허설은 합성 데이터로 하고, 운영 PG에 쓰지 않는다. 리허설 항목: 단일 PG 트랜잭션, 커밋 후 setval, 다음 기본 삽입, 해시 불일치 중단, outbox 삭제와 마커 제거가 한 ledger 트랜잭션, ledger→JSON의 gate·alerts·previous(출처 포함)·lastEventAt·lastRun·`usage-prune.json`의 lastPruneAt, 같은 id 재실행이 행을 늘리지 않음, 재전환 import가 옛 ledger previous를 쓰지 않음.

롤백: 백필을 멈추고 D1 표를 비운다. 수집기는 그대로다.

### export patch

선배포 예외. **C 뒤, E 앞, D 앞.** 순서는 export patch → E다. D 4단계(수집기 `d1` 기동)부터 하루 1회 객체가 생기려면 이 patch가 먼저 나가 있어야 한다. scheduled 핸들러, `triggers.crons`, `r2_buckets`, `d1_databases` 바인딩. 15분 분기는 E 배포와 함께 활성화되며 별도 플래그는 없다. E 전에는 경계를 쓰지 않는다.

게이트: 증분 경계, 고수위 단조, 세대가 바뀌면 고수위 0, 매니페스트, 4MB 페이지 절단, 복원 왕복(명시 id, 펜스는 복원 최대 id + 고정 여유). Miniflare의 scheduled와 R2로 로컬에서 본다. 실원격은 배포 뒤 첫 객체 1개(키 존재, 바이트 > 0, 로그 ok=1)다. 값과 봉투는 출력하지 않는다. 수집기 하루 1회 읽기가 36시간 초과, 읽기 실패, 체크포인트 stall을 Discord 경로로 알리는 단위 테스트는 B2다. 그 읽기는 `ZZIK_STORE=d1`에서만 돈다.

롤백: cron을 빼고 그 커밋을 되돌린다. R2 객체는 lifecycle에 맡긴다. 수집기는 아직 PG다.

### D. 전환 창

핵심 경로. 두 관문 후 배포. A·E·export patch의 두 관문 기록도 D 착수 전에 있어야 한다. 없으면 D를 열지 않는다. 한 유지 창이다. 순서는 고정이다. 수집기 d1 기동은 Worker 읽기 플래그보다 앞이다.

1. PG 모드 수집기의 새 관측을 막는다. B3의 SIGTERM 유예로 in-flight가 끝나거나 30초 한도에 걸렸는지 확인한다. Antigravity 자식을 확인한다.
2. PG in-flight 트랜잭션이 끝났는지만 확인한다. 이 모드에는 outbox가 없다. ack 완료, 응답 유실, 미전송의 분류는 이 단계가 하지 않는다. 그 분류는 4단계 이후의 실패 재시도와 롤백 drain에서만 한다.
3. 최종 백필. receipt 0, `write_seq` 최댓값 0, ledger outbox 0을 다시 확인한 뒤에만 쓴다. §4.4와 `sqlite_sequence`. `operation_id`는 NULL이다.
4. `ZZIK_STORE=d1`로 수집기를 시작한다. capability 파일은 없다. 간격은 900이다. **첫 전환**의 다음 `write_seq`는 1이다. 재전환이면 §5.1이다. 첫 6제공자의 receipt와 스냅샷 seq를 개수로 확인한다. 여기부터 관측은 D1에 쌓인다. 화면은 아직 PG다.
5. `USAGE_READ_STORE=d1` 플래그만 다시 배포한다. 바인딩(`d1_databases`, cron, R2)은 export patch와 E에서 이미 나갔다. 드라이버 삭제와 플래그를 한 배포에 넣지 않는다.
6. 승인된 opt-in으로 대상 원격 D1에 대해 배포된 Worker 번들의 6제공자 200과 decode boolean, 이력 쪽의 id 문자열을 확인한다. 이 원격 opt-in은 D 창 전에 미리 돌려 유지 창을 줄일 수 있다. 값은 상태, 개수, boolean만. 로컬 Miniflare는 이 게이트를 대체하지 않는다. 공개 preview와 Access 우회는 만들지 않는다. workers.dev는 404, 쿠키 없는 본 경로는 302다.
7. 인증된 운영 화면에서 최신값과 이력을 본다.

4단계 이후에 drain이 필요하면 operation을 ack 완료, 응답 유실(같은 id로 한 번 더), 미전송으로 나눈다. 미전송을 새 id로 만들지 않는다. drain이 실패하면 아래 롤백으로 간다. D1에 수집기 행이 없으면(receipt 0) 표를 비워도 된다.

롤백 (G 전 무손실 경로):

1. 새 관측을 중지한다. D1 모드면 sender의 현재 HTTP를 30초까지 기다린다.
2. D1을 열 수 없으면 역이관을 시작하지 않는다. 플래그를 postgres로 되돌린다. 화면은 정지 시각까지의 PG다. 그 시각 이후는 없다. 사용자에게 그 공백을 말한다. 그 구간의 알림은 다시 보내지 않는다. 이것이 허용 손실이다. JSON의 previous는 PG 마지막 행과 맞는 `remoteCommitted`다.
3. D1을 열 수 있으면 outbox를 분류한 뒤, 미전송 operation은 같은 id로 D1에 drain하고, 그다음 D1에 있는 관측을 PG로 넣는다. 이벤트 명시 id와 스냅샷 덮어쓰기는 **하나의 PG 트랜잭션**이다. 해시가 다르면 중단한다. receipt는 PG 표로 복사하지 않는다. 커밋 뒤에 sequence를 `max(id)` 이상으로 올리고 다음 기본 id를 확인한다. setval은 트랜잭션 밖이며 위로만 움직인다. 그 사이에 수집기를 켜지 않는다.
4. 3번을 했으면 PG 커밋 성공 뒤에만, 2번 경로(D1을 열 수 없음)면 바로, ledger 트랜잭션 하나에서 역이관된 outbox 행을 삭제하고 `acked_seq`를 맞추고, JSON을 쓰고, import 마커를 지우거나 `rolled-back`으로 표시한다. JSON 필드는 gate, alerts(현재 ledger 값), previous, lastEventAt, lastRun이다. `lastPruneAt`은 `usage-prune.json`에 따로 쓴다. previous는 PG 커밋에 들어간 마지막 관측(역이관 직후의 remoteCommitted) 하나다. 2번 경로는 역이관 커밋이 없으므로 2번에서 정한 remoteCommitted를 그대로 쓴다. 전환 전 백업 JSON으로 덮지 않는다. PG 커밋과 이 트랜잭션 사이에 죽으면 역이관을 다시 실행한다. 같은 해시는 건너뛰고 outbox 삭제를 다시 한다.
5. `USAGE_READ_STORE=postgres`, `ZZIK_STORE=postgres`, 간격 900. capability 파일을 지운다. `ZZIK_INTERVAL_SEC_*`의 180을 치운다.

재전환 규칙:

- 마커가 없거나 rolled-back이면 JSON을 다시 import한다. 롤백 전에 쓰던 ledger의 previous, lastEventAt, gate를 이어서 쓰지 않는다.
- D1이 비어 있으면(receipt 0, write_seq 최댓값 0, 새 ledger의 outbox 0) 첫 전환과 같은 백필을 하고 다음 `write_seq`는 1이다.
- 2번 경로가 아닌 재전환에서 D1에 이전 세대가 남아 있으면 전량 백필을 다시 하지 않는다. PG에만 있는 id만 해시 대조 후 넣는다. 이미 D1에 있는 id로 두 번째 이벤트를 만들지 않는다. 그 행의 `operation_id`는 NULL이다. 다음 `write_seq`는 §5.1이다.
- 2번 경로로 돌아간 뒤의 재전환은 D1 표를 비우고 `data_generation`을 올린 뒤 첫 전환과 같은 전량 백필을 한다(그 D1 잔여 관측은 이미 허용 손실로 선언됨).
- 재전환 기동 전에 previous와 lastEventAt이 `remoteCommitted`와 같은지 확인한다. 다르면 그 값으로 맞춘 뒤에 켠다.

담당 실행: z-sol이 수집기, z-ds가 Worker 플래그. 사용자 승인 없이 4–6을 하지 않는다.

### E. 버킷

선배포 예외. **export patch 다음, D 전에 배포한다.** 그러면 D 롤백 실행본에 버킷 경로가 이미 있어, G 전 복귀가 버킷 없는 바이너리에 기대지 않는다. 간격은 900인 채로 둔다. 15분 분기는 이 배포와 함께 활성화되며 별도 플래그는 없다. cron과 `d1_databases` 바인딩은 export patch가 먼저 넣는다. 기능 확인 뒤에 30일 탭이 이 경로를 쓴다. D1에서는 15분 cron이 경계 표를 채운다. 읽기가 postgres인 동안에는 같은 §7.1 규칙으로 요청이 원시를 접는다. PG에 표를 추가하지 않는다.

게이트: 실패가 구간 중간에 있으면 세그먼트가 이어지지 않는다. 공백과 리셋과 계열 소멸이 점으로 남는다. 평평한 ok만 버킷 안에서 접힌다. `flat`과 `point`가 서로를 지우지 않는다. 체크포인트는 대표 id와 따로 전진하고, 페이지 재개 때 `last_processed_id` 행을 다시 읽어 직전 상태를 복원한다. 요청 두 개가 겹쳐도 경계 행이 되돌아가지 않는다(요청이 쓰지 않음). 가장자리 `from`/`until`. anchor는 원시 이벤트의 직전 ok이고, 그 행이 없으면 null이다. 보존 삭제가 경계 행을 지우면서 체크포인트는 그대로다. 4,000점과 8초 읽기에서 `complete: false`. 실 D1 cold에서 쿼리 수, rows_read, 응답 바이트, 벽시계를 측정한다. 고밀도 합성(제공자당 1만 행 규모)의 경계 접기를 여기서 재고, 그 결과를 두 번째 제공자 확대 게이트의 전제로 남긴다. 7일 원시와 요약·툴팁·#92 캐시 교체는 회귀하지 않는다. 인증된 화면에서 30일 탭을 범위 전환, 빈 이력, 오류와 함께 본다.

롤백: 30일 탭을 원시 경로로 되돌리는 설정. 간격이 900인 동안에는 원시 30일이 상한 안에 들어온다. F 이후에 이 롤백만 하면 30일 화면이 다시 상한에 걸린다. F 이후의 저장소 롤백은 D의 무손실 경로를 쓰고, 버킷 코드는 PG 읽기에도 남겨 둔다.

### F. 72시간 뒤 간격

D 이후 72시간 동안 모든 제공자는 900초다. 볼 것은 D1 성공 코드, `write_seq`가 제공자별로 역행하지 않는지, 이벤트 행 수, R2 export 성공(로그 ok, 고수위 단조)이다. PG 행 수가 계속 같기를 기대하지 않는다. PG 쓰기는 D에서 멈췄다.

180초 키를 쓰기 전의 진입 게이트:

- 위 72시간이 끝나 있다.
- 버킷 경로는 이미 배포되어 있다(E는 D 전). capability 파일 `{ "v":1, "readStore":"d1", "bucketRoute":true }`는 운영자가 직접 쓴다. 수집기가 배포 상태를 HTTP로 추측하지 않는다. 파일이 없거나 파손되었거나 필드가 다르면 180은 78이다.
- E의 합성 고밀도(제공자당 1만 행 규모) 경계 접기 측정이 기록되어 있다. 이 기록은 F 진입 전제다.

진입 게이트를 통과하면 claude를 뺀 다섯 제공자를 동시에 180초로 내린다. 키는 `ZZIK_INTERVAL_SEC_CODEX=180`, `ZZIK_INTERVAL_SEC_ANTIGRAVITY=180`, `ZZIK_INTERVAL_SEC_OPENCODE=180`, `ZZIK_INTERVAL_SEC_GROK=180`, `ZZIK_INTERVAL_SEC_OLLAMA=180`이다. 다섯 키를 함께 쓴다. `ZZIK_INTERVAL_SEC_CLAUDE`는 두지 않는다. 키가 없으면 그 제공자는 900이다. `ZZIK_INTERVAL_SEC_CLAUDE`가 있고 값이 900 미만이면 capability가 있어도 78이다. 179 이하는 항상 78이다.

429 관측: provider 429와 D1 429를 따로 센다. D1 429는 provider gate를 열지 않는다(§5.3). provider 429가 있으면 Retry-After와 그 제공자의 gate 대기를 기록한다. 코드는 간격 키를 늘리거나 줄이지 않는다. 내린 뒤 72시간 안에 provider 429가 한 번도 없으면 “실측 429를 관측했다”고 적지 않고, 그 항목은 합성 테스트로 닫는다.

자동 backoff: 기존 provider gate와 Retry-After 대기만 한다. 그 대기는 간격 키를 다시 쓰지 않는다. 백오프 상한(429는 3600, 5xx는 900, 인증은 6시간)은 interval과 따로 논다. 180초로 자르지 않는다.

즉시 900 복귀:

- 한 제공자의 gate가 열리거나 그 제공자의 429를 관측하면, 운영자가 그 제공자의 `ZZIK_INTERVAL_SEC_*`만 즉시 지운다. 수집기가 키를 스스로 바꾸지 않는다. 나머지 180초 키는 유지한다. claude는 이미 900이다.
- D1 non-2xx, outbox 최대 나이 180초 이상, capability 불일치는 capability 파일과 다섯 키를 모두 지운다.
- 데이터까지 PG로 되돌릴 때는 D의 경로다. 드라이버는 아직 있다.

내린 뒤 72시간:

- D1 non-2xx가 있으면 다섯 키와 capability를 지워 F 전체를 900으로 되돌린다.
- 한 제공자의 429 또는 gate는 그 제공자만 즉시 900으로 되돌린다.
- outbox 최대 나이 < 180초.
- 아직 180인 제공자의 receipt 증가는 하루 약 480(receipt+snapshot, 2문장). claude는 하루 약 96. 중간에 900으로 되돌린 제공자는 약 96으로 센다.
- 180초인 제공자의 알림이 빠져도 실패로 보지 않는다. interval이 180초라 백오프 한 번에 나이가 넘을 수 있다. claude(900)의 알림 누락은 이 기대에 넣지 않는다.
- 동시성 2, 같은 제공자 1, Antigravity CLI 1은 유지한다. claude는 900이다.

ollama만으로는 버킷 고밀도와 provider 429를 보지 못했다. 다섯을 동시에 내려도 그 둘이 같은 방식으로 닫히지는 않는다.

- 고밀도(제공자당 1만 행)는 해소되지 않는다. 이벤트는 값이 바뀌거나 6시간 하트비트일 때만 남는다. 180초 폴링은 스냅샷과 receipt를 늘릴 뿐, 매 회를 이벤트로 만들지 않는다. ollama 봉투가 약 500B이고 이벤트가 하루 수 건인 것과 같다. 값이 바뀌면 경계 점이 ollama 하트비트보다 늘 수 있으나, 그 증가를 1만 행 증명으로 보지 않는다. 증명은 E의 합성 측정이고 F 진입 전에 기록이 있어야 한다. 내린 뒤 72시간의 경계 행 수는 그 기록을 대신하지 않는다.
- provider 429는 관측될 수 있게 된다. ollama는 인용한 분당 한도 대비 여유가 커서 429가 나기 어려웠다. 대상에 usage 한도가 있는 codex, antigravity, opencode, grok가 들어 있다. 72시간 안의 발생은 보장하지 않는다. 한 번도 없으면 실측으로 적지 않고 합성 테스트로 닫는다. 조사 문서가 인용한 분당 호출 한도는 이 개정에서 다시 호출해 확인하지 않았다. 180초는 그 인용 대비 여유의 설명이지, 한도를 재측정한 값이 아니다.

이 단계에서 보는 것: 제공자별 간격 분리, `lastStartedAt`과 `nextDue`, 동시 2에서 claude가 900을 유지하는지, 180초 제공자의 D1 쓰기가 이어지는지, receipt 35일 정리, 키 하나를 지우면 그 제공자만 900으로 돌아가는지.

게이트: `postgres`에서 어떤 제공자든 180 → 78. `d1`+capability 없음+180 → 78. `d1`+capability+다섯 키 180 → 그 다섯만 허용하고 claude는 900. `ZZIK_INTERVAL_SEC_CLAUDE=180` → 78. 다섯 중 한 키가 없으면 그 제공자는 900. 179 → 78. 백오프 상한이 interval과 따로 논다. 인증된 화면. outbox 나이. 보존 정리.

롤백: 한 제공자는 그 키만 지운다. 전체는 capability 파일과 다섯 키를 지워 900으로 되돌린다. 데이터까지 PG로 되돌릴 때는 D의 경로다. 드라이버는 아직 있다.

### G. PG 제거와 Neon

F의 첫 제공자(ollama)를 줄인 뒤 **7일**간 R2 export가 성공하고, 사용자 별도 승인이 있어야 한다. 성공은 일자 객체 7개와 이벤트 고수위의 단조 증가다. G1과 G2를 한 작업으로 묶지 않는다.

G1: Worker와 수집기 실행 경로에서 postgres.js를 제거한다. `nodejs_compat`는 다른 의존을 확인한 뒤에만 뺀다. 수집기 실행 경로에서 `DB_URL`을 뺀다. 이 시점부터:

- `USAGE_READ_STORE` 미지정, 오타, 바인딩 없음은 503 `storage_unavailable`다. postgres로 떨어지지 않고, 조용히 D1로 간주하지도 않는다.
- `ZZIK_STORE=postgres`와 수집기 저장소 미지정은 종료 78이다. 동작하는 값은 `d1`뿐이다.
- 역이관 스크립트 파일은 저장소에 남겨도 실행 대상이 사라진다.
- 복구는 forward-fix와 R2 export다. 무손실 PG 복귀를 보장하지 않는다.

게이트: scratch D1에 R2 객체를 복원하고 id 고수위 펜스와 outbox 재생을 한 번 실행한다. 운영 D1을 덮어쓰지 않는다. 배포 스킬의 302, 404, 6제공자 확인. 인증된 화면.

G2: 추가 승인으로 `DB_URL` secret 제거와 Neon 프로젝트 삭제. 삭제 전에 마지막 성공 R2 객체의 완료 시각이 24시간 안인지 확인한다.

G 이후 D1이 불통이면: 수집을 멈춘다. 마지막 성공 R2 객체로 §6.2를 한다. 그 시각 이후의 관측은 허용 손실이다. ledger 디스크가 살아 있으면 receipt에 없는 operation만 이어 보낸다. ledger까지 없으면 RPO는 그 R2 객체다. 목표 RPO는 24시간이다.

## 13. 열린 질문

설계를 막는 질문은 아래뿐이다. 간격 키, id, 롤백의 경계, 버킷의 실패 처리, ingest 미채택, dual-write 금지, export의 위치, 180초 대상(claude를 뺀 다섯 제공자의 동시 적용)은 결정이다.

1. R2를 정본 export로 둔다. RPO는 마지막 성공 객체의 완료 시각부터다. 버킷 이름과 계정 id는 승인 기록에만 두고 이 문서에는 적지 않는다. lifecycle이 30일 이상을 실제로 지우는지는 배포 때 설정을 확인한다. 이 개정은 그 API를 호출하지 않았다.
2. D1 포함량의 계정 잔여와 Time Travel 바이트가 10GB에 합산되는지는 미확인이다. R2 포함량의 잔여와 복원 이그레스도 미확인이다. 요금 0과 “용량의 2배”는 이 ADR의 숫자가 아니다.
3. 토큰이 데이터베이스 한 개로 좁혀지는지는 발급 화면에서 확인한다. 좁혀지지 않아도 D1 Write 수용은 유지한다.
4. 180초 대상은 claude를 뺀 codex, antigravity, opencode, grok, ollama이고, F에서 다섯을 동시에 적용한다. 이름은 결정이다. 실측 429가 72시간 안에 나오는지는 설계를 막는 질문이 아니다. §11 F의 관측 규칙으로 닫는다. 없으면 실측했다고 적지 않고 합성 테스트로 닫는다. 저장소가 180초를 보장하지 않는다. 한도 수치는 다시 호출하기 전까지 인용의 자리에 둔다.
5. 이슈 #93 본문의 dual-write 문장은 아직 그대로다. 이 ADR의 단일 전환이 우선이며, 이슈 본문 수정은 이 승인 커밋에 없다. 배포·수집기 스킬에는 “D1 이전 진행 중(ADR 0.10), 단계별 게이트는 ADR §11” 한 줄 포인터만 두었다. 절차는 구현 때까지 이 ADR에 두고 스킬로 복사하지 않는다. `wrangler.jsonc`에 `triggers.crons`, `r2_buckets`, `d1_databases`를 더하는 작업은 export patch다.
6. Cron Trigger가 같은 cron을 겹쳐 실행하는지는 공식 문서를 다시 조회하지 않았다. §7.2는 겹침을 허용하고, 체크포인트 UPDATE는 id가 더 클 때만 하는 것으로 닫았다.

## 개정 이력

### 2026-11-16 검토 반영

상태: 제안 → 검토 반영. 입력은 `/tmp/fable-review-adr-0.10.md`. 저장소는 수정하지 않았다.

- 필수 수정 14건을 본문에 넣고 부록에 `fable-1`–`fable-14`로 적었다.
- S1. 30일 버킷 writer는 15분 Cron 하나다. 요청 경로의 CAS는 제거했다. 페이지를 다시 열 때는 `last_processed_id` 행을 재조회한다. 경계 행은 `flat`과 `point`로 나눈다.
- S2. 역이관은 PG 단일 트랜잭션이다. PG `operation_id` 열과 Neon 마이그레이션은 없다. 백필이 operation_id를 복사하지 않는 대신, outbox 삭제·백필 전 outbox 0·재전환 때 기존 id를 다시 넣지 않는 것으로 중복 이벤트를 막는다.
- S5. D는 최종 백필 직후 수집기 `d1`을 켜고, Worker 읽기 플래그는 그다음이다.
- export는 수집기 0600 파일이 아니다. 같은 계정 비공개 R2와 Worker Cron이고, 증분 페이지와 `usage_export_log`가 정본이다. 수집기가 하루 한 번 로그를 읽어 36시간을 넘으면 Discord로 알린다. 보존은 30일 이상이다. `wrangler.jsonc`에 `triggers.crons`와 `r2_buckets`를 더하고 Access는 그대로다. 이 patch는 C와 D 사이다.
- 첫 180초 제공자는 ollama다. 그 단계는 버킷 고밀도와 provider 429를 검증하지 못한다. 그 검증은 두 번째 제공자 확대 게이트에 둔다.
- B·C·D는 교차 리뷰와 work-reviewer를 통과한 뒤에만 배포한다. B는 B1 ledger/outbox, B2 writer, B3 scheduler로 나눈다. A·E·export patch는 선배포 예외다. E는 D 전에 올린다.
- 롤백의 ledger→JSON에 previous와 lastRun을 넣는다. previous의 출처를 나누고, 마커를 지워 재전환이 JSON을 다시 가져오게 한다. 수용 체인이 끊기면 `changed`는 remoteCommitted previous 기준이다.
- G1 이후 읽기 플래그 미지정은 503, 수집기 `postgres`와 미지정은 78이다.
- 미채택: S3(STRICT+CHECK 유지), 12시간 export cron, D1 전량 export API, 요청 경로 CAS.

### 2026-11-16 승인

상태: 검토 반영 → 승인. 입력은 `/tmp/fable-recheck-adr-0.10.md`. 이슈 [#93](https://github.com/qus0in-factory/zzik/issues/93). 저장 위치는 `docs/adr/0.10-d1-storage.md`. 새 설계는 더하지 않았다. M2의 선택이었던 “행이 없으면 공백 point로 재개”는 넣지 않았다.

### 2026-11-16 F단계 대상

사용자 결정과 opus 결정. 결정표, §11 F, §12, §13, 이 이력만 고쳤다. 이전 이력과 부록의 “첫 제공자는 ollama”, “두 번째 제공자 확대 게이트”, “Antigravity는 마지막”은 그 시점의 기록으로 남긴다. 이 절이 그 결정을 대체한다.

- 사용자 결정. claude를 뺀 codex, antigravity, opencode, grok, ollama를 180초로 한다. claude는 900초다.
- opus 결정. 시점은 F 그대로다. D1 단독 전환, 버킷 배포, 900초로 72시간을 본 다음이다. PG에 원격 쓰기가 있는 동안 900초 미만은 종료 78이다.
- 한 명씩 확대하지 않고 다섯 키를 동시에 180으로 둔다. `ZZIK_INTERVAL_SEC_CLAUDE`를 180으로 두지 않는다. 그 키가 900 미만이면 78이다.
- 버킷 고밀도(제공자당 1만 행 합성)는 F 진입 전제다. E의 측정 기록이 있어야 다섯 키를 쓴다.
- provider 429에서 코드는 간격을 바꾸지 않는다. provider gate와 Retry-After가 기다린다. 상한은 interval과 따로다. 한 제공자의 429 또는 gate가 열리면 운영자가 그 키만 즉시 지워 900으로 되돌린다. D1 non-2xx, outbox 나이 180초 이상, capability 불일치는 다섯 키와 capability 파일을 모두 지운다.
- ollama만의 공백. 다섯을 동시에 내려도 1만 행 고밀도는 해소되지 않는다. 이벤트는 값 변화나 6시간 하트비트일 때만 남기 때문이다. provider 429는 한도가 있는 제공자가 대상에 들어가 관측될 수 있게 되나, 72시간 안의 발생은 보장하지 않는다. 없으면 실측으로 적지 않는다.

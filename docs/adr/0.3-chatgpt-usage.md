# ADR 0.3 — zzik: ChatGPT(Codex 구독) 사용량 표시 (수집기 다중 제공자화)

- 상태: Proposed (설계 전용, 미구현. 설계: fable, 총괄: opus. 이슈 #14)
- 날짜: 2026-11-11
- 범위: Codex 사용량 수집 방식, 자격 증명, 수집기의 다중 제공자 구조, 봉투·KV, 실응답 미확인 구조 대응, Worker API, 프론트 다중 제공자 화면, 레이어·테스트, 검증, 수동 단계
- 선행: ADR 0.2(`docs/adr/0.2-claude-usage.md`)와 부록(`0.2-claude-usage.stack.md`, 특히 부록 B의 운영 제약), 조사 `docs/research/chatgpt-usage.md`
- 위치: `docs/adr/0.3-chatgpt-usage.md`

## Context

- 목표: 대시보드에 Claude와 나란히 ChatGPT(Codex 구독) 사용량을 표시한다. 응답에 있는 항목을 빠짐없이 보여 주고 raw JSON을 그대로 볼 수 있게 한다.
- 운영 제약(0.2 부록 B, 그대로 적용): 원격 SSH 전용, 무인 실행, PM2 상주 프로세스, KV 쓰기는 로그인된 wrangler 실행, 자격 증명은 파일만.
- dev의 현재 구현(`645bc10`):
  - 수집기: `collector/main.mjs`가 300초마다 `runOnce`를 돈다. 제공자가 하나로 고정되어 있다(봉투의 `provider: 'claude'`, KV 키 env `ZZIK_KV_KEY`, 상태 파일 `usage-state.json`, 로그 파일 하나).
  - Worker: Hono 라우터, `GET /api/usage`, `KvSnapshotStore`가 `usage:claude`를 고정으로 읽는다.
  - 계약: `shared/usage-contract.ts`의 `UsageEnvelope.provider`가 `'claude'` 리터럴이고 프론트 디코더(`src/domain/usage/snapshot.ts`)도 `provider === 'claude'`를 검사한다.
  - 프론트: 화면은 fixture 게이트웨이에 연결된 상태이고, 실제 API 연결과 TanStack Query 전환은 `0.2/query` 브랜치에서 진행 중이다(0.2 부록 A).
  - 의존성 버전은 공급망 정책에 따라 고정한다(`hono` 고정 커밋 참고). 0.3은 새 패키지를 추가하지 않는다.
- 조사 결과(`docs/research/chatgpt-usage.md`):
  - biseo는 `GET https://chatgpt.com/backend-api/wham/usage`에 `Authorization: Bearer <~/.codex/auth.json의 tokens.access_token>`만 붙여 이 Mac, 이 계정에서 사용량을 받아 왔다. 다른 헤더는 보내지 않았다.
  - 알려진 응답 형태는 biseo 테스트의 합성 데이터뿐이다: `rate_limit.primary_window`/`secondary_window` 각각 `used_percent`, `reset_at`(Unix 초) 또는 `reset_after_seconds`, `limit_window_seconds`, 그리고 `rate_limit.limit_reached`. 실제 응답 전체 구조(plan, credits, 추가 버킷, 식별자 포함 여부)는 확인되지 않았다.
  - `~/.codex/auth.json`의 키는 `auth_mode`, `OPENAI_API_KEY`, `tokens.{id_token, access_token, refresh_token, account_id, …}`, `last_refresh`다. 만료 시각 필드는 없다.
  - Codex는 사용 중에 토큰을 스스로 갱신한다. 공식 app-server에 `account/rateLimits/read`가 있으나 이 Mac의 설치 버전에서 검증되지 않았다.
  - biseo의 Codex 조회에는 429 처리, 백오프, 게이트가 없었다.
- 이 엔드포인트는 문서화된 공개 API가 아니다.

미확인 전제 (구현 중 해당 단계에서 확인한다. 토큰, JWT payload, 계정 식별자는 어떤 출력에도 내지 않는다):

1. 이 Mac에서 `Authorization` 헤더만으로 WHAM이 200과 JSON을 준다(biseo의 과거 동작이 지금도 유효한지). 403이 오면 `ChatGPT-Account-Id` 헤더가 필요한지 본다(D4).
2. 실제 응답의 키 구조. dry-run의 키 경로 출력으로 확인한다(D6). 이메일, 사용자 ID, 계정 ID 같은 식별자 키가 있는지도 이때 본다.
3. `tokens.access_token`이 `exp` 클레임을 가진 JWT다. 아니면 만료 미상으로 처리된다(D2).
4. Codex access token의 수명 T. `exp`와 `last_refresh`의 차이로 잰다. 유휴 공백 추정(D2)에 넣는다.
5. Codex의 인증 저장 방식이 파일이다. `~/.codex/config.toml`의 `cli_auth_credentials_store` 값을 본다. keyring이나 auto로 동작 중이면 `auth.json`이 갱신되지 않는 낡은 사본일 수 있다(U1).
6. Codex가 `auth.json`을 원자적으로 교체하는지. 아닐 경우에 대비해 읽기를 한 번 재시도한다(D2).
7. SSH 세션에서 추론 없이 Codex의 토큰 갱신을 일으키는 가장 가벼운 실행 방법(U4).
8. 0.2 프론트 통합(`0.2/query`)이 부록 A의 형태로 dev에 들어온다. 이 문서의 프론트 변경은 그 위에 얹는 것으로 적었다.

## Decision

전체 구조(굵은 부분이 0.3 추가):

```
[Mac] PM2 → collector 한 프로세스, 300초 주기
        ├─ claude: ~/.claude/.credentials.json → api.anthropic.com/api/oauth/usage → KV usage:claude
        └─ codex : ~/.codex/auth.json → chatgpt.com/backend-api/wham/usage → KV usage:codex
              (제공자마다 상태 파일, 게이트, 봉투가 따로다. 로그는 한 파일에 provider 필드로 구분)

[브라우저] ─Access→ Worker GET /api/usage/:provider (JWT 검증 후 해당 KV 키 읽기)
            화면: 제공자별 섹션(Claude, ChatGPT), 섹션마다 독립 조회
```

### D1. 수집 방식: WHAM HTTP 직접 호출. app-server는 채택하지 않는다

- 수집기가 `GET https://chatgpt.com/backend-api/wham/usage`를 직접 호출한다.
- 이유:
  - 0.2 수집기와 같은 모양이다(파일에서 토큰 읽기 → HTTP GET 한 번 → 봉투). 포트 구현 두 개만 더하면 되고 새 프로세스 종류가 생기지 않는다.
  - biseo가 이 Mac, 이 계정에서 같은 호출로 운영된 실적이 있다.
  - app-server 방식은 수집기가 `codex` 바이너리를 띄워 JSON-RPC 초기화와 조회를 해야 한다. 설치 버전의 메서드 지원, 조회 시 자동 갱신 여부가 검증되지 않았고, `~/.codex`의 상태 DB와 기존 `app-server-daemon`에 미치는 영향도 모른다. 무인 운영에 검증되지 않은 프로세스를 넣지 않는다.
- app-server의 장점은 갱신을 Codex에 맡길 수 있다는 것 하나다. 그 필요성은 전제 4의 실측에 달려 있다.
- 전환 조건: V12의 관측에서 Codex 쪽 `token_expired` 시간이 불편한 수준이면 app-server를 후속 ADR로 검토한다. 수집기에서는 `usage` 포트 구현 하나를 바꾸는 일이고, 응답 구조가 달라지므로 프론트 정규화기도 하나 더 필요하다.

### D2. 자격 증명: `auth.json` 읽기 전용, 만료는 JWT `exp`로 판정

- 경로: env `ZZIK_CODEX_AUTH_PATH`, 없으면 `${CODEX_HOME:-~/.codex}/auth.json`. ecosystem 파일에 경로를 명시한다.
- 매 실행마다 파일을 다시 읽는다. 수집기는 `tokens.access_token` 하나만 꺼낸다.
  - `refresh_token`, `id_token`, `OPENAI_API_KEY`, `account_id`는 쓰지 않고 어디에도 넘기지 않는다.
  - 수집기는 토큰을 갱신하지 않고 `auth.json`을 쓰지 않는다. 갱신 소유자는 Codex CLI 하나다. refresh token은 회전하므로 수집기가 갱신하면 Codex의 로그인이 깨질 수 있다(0.2 D3과 같은 이유).
- `auth_mode`가 ChatGPT 로그인 방식이 아니거나 `tokens.access_token`이 없으면 `no_credentials`다. API 키로는 이 엔드포인트를 쓸 수 없다.
- JSON 파싱에 실패하면 200ms 뒤 한 번 다시 읽는다(Codex가 파일을 쓰는 중일 수 있다). 그래도 실패하면 `no_credentials`로 두고 다음 주기에 다시 본다.
- 만료 판정:
  - access token의 가운데 조각을 base64url로 풀어 `exp`(초)만 읽고 ms로 바꾼다. 서명은 검증하지 않는다. 이 값은 "호출해 봐야 소용없는지"를 미리 아는 용도일 뿐이고 인증 판단은 서버가 한다.
  - `exp`가 지났으면 호출하지 않고 `token_expired`.
  - JWT가 아니거나 `exp`가 없으면 만료 미상(`expiresAt: null`)으로 두고 호출해서 401로 판정한다.
  - payload의 다른 클레임(이메일, 계정, 플랜)은 읽지 않고 버린다. 봉투에는 `tokenExpiresAt`만 들어간다.
- 401과 JSON 본문의 403은 `auth_required`. 게이트는 0.2와 같다(1시간, `exp`가 바뀌면 즉시 해제).
- 유휴 공백: Codex를 쓰지 않는 간격이 토큰 수명 T보다 길면 그 초과분만큼 `token_expired`다. T는 전제 4로 잰다. 해소 수단은 이 Mac에서 Codex를 실행하는 것이다(U4).

### D3. 수집기 다중 제공자 구조

원칙: 한 제공자의 실패(자격 증명, 429, 응답 이상, 예외)가 다른 제공자의 수집을 막거나 늦추지 않는다.

- 제공자 목록은 정적이다: `claude`, `codex`. env `ZZIK_PROVIDERS`(기본 `claude,codex`)로 켜고 끈다. 동적 플러그인 구조는 만들지 않는다.
- 제공자 정의(조립 루트가 만든다)는 다음 묶음이다.

| 요소 | claude | codex |
|---|---|---|
| 자격 증명 포트 | `claude-credentials-file.mjs` | `codex-credentials-file.mjs` |
| usage 포트 | `claude-usage-client.mjs` | `codex-usage-client.mjs` |
| KV 키 | `usage:claude` | `usage:codex` |
| 상태 파일 | `usage-state.claude.json` | `usage-state.codex.json` |

- 공유하는 것: 시계, 로거, wrangler KV 어댑터(키만 다르게 생성), 백오프·게이트·봉투 로직(domain).
- 실행 단위:
  - `runOnce(ports, { provider })`는 지금 구조 그대로 한 제공자의 한 실행이다. 봉투에 `provider`를 넣는 것만 바뀐다.
  - 새 `runCycle(providers)`가 제공자를 순서대로(claude → codex) 돌린다. 각 실행을 예외 격리해서 하나가 던져도 다음 제공자를 실행한다.
  - 순차 실행으로 둔다. wrangler 프로세스가 동시에 떠서 OAuth 갱신이 겹치는 일을 피하고, 한 주기가 5분 안에 끝나는 데는 문제가 없다.
- 상태 격리: 게이트(`nextAllowedAt`, `failCount`, `authDeniedExpiresAt`)와 이전 봉투가 제공자별 파일에 있다. Anthropic의 429가 Codex 호출을 막지 않는다.
  - 기존 `usage-state.json`은 claude의 상태다. `usage-state.claude.json`이 없으면 기존 파일을 읽고, 쓰기는 새 이름으로 한다(백오프와 마지막 성공 본문을 잃지 않기 위한 일회성 이행).
- 로그: 파일 하나를 유지하고 줄마다 `provider=<id>`를 넣는다. 한 주기에 제공자 수만큼 줄이 생긴다. 형식은 `<시각> provider=codex status=… called=… httpStatus=… tokenExpiresAt=… kv=…`다.
- CLI: `--provider <id>`를 더한다. `--once`와 `--dry-run`에서 대상을 고른다(생략하면 켜진 제공자 전부). `--credentials-file`은 `--provider`와 `--dry-run`이 함께 있을 때만 받는다. `--once`의 종료 코드는 제공자별 결과 중 가장 큰 값이다.
- KV 쓰기 횟수: 제공자 2개 × 288회 = 576회/일. Free 한도 1,000회 안이다. 제공자가 넷이 되면 넘으므로 그때는 주기를 늘리거나 키를 합친다.
- `ZZIK_KV_KEY` env는 없앤다. 키는 제공자 id에서 정해진다.

### D4. 요청, 응답 분류, 429·5xx 정책

요청:

- 고정 URL(상수, env로 바꿀 수 없다), `GET`, 헤더는 `Authorization: Bearer <token>`과 `Accept: application/json`.
- `redirect: 'error'`. 다른 호스트로 넘어가면 실패시킨다(토큰이 따라가지 않게).
- 타임아웃 10초.
- `ChatGPT-Account-Id`는 기본으로 보내지 않는다. biseo가 이 계정에서 헤더 없이 동작했고, 보내는 식별자를 최소로 한다. 전제 1에서 필요하다고 확인되면 어댑터 옵션으로 켠다. 값은 `auth.json`에서 읽어 헤더로만 흐른다.

응답 분류:

| 응답 | 결과 |
|---|---|
| 200이고 본문이 JSON 객체 | `ok`, 본문 원문을 싣는다 |
| 200이지만 JSON 객체가 아님(HTML 등) | `upstream_error`. 본문은 저장하지 않는다 |
| 401 | `auth_required` |
| 403이고 응답이 JSON | `auth_required` |
| 403이고 응답이 JSON이 아님 | `upstream_error`. `chatgpt.com` 앞단의 차단 페이지일 수 있고 재로그인으로 풀리지 않는다 |
| 429 | `rate_limited`, Retry-After 해석 |
| 그 밖의 4xx, 5xx | `upstream_error` |
| 타임아웃 | `upstream_error` |
| 리다이렉트, 연결 실패 | `network_error` |

정책: 0.2 D5를 그대로 쓴다(`collector/domain/usage/backoff.mjs`, `gate.mjs`, `retry-after.mjs`).

- 429: 대기 = max(Retry-After, min(600 × 2^(n−1), 3600))초. 5xx와 타임아웃: min(600 × 2^(n−1), 900)초. 성공하면 초기화.
- 사용률 100%(구독 한도 도달)와 조회 요청의 HTTP 429는 다른 것이다. 앞의 것은 200 응답 안의 값이고 게이트와 무관하다.
- biseo에는 Codex용 백오프가 없었다. 0.3에서 처음 적용된다.

### D5. 봉투, 계약, KV

- 봉투 형식은 0.2 D4 그대로이고 `schema`는 1을 유지한다. 바뀌는 것은 `provider`의 값 범위뿐이다.
- `shared/usage-contract.ts` 변경:
  - `USAGE_PROVIDERS = ['claude', 'codex'] as const`, `type UsageProvider`
  - `USAGE_KV_KEYS: Record<UsageProvider, string>` (`usage:claude`, `usage:codex`). `USAGE_KEY`는 지운다.
  - `UsageEnvelope.provider: UsageProvider`
  - `USAGE_COLLECTOR_VERSION = '0.3.0'`
- 수집기는 `.mjs`라 shared의 값을 런타임에 가져올 수 없다. `collector/domain/usage/providers.mjs`에 같은 목록과 키를 두고, 두 곳이 일치하는지를 테스트 하나가 확인한다.
- `tokenExpiresAt`은 Codex에서는 JWT `exp`다. `rawText` 64KB 규칙, 실패 시 이전 성공 본문 유지, 하트비트(`runAt`)는 같다.
- KV에는 응답 원문을 그대로 넣는다. 응답에 식별자(이메일, 계정 ID 등)가 들어 있더라도 가공하지 않는다. 근거: namespace는 비공개이고 API는 Access와 JWT 검증 뒤에 있으며 보는 사람이 데이터의 주인 한 명이다. 대신 로그, 상태 파일의 로그 줄, 레포의 fixture에는 실제 값을 남기지 않는다(D6).

### D6. 실응답 미확인 구조 대응

세 단계로 막는다.

1. 원문 보존: 수집기와 Worker는 본문을 해석하지 않는다. 구조가 예상과 달라도 KV와 Raw 보기에는 그대로 있다.
2. 값 없는 구조 확인: `--dry-run`의 출력을 최상위 키 목록에서 키 경로 목록(깊이 4까지, 배열은 `[]`로 표기, 값은 출력하지 않음)으로 넓힌다. 예: `rate_limit.primary_window.used_percent`. 실제 응답 구조를 값 노출 없이 확인하고(전제 2), 그 구조에 합성 값을 채워 fixture를 만든다.
3. 구조에 덜 의존하는 정규화(프론트 domain): 알려진 경로를 하드코딩하지 않고 "창 객체"를 찾아낸다.

정규화 규칙(`src/domain/usage/codex-view.ts`, 순수 함수. 출력은 기존 `UsageReport`라서 화면 컴포넌트를 그대로 쓴다):

- 창 객체: `used_percent`가 0 이상의 유한한 숫자이고 `limit_window_seconds`, `reset_at`, `reset_after_seconds` 중 하나 이상을 가진 객체.
- 탐색: 응답을 깊이 4까지 훑어 창 객체를 전부 찾는다. 배열 안도 본다. 항목 id는 JSON 경로다(`rate_limit.primary_window`).
- 배치:
  - `rate_limit` 아래의 창 → "사용 창" 섹션. `primary`/`secondary`라는 이름이 아니라 `limit_window_seconds`로 분류하고 길이 오름차순으로 놓는다.
  - 그 밖의 위치에서 찾은 창 → "추가 한도" 섹션. 발견 순서대로.
  - 없는 창을 0%로 만들어 내지 않는다.
- 라벨:
  - 18,000초 → `5시간 한도`, 604,800초 → `주간 한도`.
  - 다른 길이 → `N시간 한도` 또는 `N일 한도`로 만들고 "미확인" 배지를 붙인다. 길이를 모르면 경로를 라벨로 쓰고 "미확인".
  - `rate_limit` 밖의 창 → `<상위 키를 읽기 좋게 바꾼 이름> · <창 라벨>` + "미확인". 실측 뒤에 확인된 것만 고정 라벨 표로 올린다.
- 리셋 시각: `reset_at`(Unix 초)이 있으면 그것을 ISO로, 없고 `reset_after_seconds`가 있으면 봉투의 `fetchedAt`에 더한다(화면을 보는 시각이 아니라 수집 시각 기준). 둘 다 없으면 null.
- 단계와 집계: 0.2.1의 규칙을 재사용한다(80% 주의, 100% 한도, 리셋이 지난 항목은 집계에서 제외). 추가로 `rate_limit.limit_reached === true`이면 전체 상태를 `limit`으로 올린다.
- 기타 항목: 창을 하나도 내지 않은 최상위 키는 전부 "기타 항목"에 키-값으로 나온다. 창을 낸 최상위 키에 창이 아닌 필드(`limit_reached` 등)가 남아 있으면 그 필드들도 "기타 항목"에 나온다.
- 완전성 불변식: 응답의 모든 최상위 키가 카드의 출처이거나 "기타 항목"에 있다. 테스트로 고정한다.
- 값이 이상하면(`used_percent`가 문자열, 음수 등) 던지지 않고 `issues`에 넣는다. 최상위가 객체가 아니면 Raw만 보여 준다.

### D7. Worker API: `GET /api/usage/:provider`

| 경로 | 동작 |
|---|---|
| `GET /api/usage/claude` | `usage:claude`를 읽어 `{ "snapshot": … }` |
| `GET /api/usage/codex` | `usage:codex`를 읽어 `{ "snapshot": … }` |
| `GET /api/usage` | `claude`의 별칭. 이미 배포된 프론트가 쓰는 경로라 0.3 동안 유지하고 다음 버전에서 지운다 |
| `/api/usage/<목록에 없는 값>` | 404 `not_found` |

- 응답 본문 형태, 오류 코드, 공통 헤더는 0.2 D8 그대로다. 판정 순서도 같다: 설정 → 인증 → 경로(제공자 확인 포함) → 메서드 → 저장소.
- 제공자 값은 `USAGE_PROVIDERS`에 있는 것만 받는다. KV 키는 `USAGE_KV_KEYS`에서 고른다. 요청 문자열로 키를 조립하지 않는다.
- 읽은 봉투의 `provider`가 요청한 제공자와 다르면 502 `snapshot_corrupt`다(키가 섞였을 때 다른 제공자의 값이 나가지 않게).
- 코드 변경: `SnapshotStore.read(provider)`, `KvSnapshotStore`의 키 고정 제거, `getUsage(store, provider)`, `usage-route.ts`에 `/:provider`.
- 제공자별 경로로 정한 이유:
  - 한 제공자의 저장값이 깨져도(502) 다른 제공자의 조회는 200이다. 통합 응답이면 부분 실패를 본문 안에 따로 표현해야 한다.
  - 프론트의 Query 키와 1:1로 맞는다(D8).
  - Worker가 통과형으로 남는다.

### D8. 프론트: 제공자별 조회와 섹션 화면

전제 8의 상태(게이트웨이가 봉투 결과를 돌려주고, `useUsage`가 `useQuery` 기반)에 더하는 변경이다.

계약:

- `UsageGateway.fetchUsage(provider: UsageProvider)`. `HttpUsageGateway`는 `/api/usage/${provider}`를 호출한다.
- `decodeUsageSnapshot(body, provider)`: `provider === 'claude'` 고정 검사를 "요청한 제공자와 같은가"로 바꾼다. `usage`의 타입은 Claude 전용 `RawUsage`가 아니라 `Record<string, unknown> | null`로 넓힌다.
- 제공자 등록부 `src/domain/usage/providers.ts`(순수 데이터와 함수 참조):

| id | 제목 | 추가 섹션 제목 | 갱신 안내 | 뷰 생성 |
|---|---|---|---|---|
| `claude` | Claude | 모델·기능별 한도 | 이 Mac에서 Claude Code를 실행하면 갱신된다 | 기존 `buildUsageView` |
| `codex` | ChatGPT (Codex) | 추가 한도 | 이 Mac에서 Codex를 실행하면 갱신된다 | `buildCodexUsageView` |

- 수집 상태 판정(0.2 D4의 표)은 제공자와 무관하게 같은 함수를 쓴다.

TanStack Query:

- 키: `usageQueryKey(provider) = ['usage', provider] as const`. 전체 무효화는 접두 `['usage']`로 한다.
- `usageQueryOptions(gateway, provider)`: queryFn은 `gateway.fetchUsage(provider)`. 주기(60초), 가시성 정지, `staleTime`, 재시도 정책은 부록 A 그대로이고 제공자마다 독립으로 돈다.
- `useUsage(provider)`: 반환 형태는 그대로(`{ state, refresh }`). 뷰는 등록부의 생성 함수로 만든다. Codex 뷰에는 `fetchedAt`을 함께 넘긴다.
- 한 제공자의 조회 실패나 로딩이 다른 제공자의 섹션에 영향을 주지 않는다. 새로고침 버튼은 섹션마다 있고 그 섹션의 쿼리만 다시 읽는다.
- Zustand: `rawJsonOpen`을 제공자별 값으로 바꾼다(`Record<UsageProvider, boolean>`). 서버 상태는 넣지 않는다는 규칙은 그대로다.

화면: 탭이 아니라 섹션으로 쌓는다.

- 이유: 이 화면의 목적이 여러 구독의 사용량을 한 번에 보는 것이다. 탭은 한쪽을 가리고, 가려진 쪽의 경고를 놓치게 한다. 제공자가 둘이라 길이도 감당할 만하다.
- 구성(위에서 아래로):
  1. 제목(`Hello Young-In` 유지). 소개 문구는 "구독 사용량을 한눈에 확인하는 공간입니다."로 바꾼다.
  2. 요약 줄: 제공자마다 칩 하나(`Claude · 정상`, `ChatGPT · 주의`). 칩은 해당 섹션으로 가는 앵커 링크다. 섹션과 같은 쿼리 키를 구독하므로 요청이 늘지 않는다.
  3. 제공자 섹션 × 2(Claude, ChatGPT 고정 순서). 각 섹션은 기존 `UsageDashboard` 하나다: 상태 줄, 사용 창, 추가 섹션, 기타 항목, Raw JSON.
- 제목 단계: 페이지 `h1`, 제공자 섹션 `h2`, 섹션 안의 "사용 창" 등은 `h3`로 내린다. 카드 제목은 그 아래 단계로 일관되게 둔다.
- 식별: 섹션에 `id="usage-claude"`/`id="usage-codex"`, `aria-label="Claude 사용량"`/`"ChatGPT 사용량"`. 기존 `aria-label="사용량"`과 `data-testid="usage-section"`은 제공자별 값으로 바뀐다(해당 ui 테스트 수정).
- 320px:
  - 요약 줄은 `flex-wrap`으로 줄바꿈한다. 칩 두 개는 한 줄에 들어간다.
  - 섹션 안의 격자는 지금처럼 기본 1열이다.
  - Codex 항목의 id는 JSON 경로라 길다. `break-all`로 접는다.
  - 페이지 가로 스크롤이 없어야 한다(V10).
- 개발용 fixture: fixture 게이트웨이가 제공자를 받아 `tests/fixtures/codex-usage.{normal,warn,limited,unknown-keys}.json`을 돌려준다. `?fixture=` 시나리오 이름은 두 제공자에 같이 적용한다.

| U1 | 구현 전 | `~/.codex/auth.json`의 존재와 권한(0600), `auth_mode` 값, `~/.codex/config.toml`의 `cli_auth_credentials_store` 값을 확인한다(토큰 값은 출력하지 않는다). 저장 방식이 파일이 아니면 `"file"`로 바꾸고 Codex를 한 번 실행해 `auth.json`이 갱신되는지 본다 |
| U2 | 수집기 코드가 반영된 뒤 | `node collector/main.mjs --dry-run --provider codex`를 한 번 실행해 status와 키 경로를 확인한다(V5). 반복하지 않는다 |
| U3 | 배포 | Worker 배포(`pnpm run deploy`) → `git pull` → `pm2 restart zzik-usage-collector --update-env` → `pm2 logs`에서 `provider=codex` 줄 확인 |
| U4 | 화면의 ChatGPT 섹션에 "인증 필요"가 뜰 때 | 이 Mac에서 Codex CLI를 한 번 실행한다. 다음 주기에 풀린다 |
| U5 | U4로 풀리지 않을 때(로그아웃, 갱신 취소) | SSH에서 Codex의 device code 로그인을 실행하고, 출력된 코드를 다른 기기의 브라우저에서 승인한다. PM2 재시작으로는 해결되지 않는다 |
| U6 | Codex 수집을 끄고 싶을 때 | ecosystem의 `ZZIK_PROVIDERS`를 `claude`로 바꾸고 `pm2 restart zzik-usage-collector --update-env`. 화면의 ChatGPT 섹션은 "수집 중단"으로 바뀐다 |

Access와 Cloudflare 대시보드 작업은 없다. KV namespace는 0.2의 것을 그대로 쓴다.

### 구현 순서 (참고)

구간 A (`0.2/query`와 겹치지 않는다. 지금 시작 가능):

1. U1. `shared/usage-contract.ts` 변경과 계약 일치 테스트.
2. 수집기: domain(`jwt-exp`, `key-paths`, `providers`, `envelope`) → app(`run-once`, `run-cycle`) → infra(Codex 어댑터 둘, 상태 파일 폴백, 로그) → `main.mjs`, ecosystem.
3. U2(실측 dry-run). 관측한 키 구조를 ADR에 적고 합성 값으로 fixture를 만든다. D6의 규칙이 실제 구조에 맞는지 확인하고 필요하면 고친다.
4. Worker: domain → app → ui → infra.
5. 프론트 domain의 Codex 정규화기(`codex-windows`, `codex-labels`, `codex-view`, `providers`). 다른 프론트 파일을 건드리지 않는다.

구간 B (`0.2/query`가 dev에 병합된 뒤):

6. 프론트 계약(`gateway`, `snapshot`) → app(`usage-query`, `useUsage`, 스토어) → infra → ui.

배포:

7. U3. Worker가 먼저 나가도 기존 프론트는 `/api/usage` 별칭으로 동작한다. 프론트가 먼저 보여도 Codex 섹션은 "데이터 없음"일 뿐이다.
8. V6~V12. 운영 스킬 갱신.

## Alternatives

| 결정 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 수집 방식 | Codex app-server의 `account/rateLimits/read` | D1. 공식 인터페이스이고 갱신을 Codex에 맡길 수 있지만, 설치 버전에서 검증되지 않았고 바이너리 실행과 JSON-RPC 연결이 무인 운영에 새 실패 지점을 만든다. 전환 조건을 정해 둔다 |
| 수집 방식 | Codex CLI의 상태 출력 파싱 | 사람용 출력이라 형식이 바뀌고 raw가 없다 |
| 토큰 | 수집기가 refresh token으로 직접 갱신 | 회전 충돌로 Codex 로그인이 깨질 수 있다. 갱신 소유자는 하나여야 한다 |
| 만료 판정 | `last_refresh` + 추정 수명 | 수명을 가정해야 한다. JWT `exp`가 토큰 자신이 말하는 값이다 |
| 만료 판정 | JWT 서명까지 검증 | 수집기는 토큰의 사용자이지 검증자가 아니다. 키 조회라는 네트워크 의존만 늘어난다 |
| 헤더 | `ChatGPT-Account-Id`를 항상 전송 | biseo가 없이 동작했다. 필요가 확인되면 켠다 |
| 수집기 구조 | 제공자별 PM2 프로세스 | 프로세스 수준 격리는 얻지만 상주 프로세스와 wrangler 동시 실행이 늘어난다. 프로세스 안의 예외 격리와 상태 분리로 충분하다 |
| 수집기 구조 | 제공자 병렬 실행 | wrangler의 OAuth 갱신이 겹칠 수 있다. 순차로도 한 주기가 몇 초다 |
| 수집기 구조 | 동적 제공자 플러그인 | 제공자가 둘이다. 정적 목록이 읽기 쉽고 테스트하기 쉽다 |
| 상태 | 한 상태 파일에 제공자별 구획 | 한쪽 쓰기가 다른 쪽 상태를 덮을 여지가 생긴다. 파일을 나누면 격리가 구조로 보장된다 |
| KV | 한 키에 두 제공자의 봉투를 합침 | 쓰기는 절반이 되지만 한 제공자의 실행이 다른 제공자의 값을 다시 써야 하고 Worker가 값을 쪼개야 한다. 576회/일은 한도 안이다 |
| 원문 | 식별자 키를 지우고 KV에 저장 | "raw 그대로"가 깨지고, 지울 키 목록이 미확인 구조에 의존한다. 보호는 Access와 JWT 검증에 맡긴다 |
| API | `/api/usage?provider=` | 동작은 같지만 경로 방식이 Hono 라우팅과 404 처리에 더 자연스럽다 |
| API | `/api/usage` 하나가 모든 제공자를 반환 | 부분 실패(한쪽 corrupt)를 본문 안에 표현해야 하고, 프론트의 조회·캐시·오류가 제공자 단위로 나뉘지 않는다 |
| API | 기존 `/api/usage`를 즉시 제거 | 배포 순서에 따라 이미 열려 있는 화면이 깨진다. 한 버전 동안 별칭으로 둔다 |
| 계약 | `schema`를 2로 올림 | 필드가 바뀌지 않았고 `provider` 값이 늘었을 뿐이다. 기존 봉투가 그대로 유효하다 |
| 정규화 | Worker나 수집기에서 Codex 응답을 공통 형태로 변환 | 구조가 미확인이라 변환 규칙을 고칠 일이 생기는데, 그때 수집기 재시작과 Worker 배포가 필요해진다. 프론트 domain 한 곳만 고치게 한다 |
| 정규화 | `rate_limit.primary_window` 등 알려진 경로만 처리 | 합성 데이터에서 본 경로일 뿐이다. 추가 버킷이 있으면 화면에서 사라진다 |
| 정규화 | Codex 응답을 Claude 형태로 바꿔 기존 `buildUsageView`에 넣음 | 중첩 구조와 리셋 표현(Unix 초, 상대 초)이 달라 억지 변환이 되고 raw와 화면의 대응이 흐려진다 |
| 화면 | 제공자 탭 | D8. 한쪽이 가려진다. 제공자가 더 늘어 화면이 길어지면 다시 검토한다 |
| 화면 | 두 제공자를 한 격자에 섞어 표시 | 수집 상태(정상, 인증 필요)가 제공자 단위라 상태 줄을 붙일 자리가 없어진다 |
| 화면 | Claude 전용 프론트 파일 이름 정리 | 진행 중인 `0.2/query`와 충돌한다. 별도 정리 작업으로 미룬다 |

## Consequences

긍정적:
- Codex 사용량이 0.2와 같은 경로(로컬 수집 → KV → 인증된 API → 화면)로 들어온다. 새 인프라, 새 비밀, 새 패키지, Access 변경이 없다.
- 제공자별로 상태, 게이트, KV 키, 조회, 화면 섹션이 분리된다. 한쪽 장애가 다른 쪽에 번지지 않는다.
- 응답 구조를 몰라도 잃는 것이 없다. 원문은 KV와 Raw 보기에 남고, 정규화기는 창 객체를 찾아서 보여 주며, 나머지는 기타 항목에 나온다.
- Codex 조회에 처음으로 429·5xx 백오프가 붙는다.
- 구조가 예상과 다를 때 고칠 곳이 프론트 domain 파일 몇 개로 한정된다.
- 제공자를 env 하나로 끌 수 있다.

부정적 / 리스크:
- 문서화되지 않은 엔드포인트에 하나 더 의존한다. 구조나 인증 요구가 바뀌면 수집이 멈춘다. `chatgpt.com` 앞단의 차단이 Node의 요청을 막을 가능성도 있다(D4에서 `upstream_error`로 분류).
- 실제 응답을 보지 않고 정한 규칙이 있다(D6). 첫 실측 뒤에 라벨 표와 탐색 규칙을 고쳐야 할 수 있다.
- Codex를 오래 쓰지 않으면 토큰이 만료되어 `token_expired`로 멈춘다. 수명이 측정되기 전이라 공백의 크기를 모른다.
- Codex의 인증 저장이 파일이 아니면 `auth.json`이 낡아 수집이 안 된다(전제 5). 설정을 바꾸면 재로그인이 필요할 수 있고, 그것은 다른 기기의 브라우저 승인이 필요한 일이다.
- KV에 응답 원문이 그대로 들어간다. 식별자가 포함되어 있으면 그것도 저장된다.
- KV 쓰기와 wrangler 실행이 두 배가 된다(576회/일, 주기마다 프로세스 2개).
- 화면이 길어진다. 모바일에서는 ChatGPT 섹션이 스크롤 아래에 있고 요약 칩으로 보완한다.
- 프론트 변경(구간 B)은 `0.2/query` 병합을 기다린다. 섹션 식별자와 제목 단계가 바뀌어 기존 ui 테스트 일부를 고쳐야 한다.
- 프론트에 Claude 전용 이름의 파일(`view.ts` 등)과 `codex-` 접두 파일이 섞인다.
- `/api/usage` 별칭이 한 버전 동안 남는다.

후속 과제:
- app-server 방식 검증과 전환 검토(전환 조건: V12)
- `/api/usage` 별칭 제거
- 실측으로 확인된 Codex 버킷의 고정 라벨 등록
- 프론트 Claude 전용 파일의 이름 정리
- 제공자가 더 늘 때 KV 쓰기 한도와 화면 구성 재검토

## Verification

판정 원칙은 0.1, 0.2와 같다. 미인증 응답에 사용량 데이터가 나오면 전체 실패다. 어떤 출력에도 토큰, JWT payload, 계정 식별자 값이 나오면 실패다.

### 단위 테스트와 타입 검사

- V1. `pnpm test`가 D10 표의 항목을 포함해 통과한다. 기존 Claude 테스트가 이름 변경과 `provider` 인자 추가 뒤에도 통과한다.
- V2. `pnpm typecheck`, `pnpm typecheck:collector`, `pnpm build`가 통과한다. arch 테스트가 통과하고 수집기에 외부 패키지 import가 없다.

### 로컬

- V3. 가짜 자격 증명 dry-run(네트워크 호출 없음):
  - `--dry-run --provider codex --credentials-file tests/fixtures/codex-auth.expired.json` → `status=token_expired`, `called=0`.
  - `--credentials-file /nonexistent` → `status=no_credentials`, 종료 코드 0.
  - `--provider claude`의 기존 dry-run 결과가 0.2와 같다.
- V4. `wrangler dev`: 헤더 없는 `/api/usage/codex`, `/api/usage/claude`, `/api/usage`, `/api/usage/nope`가 모두 401이다.
- V5. 실측 dry-run 1회(U2): `--dry-run --provider codex`.
  - status가 `ok`이고 키 경로 목록과 sha256이 나온다. 값, 토큰, 식별자가 출력에 없다.
  - 키 경로를 ADR에 기록한다. `rate_limit` 아래의 창 구조가 D6의 "창 객체" 조건에 맞는지, 식별자로 보이는 키가 있는지 적는다.
  - status가 `auth_required`나 `upstream_error`면 전제 1의 헤더 필요 여부를 판단하고 D4를 고친다.
  - 로그의 `tokenExpiresAt`과 `auth.json`의 `last_refresh`로 토큰 수명(전제 4)을 계산해 적는다.

### 수집기 반영 후

- V6. `pm2 logs zzik-usage-collector`에 주기마다 `provider=claude`와 `provider=codex` 줄이 하나씩 생긴다. `usage-state.claude.json`과 `usage-state.codex.json`이 0600으로 있다. 로그와 상태 파일에 토큰 문자열이 없다. 재시작 직후 claude의 이전 게이트와 마지막 성공 본문이 유지되어 있다(이전 상태 파일에서 넘어왔는지).
- V7. `pnpm exec wrangler kv key get usage:codex --namespace-id 5fe6ac40c73c4d05ac2fab052c2100e6 --remote`: 봉투의 `provider`가 `codex`, `status`가 `ok`, `runAt`이 5분 안쪽이다. `usage:claude`도 계속 갱신된다.
- V8. 격리: ecosystem에서 `ZZIK_CODEX_AUTH_PATH`를 없는 경로로 바꿔 재시작하면 codex는 `no_credentials`, claude는 `ok`로 계속 돈다. 원래 값으로 되돌린다.

### 배포 후

- V9. 미인증 차단(쿠키 없는 curl): `/api/usage/codex`가 Access 로그인으로 가는 302이고 본문에 `rawText`나 `used_percent`가 없다. 0.1의 V3~V6과 0.2의 V10을 다시 수행해 통과한다.
- V10. 화면(원격 기기의 브라우저):
  - 요약 칩 두 개와 섹션 두 개가 보인다. `Hello Young-In`이 그대로다.
  - ChatGPT 섹션의 창 카드가 Raw의 `rate_limit` 값과 맞는다. Raw의 최상위 키가 모두 카드의 출처이거나 기타 항목에 있다.
  - DevTools에서 `/api/usage/claude`와 `/api/usage/codex`가 각각 200, `no-store`다.
  - 너비 320px(실제 브라우저의 기기 모드)에서 페이지 가로 스크롤이 없다.
- V11. 대조: ChatGPT 섹션의 5시간, 주간 사용률이 같은 시각 Codex CLI의 상태 표시와 수집 주기 오차 안에서 맞는다.
- V12. 며칠 관측: 로그에서 제공자별 `status` 분포를 센다. Codex의 `token_expired` 비율과 `token_refreshed` 간격으로 유휴 공백을 계산해 ADR에 기록하고 D1의 전환 조건에 해당하는지 판정한다. `rate_limited`가 잦으면 주기를 늘린다. KV 쓰기 실패가 0.2 때보다 늘었는지도 본다.

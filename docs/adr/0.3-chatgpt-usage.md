## Context

- 목표: 대시보드에 Claude와 나란히 ChatGPT(Codex 구독) 사용량을 표시한다. 응답에 있는 항목을 빠짐없이 보여 주고 raw JSON을 볼 수 있게 한다.
- 운영 제약(0.2 부록 B, 그대로 적용): 원격 SSH 전용, 무인 실행, PM2 상주 프로세스, KV 쓰기는 로그인된 wrangler 실행, 자격 증명은 파일만. 사용자에게 Codex 재로그인을 요구하는 일은 부담이 크므로 피한다.
- dev의 현재 구현(`1a1c72c`):
  - 수집기: 제공자 하나로 고정(봉투의 `provider: 'claude'`, 상태 파일 `usage-state.json`, 로그 파일 하나).
  - Worker: Hono, `GET /api/usage`, `KvSnapshotStore`가 `usage:claude` 고정.
  - 프론트: `0.2/query`가 병합되어 실제 API에 연결되어 있다. `useUsage()`는 `useQuery` 기반이고 `usageQueryKey = ['usage', 'claude']`, 게이트웨이 포트는 `fetchUsage()`(인자 없음), 디코더는 `provider === 'claude'`를 검사한다. Zustand 스토어에 `rawJsonOpen`(불리언 하나)과 `fixtureName`이 있다.
  - `shared/usage-contract.ts`의 `USAGE_KEY`는 정의만 있고 import하는 곳이 없다.
- 조사(`docs/research/chatgpt-usage.md`):
  - biseo의 코드는 `GET https://chatgpt.com/backend-api/wham/usage`에 `Authorization: Bearer <~/.codex/auth.json의 tokens.access_token>`만 붙여 호출한다. 사용자는 이 Mac에서 biseo를 운영했지만, 이 계정에서 이 호출이 200을 받았다는 관측 기록은 문서에 없다.
  - 알려진 응답 형태는 biseo 테스트의 합성 데이터뿐이다(`rate_limit.primary_window`/`secondary_window`의 `used_percent`, `reset_at` 또는 `reset_after_seconds`, `limit_window_seconds`, 그리고 `rate_limit.limit_reached`).
  - biseo의 Codex 조회에는 429 처리와 백오프가 없었다.
- 리뷰의 실측(이 Mac, 값은 기록하지 않음):
  - `~/.codex/auth.json`: 0600, `auth_mode`는 `chatgpt`, `tokens.access_token`은 `exp`가 있는 JWT.
  - 토큰 수명 `exp − iat`는 240시간(10일)이다. 리뷰 시점에 만료까지 약 62시간이 남아 있었다(만료는 11-14 14시경).
  - `auth.json`의 mtime이 토큰의 `iat`와 같다(11-04 14:18). 발급 뒤 파일이 다시 쓰인 적이 없다.
  - `~/.codex/config.toml`에 `cli_auth_credentials_store` 키가 없다.
  - `~/.codex/auth.lock`이 있다.
- 이 엔드포인트는 문서화된 공개 API가 아니다.

mtime과 `iat`가 같다는 관측의 해석: 이것만으로는 어느 쪽도 판정되지 않는다. 수명이 10일인 토큰이 발급 7.4일째에 아직 갱신되지 않았다면 파일이 다시 쓰이지 않은 것이 정상이다. 한편 Codex가 다른 저장소(keyring)를 쓰고 있고 파일은 예전 로그인의 흔적일 가능성도 배제되지 않는다. 판정은 첫 갱신이 일어난 뒤에만 가능하고, 그 시점이 현재 토큰의 만료(11-14) 전후로 다가와 있다. 이것이 게이트 G1이다.

미확인 전제:

1. 이 계정에서 `Authorization` 헤더만으로 WHAM이 200과 JSON을 준다(G2).
2. 실제 응답의 키 구조와 식별자 키의 유무(G2).
3. Codex가 토큰을 갱신할 때 `auth.json`을 다시 쓴다(G1).
4. Codex의 갱신 시점(만료 직전인지, 발급 후 며칠인지). G1 관측에서 함께 기록한다.
5. Codex가 `auth.json`을 원자적으로 교체하는지. `auth.lock`이 있으므로 쓰는 중에 읽힐 수 있다고 보고 한 번 재시도한다(D2).

## 게이트: 진행을 막는 두 가지 확인

둘 다 사용자의 Codex 설정을 바꾸지 않는다.

### G2. 첫 실측 (수집기의 Codex KV 쓰기를 켜기 전)

- 시점: 현재 토큰이 만료되기 전(11-14 14시경 이전)에 한다. 만료 뒤에는 G1이 통과해야만 할 수 있다.
- 방법: `node collector/main.mjs --dry-run --provider codex` 한 번. KV, 상태, 로그에 쓰지 않는다. 출력은 status, 키 경로(값 없음), 본문 sha256이다.
- 판정과 다음 행동:

| 결과 | 행동 |
|---|---|
| `ok` | 키 경로를 ADR에 기록한다. 식별자로 보이는 키(이름이 `email`, `user`, `account`, `org`, `workspace`, `name`, `id`로 끝나거나 그것을 포함)를 골라 D5의 가림 목록을 정한다. 그 뒤에 KV 쓰기를 켠다 |
| `auth_rejected`(401 또는 JSON 403) | `--codex-account-header`를 붙여 dry-run을 한 번 더 한다. `ok`면 `ZZIK_CODEX_SEND_ACCOUNT_ID=1`로 운영한다(D4). 그래도 거부되면 WHAM 직접 호출은 이 계정에서 불가로 보고 F2로 간다 |
| `upstream_error`이고 차단 응답(D4의 진단에 `cf-mitigated` 또는 HTML) | 하루 뒤 한 번 더 한다. 같으면 WHAM 직접 호출은 불가로 보고 F2로 간다. 헤더를 꾸며 차단을 넘으려 하지 않는다 |

### G1. 갱신 관측 (프론트의 ChatGPT 섹션을 main에 내보내기 전)

- 확인하려는 것: Codex가 토큰을 갱신하면 `auth.json`의 access token이 새것으로 바뀐다.
- 관측 방법: G2를 통과해 수집기가 codex를 돌리기 시작하면 수집기 자체가 관측 장치다. 로그의 `provider=codex` 줄에서 `tokenExpiresAt`이 뒤로 이동하고 `token_refreshed`가 찍히면 통과다. 수동으로는 `auth.json`의 mtime과 JWT의 `exp`(시각만)가 함께 전진했는지 본다.
- 사용자 행동: 없다. 평소처럼 Codex를 쓰면 된다. 현재 토큰의 만료가 11-14라서 그 전후로 첫 갱신이 일어난다.
- 판정:

| 관측 | 판정 |
|---|---|
| `token_refreshed`가 찍힘 | 통과. 갱신 시점(만료 얼마 전인지)을 ADR에 기록한다 |
| codex가 `token_expired`인 채로 있고, 그동안 사용자가 Codex를 쓰지 않았음 | 미정. SSH에서 Codex를 한 번 실행한 뒤(U4) 다음 주기를 본다 |
| codex가 `token_expired`인데 같은 기간에 Codex CLI는 정상 동작함 | 실패. Codex가 파일이 아닌 저장소를 쓰고 있다 |

- 실패 시의 결정(위에서부터 차례로, 사용자 부담이 적은 순서):
  - F1. `ZZIK_PROVIDERS=claude`로 codex 수집을 끈다. 프론트의 ChatGPT 섹션은 내보내지 않는다. 다중 제공자 구조와 Worker의 제공자별 경로는 그대로 남긴다(Claude에 영향 없음).
  - F2. app-server 경로를 검증한다. Codex가 자기 저장소에서 인증을 읽으므로 사용자 설정을 바꾸지 않는다. SSH에서 `codex app-server`에 초기화와 `account/rateLimits/read`를 한 번 보내 응답이 오는지 확인하고, 되면 후속 ADR(0.3.1)로 수집기의 codex 포트 두 개와 프론트 정규화기를 그 형태로 바꾼다.
  - F3. F2도 안 되면 사용자에게 선택을 묻는다: `config.toml`에 `cli_auth_credentials_store = "file"`을 넣고 재로그인(다른 기기 브라우저에서 승인)할지, Codex 표시를 보류할지. 이 설정 변경은 에이전트가 먼저 하지 않는다.
- 구현 진행과의 관계: 구간 A(수집기)와 Worker, 프론트 domain의 정규화기는 G1을 기다리지 않는다. 다중 제공자 구조는 어느 경로에서도 쓰이고, G1의 관측 자체가 codex 수집기가 돌아야 가능하다. G1에 걸리는 것은 프론트 ChatGPT 섹션의 dev→main 반영 하나다.

## Decision

전체 구조:

```
[Mac] PM2 → collector 한 프로세스, 300초 주기
        ├─ claude: ~/.claude/.credentials.json → api.anthropic.com/api/oauth/usage → KV usage:claude
        └─ codex : ~/.codex/auth.json → chatgpt.com/backend-api/wham/usage → KV usage:codex
              (제공자마다 상태 파일, 게이트, 봉투가 따로다. 로그는 한 파일에 provider 필드로 구분)

[브라우저] ─Access→ Worker GET /api/usage/:provider (JWT 검증 후 해당 KV 키 읽기)
            화면: 제공자별 섹션(Claude, ChatGPT), 섹션마다 독립 조회
```

### D1. 수집 방식: WHAM HTTP 직접 호출. app-server는 대기 경로로 둔다

- 수집기가 `GET https://chatgpt.com/backend-api/wham/usage`를 직접 호출한다.
- 이유:
  - 0.2 수집기와 같은 모양이다(파일에서 토큰 읽기 → HTTP GET 한 번 → 봉투). 포트 구현 두 개만 더하면 되고 새 프로세스 종류가 생기지 않는다.
  - biseo의 코드가 같은 호출을 구현했다. 다만 이 계정에서의 동작은 G2로 확인한다.
  - app-server 방식은 수집기가 `codex` 바이너리를 띄워 JSON-RPC를 해야 하고 설치 버전에서 검증되지 않았다.
- app-server로 넘어가는 조건(어느 하나):
  - G2에서 WHAM 직접 호출이 불가로 판정됨.
  - G1 실패.
  - 운영 중 차단 응답(D4)이 24시간 넘게 이어짐.
  - V12에서 codex의 `token_expired` 시간이 관측 기간의 5%를 넘음.
- 넘어갈 때 바뀌는 것은 수집기의 codex 자격 증명 포트와 usage 포트, 프론트의 codex 정규화기다. 나머지(구조, 봉투, KV, Worker, 화면)는 그대로다.

### D2. 자격 증명: `auth.json` 읽기 전용, 만료는 JWT `exp`로 판정

- 경로: env `ZZIK_CODEX_AUTH_PATH`, 없으면 `${CODEX_HOME:-~/.codex}/auth.json`.
- 매 실행마다 파일을 다시 읽는다. 자격 증명 포트가 돌려주는 것은 `{ source, token, expiresAt, accountId }`다.
  - `token`: `tokens.access_token`.
  - `expiresAt`: 아래의 JWT `exp`.
  - `accountId`: `tokens.account_id`. 메모리에서만 흐르고, D4의 헤더 옵션이 켜졌을 때만 usage 포트로 넘어간다. 봉투, 상태 파일, 로그, KV, dry-run 출력 어디에도 넣지 않는다(테스트로 고정).
  - `refresh_token`, `id_token`, `OPENAI_API_KEY`는 꺼내지 않는다.
- 수집기는 토큰을 갱신하지 않고 `auth.json`을 쓰지 않는다. 갱신 소유자는 Codex CLI 하나다(0.2 D3과 같은 이유).
- `auth_mode`가 API 키 방식이거나 `tokens.access_token`이 없으면 `no_credentials`.
- JSON 파싱에 실패하면 200ms 뒤 한 번 다시 읽는다(`auth.lock`이 있으므로 Codex가 쓰는 중일 수 있다). 그래도 실패하면 `no_credentials`.
- 파일 권한이 0600보다 넓으면 기동 시 경고를 한 줄 남긴다(값 없이). 읽기는 계속한다.
- 만료 판정:
  - access token의 가운데 조각을 base64url로 풀어 `exp`(초)만 읽고 ms로 바꾼다. 서명은 검증하지 않는다.
  - 만료 마진은 60초다. `exp − now < 60초`면 호출하지 않고 `token_expired`. 곧 만료될 토큰으로 호출해 401을 받고 인증 게이트에 스스로 걸리는 일과, 로컬 시계 오차를 함께 막는다. 이 마진은 Claude에도 같이 적용한다.
  - JWT가 아니거나 `exp`가 없으면 만료 미상(`expiresAt: null`)으로 두고 호출해서 서버 응답으로 판정한다.
  - payload의 다른 클레임은 읽지 않고 버린다.
- 실측 수명 T = 240시간. Codex를 10일 가까이 쓰지 않아야 `token_expired`가 된다(정확한 갱신 시점은 전제 4). Claude(시간 단위)보다 유휴 공백의 위험이 훨씬 작다. 해소 수단은 이 Mac에서 Codex를 실행하는 것이다(U4).

### D3. 수집기 다중 제공자 구조

원칙: 한 제공자의 실패(자격 증명, 429, 응답 이상, 예외)가 다른 제공자의 수집을 막거나 늦추지 않는다.

- 제공자 목록은 정적이다: `claude`, `codex`.
- `ZZIK_PROVIDERS`(기본 `claude,codex`) 해석: 쉼표로 나누고 공백을 떼고 소문자로 바꾸고 중복을 없앤다. 목록에 없는 값은 버리고 기동 시 stderr에 경고를 남긴다. 결과가 비면 설정 오류로 종료한다(코드 78).
- 제공자 정의(조립 루트가 만든다):

| 요소 | claude | codex |
|---|---|---|
| 자격 증명 포트 | `claude-credentials-file.mjs` | `codex-credentials-file.mjs` |
| usage 포트 | `claude-usage-client.mjs` | `codex-usage-client.mjs` |
| KV 키 | `usage:claude` | `usage:codex` |
| 상태 파일 | `usage-state.claude.json` | `usage-state.codex.json` |
| 가림 목록(D5) | 없음 | G2에서 정함 |

- 공유하는 것: 시계, 로거, wrangler KV 어댑터(키만 다르게 생성), 백오프·게이트·봉투 로직.
- 실행 단위:
  - `runOnce(ports, { provider })`: 한 제공자의 한 실행.
  - `runCycle(providers)`: 제공자를 순서대로(claude → codex) 돌린다. 각 실행을 예외 격리한다.
  - 순차 실행이다. wrangler 프로세스가 동시에 떠서 OAuth 갱신이 겹치는 일을 피한다.
- 중복 실행 가드: 상주 모드의 `inFlight` 가드는 `runCycle` 전체를 감싼다. 이전 주기가 끝나지 않았으면 이번 주기를 통째로 건너뛴다. 제공자별로 가드를 두지 않는다.
- 주기 예산: 240초. 제공자 하나의 상한은 usage 호출 10초 + wrangler 60초 남짓이라 둘의 합이 예산 안이다. `runCycle`은 각 제공자를 시작하기 전에 경과 시간을 보고, 예산을 넘었으면 남은 제공자를 이번 주기에서 건너뛰고 로그에 남긴다. 제공자를 더할 때는 이 합이 예산을 넘지 않는지 확인한다.
- 로그 전용 상태: `cycle_error`(실행이 예외로 끝남), `skipped_budget`(예산 초과로 건너뜀). 봉투의 `status`에는 쓰지 않고 KV도 쓰지 않는다.
- 종료 코드: `--once`와 `--dry-run`에서만 의미가 있다(제공자별 결과 중 가장 큰 값). 상주 모드는 실패를 stderr와 로그에 남기고 계속 돈다. PM2의 `autorestart`는 프로세스가 죽었을 때만 작동하고 수집 실패와는 무관하다.
- 상태 격리: 게이트와 이전 봉투가 제공자별 파일에 있다.
  - claude의 이행: `usage-state.claude.json`이 없을 때(파일 없음)만 기존 `usage-state.json`을 읽는다. 새 파일이 있으면 기존 파일은 읽지도 쓰지도 않는다. 새 파일이 깨져 있으면 기존 파일로 돌아가지 않고 빈 상태로 시작한다. 쓰기는 항상 새 이름이다.
  - 기존 파일은 0.3이 안정된 뒤 수동으로 지운다(U8). 그 전에는 0.2로 되돌릴 때의 복귀점으로 둔다.
  - PM2 앱은 인스턴스 하나이고 `pm2 restart`는 이전 프로세스를 끝낸 뒤 새로 띄우므로 구버전과 신버전이 함께 도는 구간은 없다. 구버전을 손으로 따로 실행하지 않는다.
- 로그: 파일 하나, 줄마다 `provider=<id>`. 응답이 정상이 아닐 때는 `diag=…`를 덧붙인다(D4).
- CLI: `--provider <id>`, `--codex-account-header`(dry-run 전용, G2용). `--credentials-file`은 `--provider`와 `--dry-run`이 함께 있을 때만 받는다.
- KV 쓰기 횟수: 576회/일. Free 한도 1,000회 안이다. 제공자가 넷이 되면 넘는다.

### D4. 요청, 응답 분류, 상태, 백오프

요청:

- 고정 URL(상수), `GET`, 헤더는 `Authorization: Bearer <token>`과 `Accept: application/json`.
- `redirect: 'manual'`. 리다이렉트를 따라가지 않으므로 토큰이 다른 호스트로 가지 않고, 3xx 응답의 `Location`에서 호스트를 읽어 진단에 남길 수 있다.
- 타임아웃 10초.
- `ChatGPT-Account-Id`는 기본으로 보내지 않는다. `ZZIK_CODEX_SEND_ACCOUNT_ID=1`일 때만 D2의 `accountId`를 헤더로 보낸다. 켤지는 G2가 정한다.
- User-Agent를 브라우저나 Codex CLI처럼 꾸미지 않는다. 쿠키와 세션 토큰도 쓰지 않는다. 앞단의 차단을 넘기 위한 위장은 하지 않으며, 막히면 공식 경로(app-server)로 간다.

응답 분류(usage 포트의 결과):

| 응답 | 결과 종류 | 진단(`diag`, 로그에만) |
|---|---|---|
| 200이고 본문이 JSON 객체 | `ok` | |
| 200이지만 JSON 객체가 아님 | `upstream_error` | content-type |
| 401 | 인증 거부 | |
| 403이고 본문이 JSON | 인증 거부 | |
| 403이고 본문이 JSON이 아님 | `upstream_error`(차단) | content-type, `cf-mitigated`, `cf-ray`, 본문 sha256 앞 8자 |
| 3xx | `upstream_error` | `Location`의 호스트만(경로와 쿼리는 남기지 않는다) |
| 429 | `rate_limited` | Retry-After |
| 그 밖의 4xx, 5xx, 타임아웃 | `upstream_error` | |
| 연결 실패 | `network_error` | |

- 진단에 본문, 헤더 전체, 토큰, 계정 값을 넣지 않는다.

인증 관련 상태(`run-once`가 정한다. 두 제공자 공통):

| 조건 | 상태 | 뜻 | 안내(화면) |
|---|---|---|---|
| `expiresAt`이 지났거나 마진 안 | `token_expired` | 호출하지 않음. 클라이언트가 갱신하면 풀린다 | Codex(또는 Claude Code)를 실행하면 갱신된다 |
| 인증 거부이고 `expiresAt`이 미래 | `auth_rejected` | 토큰은 만료 전인데 서버가 거부했다. 실행만으로 풀리지 않을 수 있다 | 클라이언트를 실행해 보고, 그대로면 재로그인(U5). 수집기 로그의 상태 코드 확인 |
| 인증 거부이고 `expiresAt`을 모름 | `auth_required` | 만료인지 거부인지 구분할 수 없다 | 클라이언트를 실행해 본다 |

- `auth_rejected`는 0.3에서 추가하는 상태다(D5). 0.2의 Claude에서도 같은 조건이면 이 상태가 된다.

게이트와 백오프(0.2 D5의 모듈 재사용, 달라지는 것만):

- 인증 거부(`auth_rejected`, `auth_required`): 대기 = min(3600 × 2^(n−1), 21600)초. 1시간, 2시간, 4시간, 이후 6시간. 자격 증명의 `expiresAt`이 바뀌면 즉시 해제한다. 풀리지 않는 거부를 매시간 두드리지 않기 위해서다.
- 차단 응답(JSON이 아닌 403): 429와 같은 수열을 쓴다(600초부터 상한 3,600초).
- 429, 5xx, 타임아웃, 네트워크 오류: 0.2 그대로.
- 사용률 100%(구독 한도 도달)와 조회의 HTTP 429는 다른 것이다. 앞의 것은 200 응답 안의 값이다.

### D5. 봉투, 계약, KV, 식별자 가림

- 봉투 형식은 0.2 D4를 따르고 `schema`는 1을 유지한다. 바뀌는 것:
  - `provider: UsageProvider`
  - `status`에 `auth_rejected` 추가
  - `rawRedacted?: string[]` 추가(가린 키 경로 목록. 가린 것이 없으면 빈 배열이거나 없음)
- `tokenExpiresAt`의 출처는 제공자마다 다르다: claude는 자격 증명 파일의 `expiresAt`, codex는 access token JWT의 `exp`. 둘 다 "이 시각이 지나면 수집기가 호출을 멈춘다"는 같은 뜻으로 쓴다.
- `shared/usage-contract.ts`:
  - `USAGE_PROVIDERS = ['claude', 'codex'] as const`, `type UsageProvider`
  - `USAGE_KV_KEYS: Record<UsageProvider, string>`
  - `USAGE_KEY` 삭제(쓰는 곳이 없다)
  - `USAGE_COLLECTOR_VERSION = '0.3.0'`
- 수집기는 `collector/domain/usage/providers.mjs`에 같은 목록과 키를 두고, 일치 여부를 테스트 하나가 확인한다.
- 식별자 가림:
  - 원칙: 사용량 표시에 필요 없는 개인 식별 값은 KV에 넣지 않는다. 조사 문서의 권고와 같다.
  - 제공자 정의에 가림 목록(키 경로 배열)을 둔다. 수집기가 성공 본문을 파싱해 그 경로의 값을 `"[가림]"`으로 바꾼 뒤 다시 직렬화해 `rawText`에 싣고, 가린 경로를 `rawRedacted`에 적는다. 키와 구조는 그대로 남는다.
  - 가림 목록이 비어 있으면 본문을 건드리지 않고 원문 그대로 싣는다(재직렬화 없음).
  - 가리기 전의 원문은 어디에도 저장하지 않는다(상태 파일의 이전 봉투도 가린 본문이다).
  - codex의 가림 목록은 G2에서 정한다. 식별자 키가 없으면 빈 목록이다. 사용자가 원문 그대로를 원하면 목록을 비우고 그 수용을 ADR에 기록한다.
  - claude의 가림 목록은 비어 있다.
- KV의 값을 읽을 수 있는 주체: Access를 통과한 화면 사용자, 이 Cloudflare 계정에서 KV를 볼 수 있는 계정 구성원, 이 Mac에서 사용자 권한으로 wrangler를 실행할 수 있는 프로세스, KV 읽기 권한이 있는 API 토큰. "보는 사람이 한 명"은 화면에만 해당한다.
- 로그, 상태 파일의 로그 줄, 레포의 fixture에는 실제 응답 값을 남기지 않는다.

### D6. 실응답 미확인 구조 대응

1. 본문 보존: 수집기는 가림 목록의 값만 바꾸고 나머지를 해석하지 않는다. Worker는 봉투를 그대로 넘긴다. 구조가 예상과 달라도 KV와 Raw 보기에는 전체 키가 있다.
2. 값 없는 구조 확인: `--dry-run`이 키 경로 목록을 출력한다. 깊이 6까지, 배열은 `[]`로 표기, 값은 출력하지 않는다. 깊이에서 잘린 곳은 경로 끝에 `…`를 붙여 더 깊은 키가 있음을 알린다.
3. 구조에 덜 의존하는 정규화(프론트 domain): 알려진 경로를 하드코딩하지 않고 "창 객체"를 찾아낸다.

정규화 규칙(`src/domain/usage/codex-view.ts`, 순수 함수. 출력은 기존 `UsageReport`):

- 창 객체: `used_percent`가 0 이상의 유한한 숫자이고 `limit_window_seconds`, `reset_at`, `reset_after_seconds` 중 하나 이상을 가진 객체.
- 탐색: 응답을 깊이 6까지 훑어 창 객체를 전부 찾는다. 배열 안도 본다. 항목 id는 JSON 경로다.
- 배치: `rate_limit` 아래의 창은 "사용 창" 섹션(길이 오름차순), 그 밖의 창은 "추가 한도" 섹션(발견 순서). 없는 창을 0%로 만들지 않는다.
- 라벨: 18,000초 → `5시간 한도`, 604,800초 → `주간 한도`. 다른 길이는 `N시간 한도`/`N일 한도` + "미확인" 배지. `rate_limit` 밖의 창은 `<상위 키 이름> · <창 라벨>` + "미확인". 실측 뒤 확인된 것만 고정 라벨로 올린다.
- 리셋 시각: `reset_at`(Unix 초)이 있으면 ISO로, 없고 `reset_after_seconds`가 있으면 봉투의 `fetchedAt`에 더한다. 둘 다 없으면 null.
- 단계와 집계: 0.2.1의 규칙 재사용(80% 주의, 100% 한도, 리셋이 지난 항목은 집계 제외). `rate_limit.limit_reached === true`이면 전체 상태를 `limit`으로 올린다.
- 기타 항목: 창을 하나도 내지 않은 최상위 키는 전부 "기타 항목"에 나온다. 가려진 값은 `[가림]`으로 보인다.
- 완전성 불변식(테스트로 고정):
  - 응답의 모든 최상위 키가 카드의 출처이거나 "기타 항목"에 있다.
  - 창을 낸 최상위 키에 창이 아닌 필드(`limit_reached` 등)가 있으면 그 필드도 "기타 항목"에 있다.
- 값이 이상하면 던지지 않고 `issues`에 넣는다. 최상위가 객체가 아니면 Raw만 보여 준다.

### D7. Worker API: `GET /api/usage/:provider`

| 경로 | 동작 |
|---|---|
| `GET /api/usage/claude` | `usage:claude`를 읽어 `{ "snapshot": … }` |
| `GET /api/usage/codex` | `usage:codex`를 읽어 `{ "snapshot": … }` |
| `GET /api/usage` | `claude`의 별칭. 배포된 프론트가 쓰는 경로라 0.3 동안 유지하고 다음 버전에서 지운다 |
| `/api/usage/<목록에 없는 값>` | 404 `not_found`. 저장소를 읽지 않는다 |

- 응답 본문, 오류 코드, 공통 헤더, 판정 순서(설정 → 인증 → 경로 → 메서드 → 저장소)는 0.2 D8 그대로다. 미인증 요청은 어떤 경로든 401이다.
- 제공자 판정의 구현 형태를 정해 둔다:
  1. 경로 조각을 `USAGE_PROVIDERS.includes(value)`로 먼저 거른다. 대소문자를 바꾸거나 다듬지 않는다. 통과하지 못하면 404.
  2. 통과한 값으로만 키를 얻는다. `Object.hasOwn(USAGE_KV_KEYS, provider)`를 확인한 뒤 읽는다. 걸러지지 않은 문자열로 객체를 인덱싱하지 않는다(`__proto__`, `constructor` 같은 값이 프로토타입을 돌려주는 일을 막는다).
  3. 요청 문자열로 KV 키를 조립하지 않는다.
- 판정 함수는 `worker/domain/usage/provider.ts`에 둔다(shared에는 로직을 두지 않는다).
- 읽은 봉투의 `provider`가 요청한 제공자와 다르면 502 `snapshot_corrupt`.
- 코드 변경: `SnapshotStore.read(provider)`, `KvSnapshotStore`의 키 고정 제거, `getUsage(store, provider)`, `usage-route.ts`에 `/:provider`와 `/` 별칭.
- Worker는 `status` 값을 검사하지 않으므로 `auth_rejected`와 `rawRedacted`는 그대로 통과한다.

### D8. 프론트: 제공자별 조회와 섹션 화면

dev에 병합된 코드(Query 기반 `useUsage`)를 기준으로 한 변경이다.

계약과 app:

| 파일 | 현재 | 0.3 |
|---|---|---|
| `domain/usage/gateway.ts` | `fetchUsage()`, 성공 결과의 `usage: RawUsage \| null` | `fetchUsage(provider)`, `usage: Record<string, unknown> \| null`, 성공 결과에 `provider` 포함 |

- 이유: 여러 구독의 사용량을 한 번에 보는 화면이다. 탭은 한쪽을 가리고 가려진 쪽의 경고를 놓치게 한다.

  3. 제공자 섹션 × 2(Claude, ChatGPT 고정 순서). 각 섹션은 기존 `UsageDashboard` 하나다.
- 제목 단계: 페이지 `h1`, 제공자 섹션 `h2`, 섹션 안의 "사용 창" 등은 `h3`.

- Raw 보기: `rawRedacted`가 있으면 "값 N개를 가렸습니다"를 Raw 위에 적는다.
- 320px:
  - 요약 줄은 `flex-wrap`. 가장 긴 칩 문구(`ChatGPT · 자격 증명 없음`)가 잘리지 않고 다음 줄로 넘어가야 한다.
  - 섹션 안의 격자는 기본 1열.
  - Codex 항목의 id는 JSON 경로라 길다. `break-all`로 접는다.

| H1 대응 | G1 통과 전까지 구현 전체를 보류(리뷰 권고) | 관측에는 codex 수집기가 돌아야 한다. 다중 제공자 구조는 어느 경로에서도 쓰인다. 프론트 ChatGPT 섹션의 main 반영만 G1에 건다 |
| H1 대응 | mtime = `iat`를 실패 신호로 보고 바로 app-server로 전환 | 수명 10일인 토큰이 7.4일째에 갱신되지 않은 것은 파일 저장이 정상일 때의 모습과 같다. 증거가 아니다 |
| 수집 방식 | 처음부터 Codex app-server | D1. 설치 버전에서 검증되지 않았고 무인 운영에 새 실패 지점을 만든다. 대기 경로로 두고 조건을 정했다 |
| 수집 방식 | Codex CLI의 상태 출력 파싱 | 사람용 출력이라 형식이 바뀌고 raw가 없다 |
| 차단 대응 | 브라우저나 Codex CLI의 User-Agent, 세션 쿠키로 통과 | 앞단 보호를 속이는 방식이고 언제든 다시 막힌다. 막히면 공식 경로로 간다 |
| 토큰 | 수집기가 refresh token으로 직접 갱신 | 회전 충돌로 Codex 로그인이 깨질 수 있다 |
| 만료 판정 | `last_refresh` + 추정 수명, 또는 JWT 서명 검증 | 앞은 가정이 필요하고, 뒤는 수집기의 역할이 아니다 |
| 인증 상태 | `auth_required` 하나로 유지(v1) | 토큰이 유효한데 거부된 경우에 "실행하면 갱신된다"는 틀린 안내가 나가고 원인을 알 수 없다(리뷰 H2) |
| 인증 상태 | 상태를 늘리지 않고 봉투에 `reason` 필드 추가 | 화면과 로그가 상태 하나로 분기하는 지금 구조에서는 상태 값이 더 단순하다 |
| 계정 헤더 | 항상 전송 / 통로 자체를 두지 않음 | 앞은 필요가 확인되지 않았다. 뒤는 G2에서 필요하다고 나왔을 때 코드 변경이 필요해진다. 통로는 두고 기본은 끈다 |
| 원문 | 식별자가 있어도 그대로 저장(v1) | KV를 읽을 수 있는 주체가 화면 사용자보다 넓다. 식별 값은 표시에 필요 없다(리뷰 H3). 사용자가 원하면 가림 목록을 비울 수 있다 |
| 원문 | 가린 사본은 KV에, 원문은 로컬 상태 파일에(리뷰의 b안) | 원문을 쓸 곳이 없다. 저장하지 않는 것이 가장 단순하다 |
| 원문 | 이름 패턴으로 자동 가림 | 미확인 구조에서 `id`로 끝나는 키를 기계적으로 가리면 필요한 값(`limit_id` 등)까지 가려진다. G2에서 사람이 목록을 정한다 |
| `USAGE_KEY` | deprecated 별칭으로 유지(리뷰 M5) | 충돌 대상이던 `0.2/query`가 병합됐고 쓰는 곳이 없다 |
| 수집기 구조 | 제공자별 PM2 프로세스, 병렬 실행, 동적 플러그인 | 상주 프로세스와 wrangler 동시 실행이 늘거나, 제공자 둘에 과하다 |
| 수집기 구조 | 제공자별 `inFlight` 가드 | 두 제공자가 겹쳐 돌 수 있다(리뷰 M3). 가드는 주기 하나다 |
| `ZZIK_PROVIDERS` | 모르는 값이 있으면 기동 실패 | 오타 하나로 Claude 수집까지 멈추고 PM2가 재시작을 반복한다. 무시하고 경고하되, 남는 제공자가 없을 때만 실패한다 |
| 상태 | 한 상태 파일에 제공자별 구획 | 한쪽 쓰기가 다른 쪽 상태를 덮을 여지가 생긴다 |
| KV | 한 키에 두 제공자의 봉투를 합침 | 한 제공자의 실행이 다른 제공자의 값을 다시 써야 한다. 576회/일은 한도 안이다 |
| API | `?provider=` 쿼리, 통합 응답, 기존 경로 즉시 제거 | 경로 방식이 라우팅과 404에 자연스럽고, 통합 응답은 부분 실패 표현이 필요하며, 즉시 제거는 열려 있는 화면을 깬다 |
| 계약 | `schema`를 2로 올림 | 필드 형태가 바뀌지 않았다. 추가된 것은 상태 값 하나와 선택 필드 하나다. 대신 배포 순서(U3)를 지킨다 |
| 정규화 | Worker나 수집기에서 공통 형태로 변환, 알려진 경로만 처리, Claude 형태로 변환 | 구조가 미확인이라 고칠 일이 생기는데 그때 고칠 곳이 프론트 domain 한 곳이어야 한다 |
| 화면 | 제공자 탭, 한 격자에 섞기 | 한쪽이 가려지거나 제공자 단위의 수집 상태를 붙일 자리가 없어진다 |

## Consequences

긍정적:
- Codex 사용량이 0.2와 같은 경로로 들어온다. 새 인프라, 새 비밀, 새 패키지, Access 변경, 사용자 Codex 설정 변경이 없다.
- 제공자별로 상태, 게이트, KV 키, 조회, 화면 섹션이 분리된다.
- 가장 불확실한 두 전제(이 계정에서의 WHAM 동작, 파일 갱신)에 게이트와 실패 시의 순서가 있다. 실패해도 Claude 쪽과 다중 제공자 구조는 남는다.
- 인증 문제가 세 상태로 나뉘어 화면의 안내가 실제 복구 방법과 맞는다. 차단과 리다이렉트는 진단이 로그에 남는다.
- 식별 값은 KV에 들어가지 않는다(G2에서 목록을 정한 경우).
- 응답 구조를 몰라도 키를 잃지 않는다.
- 토큰 수명이 10일이라 유휴 공백의 위험이 Claude보다 작다.

부정적 / 리스크:
- G1이 통과하기 전까지 기능의 성립이 확정되지 않는다. 실패하면 app-server 검증(F2)이라는 추가 작업이 생기고, 그것도 안 되면 사용자 선택(F3)으로 넘어간다.
- G2는 현재 토큰의 만료(11-14) 전에 해야 한다. 놓치면 G1 통과를 기다려야 한다.
- 문서화되지 않은 엔드포인트에 하나 더 의존한다. 앞단의 차단이 Node의 요청을 막으면 이 경로는 닫히고, 우회하지 않기로 했으므로 app-server로 가야 한다.
- 실제 응답을 보지 않고 정한 규칙이 있다(D6). 첫 실측 뒤에 라벨 표, 탐색 규칙, 가림 목록을 정해야 한다.
- 가림 목록이 있으면 `rawText`는 원문 그대로가 아니라 다시 직렬화한 JSON이다(공백과 숫자 표기가 달라질 수 있다).
- KV의 값은 화면 사용자 외에도 계정 구성원, 이 Mac의 wrangler, KV 읽기 토큰이 읽을 수 있다.
- 상태 값 `auth_rejected`가 늘었다. 이 상태를 모르는 예전 프론트가 열려 있으면 해당 섹션이 응답 오류로 보인다(새로 고치면 풀린다). 배포 순서로 줄인다.
- 0.2의 Claude 동작이 두 군데 바뀐다: 만료 마진 60초, 유효한 토큰의 401이 `auth_rejected`로 표시됨.
- KV 쓰기와 wrangler 실행이 두 배가 된다.
- 화면이 길어진다. 모바일에서는 요약 칩으로 보완한다.
- `/api/usage` 별칭과 0.2의 상태 파일이 한동안 남는다.

후속 과제:
- G1 실패 시 app-server 경로(0.3.1)
- `/api/usage` 별칭 제거
- 실측으로 확인된 Codex 버킷의 고정 라벨 등록
- 프론트 Claude 전용 파일의 이름 정리
- 제공자가 더 늘 때 KV 쓰기 한도와 화면 구성 재검토

## Verification

판정 원칙은 0.1, 0.2와 같다. 미인증 응답에 사용량 데이터가 나오면 전체 실패다. 어떤 출력에도 토큰, JWT payload, 계정 식별자 값이 나오면 실패다.

### 단위 테스트와 타입 검사

- V1. `pnpm test`가 D10 표의 항목을 포함해 통과한다. 기존 Claude 테스트가 이름 변경, `provider` 인자, 만료 마진 뒤에도 통과한다.
- V2. `pnpm typecheck`, `pnpm typecheck:collector`, `pnpm build`가 통과한다. arch 테스트가 통과하고(예외 목록 변경 없음) 수집기에 외부 패키지 import가 없다.

### 로컬

- V3. 가짜 자격 증명 dry-run(네트워크 호출 없음):
  - `--dry-run --provider codex --credentials-file tests/fixtures/codex-auth.expired.json` → `status=token_expired`, `called=0`.
  - 만료 30초 전인 가짜 토큰 → `token_expired`(마진).
  - `--credentials-file /nonexistent` → `status=no_credentials`, 종료 코드 0.
  - `ZZIK_PROVIDERS=Claude, nope` → claude만 돌고 경고가 나온다. `ZZIK_PROVIDERS=nope` → 종료 78.
- V4. `wrangler dev`: 헤더 없는 `/api/usage/codex`, `/api/usage/claude`, `/api/usage`, `/api/usage/__proto__`가 모두 401이다.
- V5. G2(U2). 판정 표대로 진행하고 다음을 ADR에 기록한다: status, 키 경로, 식별자 키와 정한 가림 목록, 계정 헤더 필요 여부, `rate_limit` 아래의 창 구조가 D6의 조건에 맞는지.

### 수집기 반영 후

- V6. `pm2 logs zzik-usage-collector`에 주기마다 `provider=claude`와 `provider=codex` 줄이 하나씩 생긴다. 상태 파일 두 개가 0600으로 있다. 로그와 상태 파일에 토큰 문자열과 계정 식별자가 없다. 재시작 직후 claude의 이전 게이트와 마지막 성공 본문이 넘어와 있다. 한 주기가 예산(240초) 안에 끝난다.

- V9. 미인증 차단(쿠키 없는 curl): `/api/usage/codex`가 Access 로그인으로 가는 302이고 본문에 `rawText`나 `used_percent`가 없다. 0.1의 V3~V6과 0.2의 V10을 다시 수행해 통과한다.

## 구현 영향 목록 (구간 A, `.worktree/codex`의 작업 중 코드 기준)

v1을 보고 이미 작성된 코드에서 바꾸거나 더할 것이다. 괄호는 근거 항목.

계약과 포트:

1. `shared/usage-contract.ts`: `UsageStatus`에 `auth_rejected` 추가, `UsageEnvelope`에 `rawRedacted?: string[]` 추가. `USAGE_KEY` 삭제는 그대로 둔다. (H2, H3, M5)
2. `collector/domain/usage/ports.mjs`: `CredentialRead`에 `accountId?: string|null`. usage 포트를 `fetchUsage(token, { accountId })`로. 실패 결과에 `diag?: string`. `LogEntry`에 `diag`. (M2, H2)

domain:

3. `credential-choice.mjs`: `credentialExpired`에 마진(60초) 적용. 경계 테스트 추가. (M1)
4. `gate.mjs`/`backoff.mjs`: 인증 거부 수열(3600 → 21600 상한), 차단 응답 수열(429와 같음). 지금은 인증 게이트가 1시간 고정이다. (H2)
5. `redact.mjs` 신규와 테스트. 제공자 정의에 가림 목록(기본 빈 배열). (H3)
6. `key-paths.mjs`: 깊이 6, 잘린 경로에 `…`. (L1)
7. `envelope.mjs`: `rawRedacted`를 받는다.
8. `jwt-exp.mjs`: 변경 없음. 지금처럼 import 없이 전역 `Buffer`를 쓰는 형태를 유지한다. (M4)

app:

9. `run-once.mjs`: 인증 거부를 `expiresAt`에 따라 `auth_rejected`/`auth_required`로 나눈다. 성공 본문에 가림을 적용한 뒤 봉투를 만든다. 계정 헤더 옵션이 켜졌을 때만 `accountId`를 usage 포트에 넘긴다. 로그 항목에 `diag`. (H2, H3, M2)
10. `run-cycle.mjs`: 제공자를 시작하기 전에 경과 시간을 보고 예산(240초)을 넘으면 건너뛴다(`skipped_budget` 로그). 시계를 주입받는다. (M3)

infra:

11. `codex-credentials-file.mjs`: 결과에 `accountId`. 파일 권한이 넓으면 경고. (M2, L5)
12. `codex-usage-client.mjs`: `redirect: 'manual'`로 바꾸고 3xx를 `upstream_error`로. JSON이 아닌 403과 200에 진단. 계정 헤더 옵션. (H2, L4, M2)
13. `state-file.mjs`: 이전 경로로 넘어가는 조건을 "새 파일 없음"으로 좁힌다. 지금은 새 파일이 깨져 있어도 이전 파일을 읽는다. (M6)
14. `log.mjs`: `diag=` 출력.

조립과 설정:

15. `main.mjs`: `ZZIK_PROVIDERS` 해석(소문자, 중복 제거, 모르는 값 경고, 빈 결과면 종료 78). `--codex-account-header`(dry-run 전용)와 env `ZZIK_CODEX_SEND_ACCOUNT_ID`. (L6, M2)

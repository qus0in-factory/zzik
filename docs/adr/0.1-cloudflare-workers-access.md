## Context

- 목표: 간단한 React+Vite 앱을 Cloudflare에 배포하고 `zzik.qus0in.dev`로 서비스한다. Cloudflare Access로 `qus0in@gmail.com` 한 명만 접속할 수 있고, 접속하면 화면에 `Hello Young-In`이 보인다.
- 레포 `/Users/young-mini/Workspace/zzik`는 사실상 비어 있다(`AGENTS.md`, `.agents/skills`, `scripts`만 있고 git 저장소도 아님).
- 도구: node 24, pnpm, wrangler 4.160 (OAuth 로그인, 계정 `c89ea66c04742e4f6f1feb8dd8e5b775`).
- 권한 제약: wrangler OAuth 토큰은 workers/routes write, zone read만 있다. Access(Zero Trust) write 권한이 없어 wrangler 자격으로는 Access 앱/정책을 만들 수 없다.
- 미확인 전제 (구현 착수 전 또는 해당 단계에서 확인할 것):
  1. `qus0in.dev` zone이 위 계정에 active 상태로 있다.
  2. 계정에 Zero Trust 조직(team domain `<team>.cloudflareaccess.com`)이 만들어져 있다. 없으면 대시보드에서 Free 플랜으로 먼저 만든다.
  3. `zzik.qus0in.dev`에 기존 CNAME 레코드가 없다. CNAME이 있으면 Custom Domain 생성이 확실히 충돌한다. 다른 유형(A/AAAA/TXT)이 있으면 실제 배포 시도로 판정한다.
  4. 현재 wrangler 토큰으로 Custom Domain을 만들 수 있다. 공식 문서가 필요한 권한 조합을 명시하지 않으므로 첫 `wrangler deploy`에서 권한 오류가 없는지로 확인한다. 실패하면 DNS/SSL 권한을 더한 범위 한정 API 토큰을 발급해 그 토큰으로 배포한다.
  5. Zero Trust 조직에 One-time PIN IdP가 등록되어 있다. 새 조직에는 자동으로 추가되지 않으므로, 없으면 구현 순서 2에서 추가한다. 없으면 설계한 로그인 경로가 동작하지 않는다.
  6. Zero Trust 대시보드에서 Access 앱에 Worker destination(`type: "worker"`)을 추가할 수 있다. 리뷰가 인용한 공식 문서(Cloudflare Access for Workers, 2026-11-02) 기준이며, 이 설계에서 직접 확인하지는 않았다. 대시보드에서 불가능하면 D3의 "백스톱 불가 시" 절차를 따른다.

## Decision

### D1. 호스팅: Workers static assets (assets-only Worker)

- Worker 이름은 `zzik`이고, Worker 스크립트 없이 `dist/`만 정적 자산으로 올린다.
- SPA 폴백은 `assets.not_found_handling: "single-page-application"`으로 처리한다.
- 빌드는 순수 Vite(`vite build`), 배포는 `wrangler deploy`로 한다. `@cloudflare/vite-plugin`은 서버 코드가 없으므로 0.1에서는 넣지 않는다.

### D2. 도메인: Custom Domain

- `routes: [{ "pattern": "zzik.qus0in.dev", "custom_domain": true }]`
- DNS 레코드와 인증서를 Cloudflare가 자동으로 만들고 관리한다. origin이 Worker 자체이므로 route 방식의 더미 DNS 레코드가 필요 없다.

### D3. 우회 차단: URL 비활성화 + Worker 단위 Access 백스톱

보호는 두 겹으로 둔다.

1. 설정으로 닫기: `workers_dev: false`, `preview_urls: false`를 명시한다. 이것이 보장하는 범위는 "현재 설정에서 `workers.dev` 호스트와 version URL이 닫혀 있다"까지다. `workers.dev`를 꺼도 version/preview/deployment URL 계열이 따로 꺼지지는 않으며, 이 URL들은 호스트 단위 Access 보호 범위 밖이다. v1의 "진입점은 하나뿐"이라는 단정은 철회한다.
2. Worker 단위 Access destination: D4의 Access 앱에 Worker `zzik`를 destination으로 추가한다. 이 destination은 해당 Worker의 route, Custom Domain, `workers.dev` 호스트, preview를 한꺼번에 보호한다. 설정 두 줄 중 하나가 실수로 바뀌거나 새 URL 계열이 열려도 Access 뒤에 남는다. Access 앱 수와 정책 수는 그대로 1개씩이다.

운영 규칙:
- 배포는 `wrangler deploy`만 쓴다. `wrangler versions upload`와 `--preview-alias`는 쓰지 않는다.
- 배포 출력에 `zzik.qus0in.dev` 외의 URL이 나오면 실패로 보고 V5를 다시 수행한다.

백스톱 불가 시(전제 6 불성립): 호스트 단위 destination만으로 진행하고, 위 운영 규칙과 V5로 대신한다. 이 경우 ADR에 편차로 기록하고 "Worker에서 JWT 검증"을 후속 과제 1순위로 올린다.

Worker 안에서 Access JWT(`Cf-Access-Jwt-Assertion`)를 검증하는 방어 심층화는 0.1에서 하지 않는다. 스크립트가 없는 assets-only 구성을 유지하기 위해서다.

### D4. Access: self-hosted 앱 1개 + Allow 정책 1개, 대시보드에서 수동 생성

| 항목 | 값 |
|---|---|
| Application type | Self-hosted |
| Application name | `zzik` |
| Destination 1 (public hostname) | `zzik.qus0in.dev` (path 없음, 와일드카드 없음, 호스트 전체) |
| Destination 2 (Worker) | Worker `zzik` — 첫 배포 직후 추가 |
| Session duration | 24h (기본값과 같음, 명시적으로 확인한 값) |
| Policy name | `owner-only` |
| Policy action | Allow |
| Include | Emails = `qus0in@gmail.com` |
| Identity provider | One-time PIN — Zero Trust > Integrations > Identity providers에서 신규 추가(기본 제공 아님) |
| 앱의 허용 로그인 수단 | One-time PIN만 선택(조직 기본 Cloudflare IdP 등 다른 수단은 선택 해제) |

- Allow 정책에 맞지 않는 요청은 기본적으로 거부된다. Bypass나 Service Auth 정책은 만들지 않는다.
- 생성 방법은 Zero Trust 대시보드 수동 생성이다. 리소스가 IdP 1개, 앱 1개, 정책 1개뿐이고, wrangler 토큰에 권한이 없어 자동화하려면 별도 토큰 발급과 보관이 필요하기 때문이다. 위 표가 설정의 기준 문서 역할을 한다.
- 순서: 호스트 destination으로 Access 앱을 먼저 만들고 그다음에 배포한다. Worker destination은 Worker가 존재해야 지정할 수 있으므로 첫 배포 직후에 추가한다. 그 사이 구간에도 `workers.dev`와 version URL은 설정으로 닫혀 있고 Custom Domain은 이미 Access 뒤에 있으므로 공개 노출 구간이 없다.

구현 기록(구현 시 채울 것, 후속 JWT 검증의 입력값):

| 항목 | 값 |
|---|---|
| Team domain | `<team>.cloudflareaccess.com` |
| Application AUD | `<aud>` |
| 첫 배포일 (= `compatibility_date`) | `<YYYY-MM-DD>` |

### D5. 디렉터리 구조: 레포 루트 단일 패키지

```
zzik/
├── AGENTS.md
├── .agents/skills/
├── scripts/
├── docs/adr/0.1-cloudflare-workers-access.md   # 이 ADR
├── package.json            # scripts: dev, build, preview(= build 후 wrangler dev), deploy(= build 후 wrangler deploy)
├── pnpm-lock.yaml
├── wrangler.jsonc
├── vite.config.ts
├── tsconfig.json
├── index.html
├── .gitignore              # node_modules, dist, .wrangler
└── src/
    ├── main.tsx
    └── App.tsx             # <h1>Hello Young-In</h1>
```

`wrangler.jsonc` 설계값:

```jsonc
{
  "name": "zzik",
  "compatibility_date": "2026-11-11", // 첫 배포일로 고정. 이후 올릴 때는 ADR에 사유를 남긴다
  "assets": {
    "directory": "./dist/",
    "not_found_handling": "single-page-application"
  },
  "routes": [{ "pattern": "zzik.qus0in.dev", "custom_domain": true }],
  "workers_dev": false,
  "preview_urls": false
}
```

- 스택은 React + TypeScript + Vite(`react-ts` 템플릿 수준)이고, wrangler는 devDependency로 고정한다.
- 화면 문구는 정적 문자열 `Hello Young-In`이다. Access 신원에서 이름을 읽어 오지 않는다.
- `pnpm deploy`는 pnpm 내장 명령과 이름이 겹치므로 배포 스크립트는 `pnpm run deploy`로 실행한다.

### 구현 순서 (참고)

1. 미확인 전제 1~3을 확인한다.
2. 대시보드에서 One-time PIN IdP를 추가한다(이미 있으면 생략).
3. 대시보드에서 Access 앱(호스트 destination, 로그인 수단 OTP만)과 정책을 만든다(D4).
4. 앱을 스캐폴딩하고 로컬 검증(V1, V2)을 수행한다.
5. `pnpm run deploy`로 배포한다. Custom Domain 생성 권한 오류가 없는지 확인한다(전제 4).
6. Access 앱에 Worker `zzik` destination을 추가한다(D3).
7. V3~V9를 수행하고 구현 기록 표(team domain, AUD, 첫 배포일)를 채운다.

## Alternatives

| 결정 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 호스팅 | Cloudflare Pages | Cloudflare가 신규 프로젝트에 Workers를 권장한다. `*.pages.dev`와 브랜치별 preview 도메인이 항상 생겨서 우회를 막으려면 Access 앱이 더 필요하다. git 연동 자동 배포가 장점이지만 0.1에는 필요 없다. |
| 호스팅 | Worker 스크립트 + assets (`run_worker_first`로 JWT 검증) | 방어 심층화는 되지만 코드와 team domain/AUD 설정이 늘어난다. Worker 단위 Access destination이 같은 우회 경로를 코드 없이 막으므로 0.1에는 과하다. 후속 ADR 후보다. |
| 도메인 | Route (`zzik.qus0in.dev/*`) | proxied DNS 레코드를 따로 만들어야 하는데 현재 토큰에 DNS write 권한이 없다. origin이 없는 구성에는 custom domain이 맞다. |
| Access 생성 | 범위를 좁힌 API 토큰 + curl/스크립트 | 재현성은 좋지만 토큰 발급과 보관이 필요하다. 리소스 3개를 한 번 만드는 데 비해 비용이 크다. |
| Access 생성 | Terraform | 드리프트 관리와 코드 리뷰가 가능하지만 state 관리, provider, 토큰이 필요하다. 보호 대상이 늘어나면 도입한다. |
| IdP | Google 로그인 | UX는 좋지만 GCP OAuth 클라이언트 설정이 필요하다. One-time PIN도 IdP 추가가 필요하지만 대시보드 클릭 한 번이고 외부 설정이 없다. 나중에 추가할 수 있다. |
| IdP | 조직 기본 Cloudflare IdP를 그대로 사용 | 추가 설정은 없지만 로그인 주체가 Cloudflare 계정에 묶이고, 비허용 사용자 동작(V8)의 문서화된 판정 기준이 OTP 쪽에만 있다. 로그인 수단을 하나로 한정해 대조를 단순하게 한다. |
| 우회 차단 | 호스트 단위 destination만 사용 (v1 설계) | `workers_dev`/`preview_urls` 설정 실수 한 번이나 version/preview URL 생성으로 Access를 통째로 우회할 수 있다(리뷰 H1). 백스톱 불가 시의 차선책으로만 남긴다. |
| 우회 차단 | 계정 수준 "Protect all Workers" (리뷰 H1-3) | 계정의 다른 Worker 전체에 영향을 주는 계정 범위 변경이라 이 ADR의 범위를 넘는다. Worker별 "Make this Worker public" bypass가 생기면 반대로 공개되므로 대조 항목도 늘어난다. Worker 한 개만 지정하는 destination이 같은 효과를 더 좁은 범위로 낸다. |
| 우회 차단 | workers.dev를 켜 두고 Access로 보호 | Worker destination을 쓰면 기술적으로 가능하지만, 쓰지 않는 URL은 꺼 두는 편이 두 겹 보호에 맞다. |
| 권한 실패 대응 | 임시로 workers.dev로 배포한 뒤 도메인 연결 (리뷰 M6) | Worker destination은 Worker가 생긴 뒤에야 붙일 수 있어서, 그 전까지 `workers.dev` URL이 Access 없이 공개된다. "공개 노출 구간 없음" 원칙과 충돌한다. 범위 한정 토큰 발급으로 대응한다. |
| 구조 | `apps/web` 모노레포 | 앱이 하나뿐이라 workspace 오버헤드만 생긴다. 두 번째 패키지가 생길 때 옮긴다. |

## Consequences

긍정적:
- 구성 파일 하나(`wrangler.jsonc`)와 Access 앱 하나로 끝난다.
- 보호가 두 겹이다. URL 설정이 실수로 바뀌어도 Worker 단위 Access가 남고, Access destination 하나가 빠져도 URL은 닫혀 있다.
- 비용이 들지 않는다. 정적 자산 요청은 Worker 스크립트를 호출하지 않아 과금되지 않고, Zero Trust는 Free 50석 안이다. 나중에 Worker 스크립트를 붙이면 요청 과금 가정이 바뀐다.
- 나중에 Worker 스크립트(API, JWT 검증)를 붙일 때 Pages에서 옮겨 올 필요가 없다.

부정적 / 리스크:
- 현재 wrangler 토큰으로 Custom Domain까지 배포되는지는 첫 배포 전까지 확정되지 않는다(전제 4).
- Access 설정이 코드로 남지 않는다. 대시보드에서 바뀌어도 감지할 수 없고, 이 ADR의 D4 표가 유일한 기준이다. Access 앱이나 정책이 삭제되면 두 겹 모두와 무관하게 공개되므로, Access 설정을 바꾼 뒤에는 V3~V5와 V9를 다시 수행한다.
- Worker destination 백스톱은 0.1에서 실측하지 않는다. 실측하려면 `workers.dev`나 version URL을 일부러 열어야 하는데 그 자체가 노출 위험이라 하지 않는다. V9의 설정 대조와 공식 문서 서술에 의존한다.
- 수동 단계가 늘었다(IdP 추가, 앱 생성, 배포 후 destination 추가). 에이전트만으로는 끝낼 수 없고 사용자가 대시보드 작업을 두 번(배포 전, 배포 후) 해야 한다.
- preview URL이 없어서 배포 전 확인은 로컬에서만 할 수 있다. `vite dev`는 Workers asset router를 재현하지 않으므로 라우팅 확인은 `wrangler dev`로 한다(V2).
- One-time PIN은 로그인할 때마다 메일을 확인해야 한다(세션 24h).
- Custom Domain을 삭제해도 Advanced Certificate는 자동으로 지워지지 않는다. 롤백하거나 재구성할 때 SSL/TLS > Edge Certificates에서 잔여 인증서를 직접 정리한다.

후속 과제:
- Access를 IaC로 옮기기(Terraform 또는 API 스크립트)
- Worker에서 JWT 검증(구현 기록의 team domain, AUD 사용)
- Google IdP 추가
- git 초기화와 CI 배포

## Verification

판정 원칙: 미인증 요청에 대해서는 상태 코드보다 "앱 콘텐츠가 나오지 않는다"가 우선한다. 미인증 응답 본문에 `Hello Young-In`이나 앱 번들이 한 번이라도 나오면 전체 실패다.

### 로컬 (배포 전)

- V1. 빌드와 UI: `pnpm build`가 성공하고 `dist/index.html`과 `dist/assets/*.js`가 생긴다. `pnpm dev`(vite) 화면에 `Hello Young-In`이 보인다. 이 단계는 UI 확인용이며 라우팅은 검증하지 않는다.
- V2. Workers 라우팅: 빌드 후 `wrangler dev`로 `dist/`를 서빙한다. `/`와 `/any/path`가 둘 다 200으로 `index.html`을 반환하고, `/assets/<실제파일>.js`가 200으로 번들을 반환한다. 존재하지 않는 `/assets/nope.js`의 응답(SPA 폴백으로 `index.html` 200이 예상됨)은 기대값으로 단언하지 않고 관측값을 기록한다.

### 미인증 차단 (배포 후, 쿠키 없는 curl)

- V3. HTML 차단: GET으로 요청해 `302`이고 `Location`에 `cdn-cgi/access/login`이 들어 있다. `Location`의 호스트는 app host(`zzik.qus0in.dev`)나 team domain 중 하나이며 어느 쪽인지 기록한다. 본문에 `Hello Young-In`이 없다.
- V4. 자산과 deep path 차단: 실제 번들 파일(`/assets/<실제파일>.js`)과 내비게이션 형태의 deep path(`Sec-Fetch-Mode: navigate` 헤더, `/any/path`)가 둘 다 `302`이고 본문에 앱 콘텐츠가 없다.
- V5. `workers.dev` 계열 미서빙: `https://zzik.<account-subdomain>.workers.dev`가 404, DNS 미해석, Access 302 중 하나다. 200으로 앱 HTML이 나오면 실패다. 배포 출력에 `zzik.qus0in.dev` 외의 URL이 없다. 같은 엔드포인트에 `Host: zzik.qus0in.dev`를 위조해 보낸 요청도 앱 HTML을 반환하지 않는다.
- V6. 평문 HTTP: `http://zzik.qus0in.dev`가 HTTPS로의 리다이렉트(301/308)나 Access 302를 반환하고 본문에 앱 콘텐츠가 없다. zone의 Always Use HTTPS/HSTS 상태는 관측값으로 기록한다(현재 토큰으로는 변경할 수 없음).

```bash
# V3
curl -s -D - -o /tmp/zzik-body.html https://zzik.qus0in.dev | grep -iE '^(HTTP/|location:)'
grep -q 'Hello Young-In' /tmp/zzik-body.html && echo "FAIL: content leaked" || echo "OK"

# V4 (파일명은 dist/assets의 실제 이름으로 교체)
curl -s -o /dev/null -w '%{http_code}\n' https://zzik.qus0in.dev/assets/index-XXXX.js          # 기대: 302
curl -s -o /dev/null -w '%{http_code}\n' -H 'Sec-Fetch-Mode: navigate' \
  https://zzik.qus0in.dev/any/path                                                             # 기대: 302

# V5
curl -s -o /tmp/zzik-wd.html -w '%{http_code}\n' https://zzik.<account-subdomain>.workers.dev  # 200+앱 HTML이면 실패
curl -s -o /tmp/zzik-host.html -w '%{http_code}\n' -H 'Host: zzik.qus0in.dev' \
  https://zzik.<account-subdomain>.workers.dev
grep -l 'Hello Young-In' /tmp/zzik-wd.html /tmp/zzik-host.html && echo "FAIL: content leaked" || echo "OK"

# V6
curl -s -D - -o /tmp/zzik-http.html http://zzik.qus0in.dev | grep -iE '^(HTTP/|location:)'
grep -q 'Hello Young-In' /tmp/zzik-http.html && echo "FAIL: content leaked" || echo "OK"
```

### 인증 동작 (브라우저 수동 확인)

- V7. 허용 사용자와 SPA 폴백: 시크릿 창에서 `https://zzik.qus0in.dev`에 접속한다. 로그인 화면에 One-time PIN만 보인다. `qus0in@gmail.com`으로 PIN을 받아 로그인하면 `Hello Young-In`이 보인다. 같은 세션에서 `https://zzik.qus0in.dev/any/path`로 이동해도 앱이 보인다. 이 항목은 브라우저로만 확인한다. curl로 재현하려면 DevTools > Application > Cookies의 `CF_Authorization` 값을 `curl -H "cookie: CF_Authorization=$TOKEN"`으로 넘기되, 이 값은 자격 증명이므로 파일이나 레포에 남기지 않는다.
- V8. 비허용 사용자: 다음 세 가지를 모두 확인한다.
  1. 허용되지 않은 이메일로 코드를 요청하면 메일이 오지 않는다. 화면 문구는 허용 여부와 상관없이 "A code has been emailed to you"이므로 이것만으로는 판정하지 않는다.
  2. 임의의 코드를 입력하면 차단 메시지(문서상 `That account does not have access.`)가 나오고 앱에 들어가지 못한다.
  3. 그 직후 V3을 다시 돌려도 앱 HTML이 나오지 않는다.

  참고: Access Authentication 로그에는 코드를 입력한 뒤의 시도만 남는다. 코드 요청만 하고 끝낸 경우 로그가 없는 것이 정상이다.

### 설정 대조 (대시보드)

- V9. Access 앱과 정책이 D4 표와 같다.
  1. Destination이 정확히 두 개다: public hostname `zzik.qus0in.dev`(경로, 와일드카드, 추가 도메인 없음)와 Worker `zzik`. 백스톱 불가로 진행한 경우 hostname 하나뿐이며 편차로 기록되어 있다.
  2. 정책은 Allow 1개뿐이고 Include는 Emails 1개(`qus0in@gmail.com`)다.
  3. Bypass와 Service Auth 정책이 0개다.
  4. 앱의 로그인 수단이 One-time PIN 하나다. Session duration이 24h다.
  5. Team domain과 AUD 값을 D4 구현 기록 표에 적었다.
  6. 계정 수준 Workers Access("Protect all Workers")를 켜지 않았고 "Make this Worker public" bypass가 없다.

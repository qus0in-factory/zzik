# ADR 0.1 — zzik: React+Vite 앱을 Cloudflare Workers에 배포하고 Access로 단일 사용자 보호

- 상태: Accepted (설계: fable, 총괄: opus)
- 날짜: 2026-11-11
- 범위: 호스팅, 도메인 연결, 접근 제어, 디렉터리 구조, 검증

## Context

- 목표: 간단한 React+Vite 앱을 Cloudflare에 배포하고 `zzik.qus0in.dev`로 서비스한다. Cloudflare Access로 `qus0in@gmail.com` 한 명만 접속할 수 있고, 접속하면 화면에 `Hello Young-In`이 보인다.
- 레포 `/Users/young-mini/Workspace/zzik`는 사실상 비어 있다(`AGENTS.md`, `.agents/skills`, `scripts`만 있고 git 저장소도 아님).
- 도구: node 24, pnpm, wrangler 4.160 (OAuth 로그인, 계정 `c89ea66c04742e4f6f1feb8dd8e5b775`).
- 권한 제약: wrangler OAuth 토큰은 workers/routes write, zone read만 있다. Access(Zero Trust) write 권한이 없어 wrangler 자격으로는 Access 앱/정책을 만들 수 없다.
- 미확인 전제 (구현 착수 전에 확인할 것):
  1. `qus0in.dev` zone이 위 계정에 active 상태로 있다.
  2. 계정에 Zero Trust 조직(team domain `<team>.cloudflareaccess.com`)이 만들어져 있다. 없으면 대시보드에서 Free 플랜으로 먼저 만든다.
  3. `zzik.qus0in.dev`에 기존 DNS 레코드가 없다. 있으면 custom domain 생성이 충돌한다.

## Decision

### D1. 호스팅: Workers static assets (assets-only Worker)

- Worker 이름은 `zzik`이고, Worker 스크립트 없이 `dist/`만 정적 자산으로 올린다.
- SPA 폴백은 `assets.not_found_handling: "single-page-application"`으로 처리한다.
- 빌드는 순수 Vite(`vite build`), 배포는 `wrangler deploy`로 한다. `@cloudflare/vite-plugin`은 서버 코드가 없으므로 0.1에서는 넣지 않는다.

### D2. 도메인: Custom Domain

- `routes: [{ "pattern": "zzik.qus0in.dev", "custom_domain": true }]`
- DNS 레코드와 인증서를 Cloudflare가 자동으로 만들고 관리한다. origin이 Worker 자체이므로 route 방식의 더미 DNS 레코드가 필요 없다.

### D3. 우회 차단: workers.dev와 preview URL 비활성화

- `workers_dev: false`, `preview_urls: false`를 설정에 명시한다.
- 그러면 Worker로 들어오는 경로는 `zzik.qus0in.dev` 하나뿐이고, 이 호스트 전체를 Access가 막는다.
- Worker 안에서 Access JWT(`Cf-Access-Jwt-Assertion`)를 검증하는 방어 심층화는 0.1에서 하지 않는다. 스크립트가 없는 assets-only 구성을 유지하기 위해서다.

### D4. Access: self-hosted 앱 1개 + Allow 정책 1개, 대시보드에서 수동 생성

| 항목 | 값 |
|---|---|
| Application type | Self-hosted |
| Application name | `zzik` |
| Domain | `zzik.qus0in.dev` (path 없음, 호스트 전체) |
| Session duration | 24h |
| Policy name | `owner-only` |
| Policy action | Allow |
| Include | Emails = `qus0in@gmail.com` |
| Identity provider | One-time PIN (기본 제공) |

- Allow 정책에 맞지 않는 요청은 기본적으로 거부된다. Bypass나 Service Auth 정책은 만들지 않는다.
- 생성 방법은 Zero Trust 대시보드 수동 생성이다. 리소스가 앱 1개, 정책 1개뿐이고, wrangler 토큰에 권한이 없어 자동화하려면 별도 토큰 발급과 보관이 필요하기 때문이다. 위 표가 설정의 기준 문서 역할을 한다.
- Access 앱을 먼저 만들고 그다음에 배포한다. 첫 배포 순간부터 보호된 상태가 되어 공개 노출 구간이 없다.

### D5. 디렉터리 구조: 레포 루트 단일 패키지

```
zzik/
├── AGENTS.md
├── .agents/skills/
├── scripts/
├── docs/adr/0.1-cloudflare-workers-access.md   # 이 ADR의 최종 위치
├── package.json            # scripts: dev, build, preview, deploy(= build 후 wrangler deploy)
├── pnpm-lock.yaml
├── wrangler.jsonc
├── vite.config.ts
├── tsconfig.json
├── index.html
├── .gitignore              # node_modules, dist, .wrangler
└── src/
    ├── main.tsx
    └── App.tsx             # <h1>Hello Young-In</h1>
```

`wrangler.jsonc` 설계값:

```jsonc
{
  "name": "zzik",
  "compatibility_date": "2026-11-11",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  },
  "routes": [{ "pattern": "zzik.qus0in.dev", "custom_domain": true }],
  "workers_dev": false,
  "preview_urls": false
}
```

- 스택은 React + TypeScript + Vite(`react-ts` 템플릿 수준)이고, wrangler는 devDependency로 고정한다.
- 화면 문구는 정적 문자열 `Hello Young-In`이다. Access 신원에서 이름을 읽어 오지 않는다.

### 구현 순서 (참고)

1. 미확인 전제 3가지를 확인한다.
2. 대시보드에서 Access 앱과 정책을 만든다(D4).
3. 앱을 스캐폴딩하고 `pnpm build`를 로컬에서 확인한다.
4. `wrangler deploy`로 배포한다.
5. Verification을 수행한다.

## Alternatives

| 결정 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 호스팅 | Cloudflare Pages | Cloudflare가 신규 프로젝트에 Workers를 권장한다. `*.pages.dev`와 브랜치별 preview 도메인이 항상 생겨서 우회를 막으려면 Access 앱이 더 필요하다. git 연동 자동 배포가 장점이지만 0.1에는 필요 없다. |
| 호스팅 | Worker 스크립트 + assets (`run_worker_first`로 JWT 검증) | 방어 심층화는 되지만 코드와 team domain/AUD 설정이 늘어난다. 진입점이 하나뿐인 0.1에는 과하다. 후속 ADR 후보다. |
| 도메인 | Route (`zzik.qus0in.dev/*`) | proxied DNS 레코드를 따로 만들어야 하는데 현재 토큰에 DNS write 권한이 없다. origin이 없는 구성에는 custom domain이 맞다. |
| Access 생성 | 범위를 좁힌 API 토큰 + curl/스크립트 | 재현성은 좋지만 토큰 발급과 보관이 필요하다. 리소스 2개를 한 번 만드는 데 비해 비용이 크다. |
| Access 생성 | Terraform | 드리프트 관리와 코드 리뷰가 가능하지만 state 관리, provider, 토큰이 필요하다. 보호 대상이 늘어나면 도입한다. |
| IdP | Google 로그인 | UX는 좋지만 GCP OAuth 클라이언트 설정이 필요하다. One-time PIN은 설정 없이 Gmail 주소로 바로 동작한다. 나중에 추가할 수 있다. |
| 우회 차단 | workers.dev를 켜 두고 Access로 보호 | 보호 대상이 2개 이상으로 늘고 설정 실수 여지가 생긴다. 쓰지 않는 URL은 끄는 편이 단순하다. |
| 구조 | `apps/web` 모노레포 | 앱이 하나뿐이라 workspace 오버헤드만 생긴다. 두 번째 패키지가 생길 때 옮긴다. |

## Consequences

긍정적:
- 구성 파일 하나(`wrangler.jsonc`)와 Access 앱 하나로 끝나고, 현재 wrangler 권한으로 배포할 수 있다.
- 공개 진입점이 custom domain 하나뿐이라 우회 경로를 따질 범위가 좁다.
- 비용이 들지 않는다(Workers 정적 자산 요청 무료, Zero Trust Free 50석).
- 나중에 Worker 스크립트(API, JWT 검증)를 붙일 때 Pages에서 옮겨 올 필요가 없다.

부정적 / 리스크:
- Access 설정이 코드로 남지 않는다. 대시보드에서 바뀌어도 감지할 수 없고, 이 ADR의 표가 유일한 기준이다.
- 보호가 Access 한 겹에만 의존한다. 누군가 `workers_dev`나 `preview_urls`를 다시 켜거나 Access 앱을 지우면 곧바로 공개된다. 설정 변경 때 Verification 2~3번을 다시 돌려 완화한다.
- preview URL이 없어서 배포 전 확인은 로컬(`pnpm dev`, `pnpm preview`)에서만 할 수 있다.
- One-time PIN은 로그인할 때마다 메일을 확인해야 한다(세션 24h).
- 수동 단계(Access 생성)가 있어서 에이전트만으로는 전체 과정을 끝낼 수 없고 사용자가 대시보드 작업을 해야 한다.

후속 과제:
- Access를 IaC로 옮기기(Terraform 또는 API 스크립트)
- Worker에서 JWT 검증
- Google IdP 추가
- git 초기화와 CI 배포

## Verification

1. 로컬 확인: `pnpm build`가 성공하고 `dist/index.html`이 생긴다. `pnpm dev`로 띄운 화면에 `Hello Young-In`이 보인다.
2. 미인증 차단: `curl -sI https://zzik.qus0in.dev`가 `302`를 반환하고 `Location`이 `https://<team>.cloudflareaccess.com/cdn-cgi/access/login/...`이다. 응답 본문에 앱 HTML(`Hello Young-In`)이 없어야 한다.
3. 우회 차단: `curl -sI https://zzik.<account-subdomain>.workers.dev`가 앱을 서빙하지 않는다(404 또는 Cloudflare 오류). 배포 출력에 workers.dev URL과 preview URL이 나오지 않는다.
4. 허용 사용자: 시크릿 창에서 `https://zzik.qus0in.dev`에 접속해 `qus0in@gmail.com`으로 PIN을 받아 로그인하면 `Hello Young-In`이 보인다.
5. 비허용 사용자: 다른 이메일을 넣으면 PIN이 오지 않아 통과할 수 없다. Zero Trust의 Access 로그에서 허용/차단 기록을 확인한다.
6. SPA 폴백: 로그인한 상태에서 `https://zzik.qus0in.dev/any/path`가 200으로 앱을 반환한다.
7. 설정 대조: 대시보드의 Access 앱과 정책이 D4 표와 같다(정책 1개, Include에 이메일 1개, Bypass 없음).

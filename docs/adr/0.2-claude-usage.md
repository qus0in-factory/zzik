## Context

- 목표: zzik 대시보드에 Claude 구독 사용량을 표시한다. 5시간/7일 창뿐 아니라 `seven_day_fable` 같은 모델별 한도를 포함해 응답에 있는 모든 항목을 보여 주고, raw JSON도 그대로 볼 수 있게 한다.
- 0.1 상태(이슈 #2 실측):
  - Worker `zzik`(assets-only), Custom Domain `zzik.qus0in.dev`, `workers_dev: false`, `preview_urls: false`.
  - Access team domain `qus0in.cloudflareaccess.com`, 앱 AUD `d83bb3725ec247352d8a87ea9be8fc43a4aea78d68821b927a479f622bf29b79`.
  - `/`, `/assets/*.js`, `/any/path`가 미인증에서 모두 302다(호스트 destination 동작 확인).
  - 0.1 D3의 두 번째 겹인 Worker destination은 추가됐는지 확인되지 않았다.
- 코드 상태(main `b8932a9`): `src/{ui,app,domain,infra}/`, 테스트는 `tests/`가 `src/`를 미러링(`tests/domain/…`, `tests/ui/…`), `vitest.config.ts`의 include는 `tests/**/*.test.{ts,tsx}`, `tsconfig.json`의 include는 `src`, `tests`, 설정 파일. 규칙은 `.agents/skills/layered-tdd`.
- 0.2.1 상태(`.worktree/ui`, 커밋 3개, 미병합): 목 데이터로 화면이 구현되어 있다. 0.2가 이어받는 것은 다음과 같다.
  - `src/domain/usage/`: `types.ts`, `classify.ts`, `labels.ts`, `level.ts`, `staleness.ts`, `view.ts`(`buildUsageView`), `gateway.ts`(포트 `UsageGateway`, `UsageClock`, `UsageScheduler`, `UsageVisibility`)
  - `src/app/usage/`: `load-usage.ts`, `usage-poller.ts`, `useUsage.ts`, `usage-text.ts`, `UsageGatewayContext.tsx`
  - `src/infra/usage/`: `fixture-usage-gateway.ts`(`?fixture=` 쿼리로 시나리오 전환), `browser-runtime.ts`
  - `src/ui/usage/`: `UsageSection`, `UsageDashboard`, `StatusBar`, `LimitCard`, `OtherItems`, `RawJson`
  - `tests/{domain,app,infra,ui}/usage/`, `tests/arch/layers.test.ts`(`src/`만 검사), `tests/fakes/usage-ports.ts`, `tests/fixtures/claude-usage.*.json`
  - 게이트웨이 성공 결과는 `{ ok: true; usage: RawUsage }`로 upstream 응답 객체만 담는다. 수집 상태(봉투)는 아직 없다.
- 데이터 출처(조사: `docs/research/biseo-usage.md`): `GET https://api.anthropic.com/api/oauth/usage`, 헤더 `Authorization: Bearer <Claude Code OAuth access token>`, `anthropic-beta: oauth-2025-04-20`, `Accept: application/json`. 응답은 최상위 키마다 `{ utilization, resets_at }` 객체 또는 `null`이다. 429가 실제로 발생한다.
- 자격 증명: 이 Mac에 `~/.claude/.credentials.json`과 Keychain 항목 `Claude Code-credentials`가 둘 다 있다. access token은 만료되고 Claude Code가 갱신한다.
- 확인된 사실(리뷰의 공식 문서 대조):
  - KV Free 한도는 쓰기 1,000회/일, 읽기 100,000회/일, 같은 키 쓰기 1회/초, 값 25MiB다.
  - `run_worker_first` 배열형은 wrangler 4.20.0 이상에서 지원되고(레포는 4.159), 자동 `Sec-Fetch-Mode: navigate` 감지를 끈다.
  - Access 서명 키는 6주마다 회전하고 이전 키는 7일간 유효하다.
  - Workers static assets 구성에서도 Access는 자산과 앱을 계속 보호한다. 단 라우터가 `ctx.access`를 사용자 Worker에 넘기지 않는다.
  - Cloudflare API 토큰 권한은 계정/존 단위이며 KV namespace 단위로 좁힐 수 없다.
- 제약:
  - Worker에는 파일 시스템이 없어 로컬 자격 증명을 읽을 수 없다.
  - 0.1의 불변 조건: Access 앱 1개, 정책 1개, Bypass와 Service Auth 정책 0개, 공개 진입점 추가 없음.
  - usage 엔드포인트는 문서화된 공개 API가 아니다. 스키마가 예고 없이 바뀔 수 있다.

미확인 전제 (구현 중 해당 단계에서 확인한다. 토큰 값은 어떤 경우에도 출력하지 않는다):

1. 자격 증명 JSON 구조가 파일과 Keychain 모두 `claudeAiOauth.accessToken`, `claudeAiOauth.expiresAt`(ms epoch)이다. 키 이름과 `expiresAt`만 출력해 확인한다.
2. LaunchAgent 문맥에서 `security find-generic-password -s 'Claude Code-credentials' -w`가 프롬프트 없이 동작한다. 화면 잠금 중에 실패하는지도 본다. 실패하면 파일로 넘어간다(D3).
3. 이 Mac에서 헤더 3개만으로 usage 엔드포인트가 200을 준다. 실제 응답의 키 목록과, 한도 항목에 `utilization`/`resets_at` 외의 필드가 있는지(`extra_usage` 등) 확인한다. 개인 식별 정보가 없는지 본 뒤 `tests/fixtures/`에 추가한다.
4. 현재 wrangler OAuth로 KV namespace 생성과 KV 바인딩이 있는 배포가 된다. 안 되면 사용자가 대시보드에서 만든다.
5. `run_worker_first: ["/api/*"]`에서 "자산에도 없고 패턴에도 안 맞는 경로"가 (a) Worker 없이 SPA 폴백으로 서빙되는지 (b) Worker가 호출되는지. 문서만으로는 확정되지 않는다(V5에서 관측).
6. 0.1의 Worker destination이 Access 앱에 들어 있는지(U1).
7. access token 수명 T. `expiresAt`과 갱신 시각의 차이로 잰다(D3의 추정식에 대입).
8. 이 계정에 다른 KV namespace가 있는지, 있다면 민감한 값이 들어 있는지(D3의 수용 조건).
9. biseo 로컬 백엔드가 이 Mac에서 같은 토큰으로 같은 엔드포인트를 60초마다 호출하고 있는지. 돌고 있으면 429가 늘 수 있다.
10. `GET /user/tokens/verify` 응답에 `expires_on`이 있다. 없으면 만료일을 사용자가 직접 입력한다(D3).
11. `jose` v6이 `nodejs_compat` 없이 Workers에서 번들되고 동작한다(V5).

## Decision

전체 구조:

```
[Mac] launchd(5분) → collector(Node 24)
        ├─ Claude 자격 증명 읽기(Keychain/파일, 읽기 전용)
        ├─ GET api.anthropic.com/api/oauth/usage
        └─ PUT Cloudflare KV REST API  ──→  KV `usage:claude` (봉투 1건)
                                                   │
[브라우저] ──Access──→ Worker `zzik` GET /api/usage ──┘ (JWT 검증 후 KV 읽기)
            └────────→ dist에 존재하는 자산 파일: Worker 스크립트를 거치지 않음
```

### D1. 수집 위치: 로컬 수집기가 Cloudflare KV에 직접 쓴다 (push, HTTP ingest 없음)

- 이 Mac의 수집기가 usage 엔드포인트를 호출하고, 결과를 Cloudflare REST API로 KV에 직접 쓴다. Worker는 KV를 읽기만 한다.
- Claude OAuth 토큰은 Mac 밖으로 나가지 않는다(목적지는 `api.anthropic.com`뿐).
- Worker에 쓰기 엔드포인트를 만들지 않는다. 수집 경로가 Access를 지나지 않으므로 0.2가 새로 요구하는 Access 설정 변경은 없다(Bypass와 Service Auth 0개 유지). 다만 0.1에서 미확인으로 남은 Worker destination은 0.2 배포 전에 닫는다(U1).
- Mac으로 들어오는 인바운드 경로(Tailscale funnel, tunnel)를 만들지 않는다.
- 대가: Mac이 꺼져 있거나 잠자는 동안에는 값이 갱신되지 않는다. D4의 stale 표시로 드러낸다.

### D2. 수집기: 의존성 없는 Node 스크립트 + launchd

- 구현: `collector/main.mjs` (Node 24, 외부 패키지 없음, JSDoc 타입). 레이어 배치는 D11.
- 실행: LaunchAgent `dev.qus0in.zzik.usage-collector` (`StartInterval` 300, `RunAtLoad` true, `ProcessType` Background). 실행마다 한 번 수집하고 종료한다. launchd는 잠에서 깬 뒤 밀린 실행을 한 번으로 합쳐 돌린다.
- 설치: `collector/install.sh`가 스크립트를 `~/Library/Application Support/zzik/collector/`로 복사하고 plist를 렌더링해 `~/Library/LaunchAgents/`에 둔 뒤 `launchctl bootstrap`한다. 레포 작업 트리와 실행 중인 수집기를 분리하기 위해서다. plist에는 설치 시점의 node 절대 경로를 넣는다. FileVault가 꺼져 있으면 경고를 출력한다. `collector/uninstall.sh`가 반대 작업을 한다.
- 로컬 파일 (디렉터리 0700, 파일 0600, tmp에 쓰고 rename):
  - `~/Library/Application Support/zzik/config.json`: 비밀이 아닌 설정(account id, KV namespace id, key 이름, 주기, API 토큰 만료일)
  - `~/Library/Application Support/zzik/cloudflare-api-token`: Cloudflare API 토큰(D3)
  - `~/Library/Application Support/zzik/usage-state.json`: 마지막 봉투, 게이트 상태
  - `~/Library/Logs/zzik/usage-collector.log`: 실행당 한 줄
- 한 번의 실행 순서: 게이트 확인 → 자격 증명 읽기 → usage 호출(타임아웃 10초) → 봉투 생성 → 로컬 상태 저장 → KV PUT(타임아웃 10초) → 로그 한 줄.
  - 로컬 상태가 기준이고 KV는 그 사본이다. KV PUT이 실패하면 재시도 루프 없이 0이 아닌 코드로 끝내고, 다음 실행이 그때의 봉투를 다시 쓴다. 그 사이 KV는 한 주기 뒤처질 뿐이다.
  - 게이트로 호출을 건너뛴 실행도 상태와 KV를 쓴다(하트비트). `--dry-run`은 상태도 KV도 쓰지 않는다.
- 로그 한 줄의 내용: 시각, `status`, `called`, `httpStatus`, `tokenExpiresAt`, KV 결과. 직전 실행과 `status`가 다르면 전이(`token_expired→ok` 등)를, 자격 증명의 `expiresAt`이 바뀌면 `token_refreshed`를 같은 줄에 적는다. 토큰 값은 적지 않는다.
- CLI 플래그:
  - `--once`: 기본 동작. 수동 실행도 게이트를 따른다(강제 호출 플래그는 두지 않는다). 수동 실행도 KV 쓰기 한도(1,000회/일)에 들어간다.
  - `--dry-run`: usage 호출까지만 하고 status, 응답의 키 목록, 본문 sha256만 출력한다.
  - `--credentials-file <path>`, `--no-keychain`: 상태 재현용. `--dry-run`과 함께일 때만 받는다(시험용 자격 증명으로 KV를 쓰는 일을 막는다).
- 운영 절차(설치, 점검, 토큰 교체, 제거)는 `.agents/skills/zzik-usage-collector/`에 두고 `AGENTS.md`에는 한 줄 포인터만 추가한다.

### D3. 토큰과 비밀 보관

비밀 목록:

| 비밀 | 위치 | 용도 | 비고 |
|---|---|---|---|
| Claude OAuth access token | Keychain `Claude Code-credentials`, `~/.claude/.credentials.json` (Claude Code 소유) | usage 호출 | 수집기는 읽기만 한다 |
| Cloudflare API 토큰 | `~/Library/Application Support/zzik/cloudflare-api-token` (0600) | KV 쓰기 | 권한 Account / Workers KV Storage / Edit 하나, 대상 계정 하나, 만료 90일 |
| Worker 쪽 비밀 | 없음 | | `wrangler secret`을 쓰지 않는다 |

Claude 토큰 규칙:

- 수집기는 토큰을 갱신하지 않는다. refresh token은 읽지도 않는다. refresh token은 회전하므로 수집기가 갱신하면 Claude Code가 가진 값이 무효가 되어 실행 중인 세션이 로그아웃될 수 있다. 갱신은 Claude Code에 맡긴다.
- 자격 증명 선택: Keychain과 파일을 둘 다 읽어 `expiresAt`이 더 늦은 쪽을 쓴다. 한쪽을 읽지 못하면(Keychain 잠김 포함) 다른 쪽을 쓴다. 둘 다 못 읽으면 `no_credentials`다. 이것은 오류가 아니라 정상 상태 중 하나이고 종료 코드는 0이다.
- 만료 처리: 고른 토큰의 `expiresAt`이 이미 지났으면 호출하지 않고 `token_expired`로 기록한다. `expiresAt` 필드가 없으면 호출해 보고 401로 판정한다.
- 401/403: `auth_required`로 기록하고 D5의 게이트를 건다.
- 토큰과 Authorization 헤더는 로그, 로컬 상태, KV, 오류 메시지 어디에도 남기지 않는다.

갱신하지 않는 결정의 대가(추정):

- 이 Mac에서 Claude Code를 하루에 A시간 쓰고 토큰 수명이 T시간이면, 하루 중 `token_expired`인 시간은 대략 max(0, 24 − A − T)시간이다.
- T는 전제 7로 잰다. 가정값으로 계산하면 A = 10일 때 T = 8이면 하루 6시간(25%), T = 1이면 13시간(54%)이다.
- 이 공백은 이 Mac에서 Claude를 쓰지 않는 시간대에 생긴다. 그동안 값이 바뀌는 원인은 다른 기기나 claude.ai에서의 사용, 그리고 창 리셋 둘뿐이다. 리셋은 저장된 `resets_at`으로 화면이 알아서 표시한다(D4). 놓치는 것은 다른 기기 사용분이다.
- Mac이 잠든 시간에는 토큰과 무관하게 수집기가 돌지 않는다.
- 실측은 V15에서 한다. 공백이 불편한 수준이면 후속 과제(추론 호출 없이 갱신을 유도하는 수단 조사)의 우선순위를 올린다.

Cloudflare API 토큰 규칙:

- 위험을 그대로 적는다. 이 토큰은 계정의 모든 KV namespace를 읽고 쓰고 지울 수 있고, launchd가 5분마다 무인으로 쓴다. 이 Mac의 사용자 권한으로 도는 프로세스는 이 토큰을 읽을 수 있다. 토큰이 새면 (a) 계정의 다른 KV 값이 읽히고 (b) 대시보드에 거짓 값이 들어갈 수 있다.
- 보관은 0600 파일이다. Keychain은 쓰지 않는다.
  - Keychain 항목을 무인으로 읽으려면 `-T /usr/bin/security`로 `security`에 접근을 열어야 하는데, 그러면 같은 사용자의 어떤 프로세스든 `security find-generic-password -w`로 프롬프트 없이 읽는다. 0600 파일과 보호 수준이 같으면서 "Keychain이라 안전하다"는 인상만 남는다.
  - ACL을 실제 소비자에 묶으려면 Node에서 Keychain을 직접 읽는 네이티브 모듈이 필요하다. 의존성 없는 수집기라는 D2와 맞지 않는다.
  - 파일은 화면 잠금 상태와 무관하게 읽힌다. Keychain 잠김으로 KV 쓰기가 멈추는 경우가 없어진다.
  - 이 Mac에는 Claude 자격 증명 파일과 wrangler OAuth 설정이 이미 같은 방식(사용자 홈의 평문 파일)으로 있다. 새 보호 수준을 도입하지 않는다.
  - 잃는 것: Keychain은 저장 시 로그인 암호로 암호화되지만 파일은 디스크 암호화(FileVault)에만 의존하고 백업에 평문으로 들어간다. 그래서 `install.sh`가 FileVault 상태를 확인하고, `set-token.sh`가 토큰 파일을 Time Machine에서 제외한다(`tmutil addexclusion`).
- 수집기는 토큰 파일의 소유자와 권한을 확인하고, 0600보다 느슨하면 읽지 않고 `kv_token_insecure`로 끝낸다.
- 입력: `collector/set-token.sh`. 토큰을 화면에 보이지 않는 프롬프트로 받고, `GET /user/tokens/verify`로 활성 상태와 만료일을 확인한 뒤, 파일을 원자적으로 쓰고, 만료일을 `config.json`에 적는다. 출력은 상태와 만료일뿐이다. 사용자가 자기 터미널에서 직접 실행한다(토큰이 에이전트 대화와 셸 기록에 남지 않게).
- 만료: 토큰을 만들 때 만료일을 90일 뒤로 준다. 수집기는 `config.json`의 만료일을 봉투의 `kvTokenExpiresAt`에 실어 보낸다. 화면은 만료 14일 전부터 경고하고, 만료 뒤 수집이 끊기면 원인을 "API 토큰 만료"로 표시한다(D4).
- 교체 절차(만료 전 또는 유출 의심 시):
  1. 대시보드에서 해당 토큰을 Roll한다(이전 값은 즉시 무효). 만료일을 다시 90일 뒤로 준다.
  2. `collector/set-token.sh`를 실행해 새 값을 넣는다.
  3. `launchctl kickstart -k gui/$(id -u)/dev.qus0in.zzik.usage-collector`로 한 번 돌리고 로그에서 KV 결과가 성공인지 본다.
  - 1과 2 사이에 낀 실행은 KV 쓰기 실패로 끝나고 다음 실행이 복구한다.
  - 유출이 의심되면 Roll 대신 토큰을 삭제하고 새로 만들며, 계정 감사 로그에서 KV 접근을 확인한다.
- 폐기 절차: `collector/uninstall.sh` 실행, 대시보드에서 토큰 삭제, 토큰 파일 삭제.
- 이 위험을 수용하는 조건: 이 계정의 다른 KV namespace에 민감한 값이 없다(전제 8). 조건이 깨지면(지금 있거나 나중에 생기면) Alternatives의 "ingest + Access Service Token"으로 옮긴다. 그 방식은 비밀이 zzik의 ingest 하나에만 통한다.
- zzik 안에서의 피해 한도: Worker와 프론트는 KV 값을 신뢰하지 않는 입력으로 다룬다(D8의 형식 검사, 프론트의 디코더, React의 텍스트 렌더링). 위조된 값이 낼 수 있는 결과는 틀린 숫자 표시까지다.

### D4. 저장: KV 키 1개에 봉투 1건, stale은 봉투의 시각으로 판정

- KV namespace `zzik-usage`, 바인딩 `USAGE_KV`, 키 `usage:claude`. 이력은 저장하지 않는다.
- 수집기는 실행할 때마다(성공, 실패, 건너뜀 모두) 봉투를 한 번 쓴다. 5분 주기면 하루 288회다. 실패하거나 건너뛴 실행은 로컬 상태에 있는 마지막 성공 본문을 그대로 싣는다. KV에는 항상 "마지막으로 성공한 값 + 지금 상태"가 있다.

봉투 형식(`shared/usage-contract.ts`):

```jsonc
{
  "schema": 1,
  "provider": "claude",
  "status": "ok",              // ok | rate_limited | token_expired | auth_required | no_credentials | upstream_error | network_error
  "called": true,              // 이번 실행에서 upstream을 실제로 호출했는가
  "runAt": "2026-11-11T03:05:00.000Z",      // 마지막 수집기 실행 시각(하트비트)
  "fetchedAt": "2026-11-11T03:05:00.412Z",  // 마지막 성공 시각, 없으면 null
  "httpStatus": 200,           // 마지막으로 실제 호출했을 때의 상태 코드. 건너뛴 실행에서도 유지한다
  "retryAt": null,             // 다음 호출이 허용되는 시각(D5의 게이트와 같은 값), 게이트가 없으면 null
  "tokenExpiresAt": "2026-11-11T09:00:00.000Z",   // Claude 자격 증명의 expiresAt, 모르면 null
  "kvTokenExpiresAt": "2027-02-09T00:00:00.000Z", // Cloudflare API 토큰 만료일, 모르면 null
  "intervalSec": 300,
  "collectorVersion": "0.2.0",
  "rawText": "{\"five_hour\":{...}}",       // 마지막 성공 응답 본문 원문 그대로, 없으면 null
  "rawOmitted": null           // null | "too_large"
}
```

- `status`는 수집기가 본 상태다. Worker나 저장소의 문제는 봉투가 아니라 HTTP 오류로 나간다(D8).
- `rawText`는 응답 본문을 파싱하지 않은 문자열이다. KV를 지나는 동안 숫자 표기나 키 순서가 바뀌지 않는다.
- 본문이 64KB를 넘으면 성공으로 기록하되 본문은 싣지 않는다(`status: "ok"`, `rawText: null`, `rawOmitted: "too_large"`). 64KB는 KV 한도(25MiB)가 아니라 이 설계가 정한 값이다.

stale 판정(프론트 domain, 시각은 0.2.1의 `UsageClock` 포트):

| 조건 | 판정 | 화면 |
|---|---|---|
| 봉투 없음 | 데이터 없음 | 수집기가 아직 쓰지 않았다는 안내 |
| `now − runAt > 3 × intervalSec`이고 `now > kvTokenExpiresAt` | API 토큰 만료 | 교체 안내(U9) |
| `now − runAt > 3 × intervalSec` | 수집 중단 | Mac 절전 또는 수집기 종료 가능 |
| `status`가 `ok`가 아님 | 상태별 표시(D9 표) | |
| `now − fetchedAt > 3 × intervalSec` | 오래된 값 | "N분 전 값" 배지, 값은 그대로 |
| 그 밖 | 정상 | |

위에서부터 먼저 맞는 줄을 쓴다. 이와 별개로 값의 표시 수준을 `fetchedAt`의 나이로 정한다.

| `now − fetchedAt` | 값 표시 |
|---|---|
| 24시간 이하 | 그대로 |
| 24시간 초과 7일 이하 | 숫자와 막대를 흐리게, "N일 전 값"을 항상 표시 |
| 7일 초과 | 숫자와 막대를 숨기고 수집 상태만 표시. Raw 보기는 유지 |

- 항목별 리셋: `resets_at`이 지난 항목은 0.2.1 명세 C5~C7대로 "리셋 지남"으로 표시하고 전체 상태 집계에서 뺀다.
- `kvTokenExpiresAt`까지 14일 이하로 남으면 상태 줄에 "API 토큰 만료 N일 전"을 덧붙인다.
- KV는 최종 일관성이라 쓰기가 읽기에 반영되기까지 최대 1분쯤 걸릴 수 있다. 5분 주기에서는 문제 삼지 않는다.

### D5. 429 백오프와 호출 게이트

- 기본 주기 300초. 화면의 새로고침은 KV만 다시 읽으며 upstream 호출을 일으키지 않는다.
- 게이트는 로컬 상태의 `nextAllowedAt` 하나다. 이 시각이 지나지 않았으면 호출하지 않는다. 봉투의 `retryAt`은 이 값의 사본이다.
- n은 연속 실패 횟수(429, 5xx, 타임아웃)이고 성공하면 0이 된다.
- 429: 대기 = max(RA, min(600 × 2^(n−1), 3600))초.
  - RA는 Retry-After 해석값이다. 초와 HTTP-date 형식을 모두 읽고 [300, 86400] 범위로 자른다. 해석할 수 없거나 0, 음수, 과거 시각이면 없는 것으로 본다.
  - 상한 3,600초는 지수항에만 걸린다. 서버가 더 긴 대기를 지시하면 그대로 따른다.
  - base가 600초(주기의 2배)라서 첫 실패에도 최소 한 주기를 건너뛴다. Retry-After가 없을 때의 수열은 600, 1200, 2400, 3600, 3600이다.
- 5xx와 타임아웃: 대기 = min(600 × 2^(n−1), 900)초. `upstream_error`.
- 401/403: `nextAllowedAt`을 1시간 뒤로 두되, 자격 증명의 `expiresAt`이 바뀌면 즉시 해제한다. `auth_required`.
- `token_expired`, `no_credentials`: 시간 게이트 없이 매 실행마다 자격 증명을 다시 읽는다(호출은 하지 않으므로 upstream 부담이 없다). `retryAt`은 null이다.
- 네트워크 오류(오프라인, DNS): 게이트 없이 다음 주기에 재시도. `network_error`.

### D6. Worker 스크립트 도입: `/api/*`를 스크립트로 보낸다

`wrangler.jsonc` 설계값 (0.1 대비 `main`, `assets.binding`, `assets.run_worker_first`, `kv_namespaces`, `vars` 추가):

```jsonc
{
  "name": "zzik",
  "main": "worker/index.ts",
  "compatibility_date": "2026-11-11",
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api/*"]
  },
  "kv_namespaces": [{ "binding": "USAGE_KV", "id": "<kv-namespace-id>" }],
  "vars": {
    "ACCESS_TEAM_DOMAIN": "qus0in.cloudflareaccess.com",
    "ACCESS_AUD": "d83bb3725ec247352d8a87ea9be8fc43a4aea78d68821b927a479f622bf29b79",
    "ALLOWED_EMAIL": "qus0in@gmail.com"
  },
  "routes": [{ "pattern": "zzik.qus0in.dev", "custom_domain": true }],
  "workers_dev": false,
  "preview_urls": false
}
```

- `ACCESS_TEAM_DOMAIN`에는 스킴과 경로 없이 호스트만 넣는다. 코드가 `https://`를 붙인다. `://`나 `/`가 들어 있으면 설정 오류로 처리한다(D7, 테스트로 고정).
- 라우팅 사실관계:
  - `/api/*`는 자산 조회보다 먼저 Worker로 간다.
  - `dist`에 실제로 있는 파일은 Worker를 거치지 않는다.
  - 배열형은 자동 내비게이션 감지를 끈다. 그래서 자산에도 없고 패턴에도 안 맞는 경로(딥링크, 없는 `favicon.ico` 등)가 어떻게 처리되는지는 전제 5의 (a)/(b) 중 하나다.
  - `worker/ui/router.ts`는 `/api/`로 시작하지 않는 요청을 받으면 `env.ASSETS.fetch(request)`로 넘긴다. 이 코드는 (b)일 때만 실행된다. (a)로 관측되면 죽은 코드이지만 방어용으로 남기고 주석에 관측 결과를 적는다.
  - 어느 쪽이든 사용자가 보는 결과는 같다: 딥링크가 `index.html` 200.
- 비용: 존재하는 자산 파일 요청은 스크립트를 부르지 않는다. `/api/*`와, (b)인 경우 자산 미스 경로가 Worker 요청으로 집계된다. 1인 사용이라 Free 한도와는 거리가 멀다.
- 설정이 틀어졌을 때의 성질: 사용량 데이터는 Worker 코드의 인증(D7)을 지난 뒤에만 나온다. 자산 서빙 경로는 KV에 닿지 않는다. `run_worker_first`가 빠지거나 바뀌면 `/api/usage`가 SPA HTML을 주거나 Worker의 401을 줄 뿐이고, 데이터가 인증 없이 나가는 경로는 생기지 않는다.
- 빌드는 그대로 `vite build`(SPA)이고 Worker 번들은 `wrangler deploy`가 만든다. `@cloudflare/vite-plugin`은 넣지 않는다.
- 0.1의 운영 규칙(`wrangler deploy`만 사용, `versions upload` 금지)은 그대로다.

### D7. Access JWT 검증: `/api/*`에서 `jose`로 검증한다

- 0.1에서 미뤘던 방어 심층화를 여기서 채택한다. 스크립트가 생겼고, `/api/usage`가 이 앱에서 처음으로 보호할 가치가 있는 데이터를 반환하기 때문이다.
- `ctx.access`는 쓸 수 없다. static assets가 붙은 Worker에서는 라우터가 `ctx.access`를 넘기지 않아 항상 `undefined`다(Cloudflare Access for Workers 문서, 2026-11-02). 그래서 헤더의 JWT를 직접 검증한다. 같은 사유를 `worker/infra/access/jose-access-verifier.ts` 상단 주석에 남긴다.
- 검증 내용:
  1. `Cf-Access-Jwt-Assertion` 헤더가 있다(쿠키는 보지 않는다).
  2. `https://qus0in.cloudflareaccess.com/cdn-cgi/access/certs`의 JWKS로 서명이 맞다. 알고리즘은 `RS256`만 허용한다.
  3. `iss`가 `https://qus0in.cloudflareaccess.com`이고 `aud`에 `ACCESS_AUD`가 들어 있으며 만료되지 않았다(`clockTolerance` 60초).
  4. `email` 클레임이 `ALLOWED_EMAIL`과 같다.
- JWKS 처리:
  - `createRemoteJWKSet` 인스턴스를 모듈 스코프에 한 번 만들어 isolate가 사는 동안 재사용한다. 요청마다 만들지 않는다.
  - 캐시는 `jose` 기본값을 쓴다(캐시 수명 10분, 재조회 쿨다운 30초, 조회 타임아웃 5초). 키 회전 주기 6주와 유예 7일에 비해 충분히 짧다.
  - 모르는 `kid`가 오면 `jose`가 쿨다운 안에서 한 번 다시 받아 온다. 캐시를 강제로 비우는 경로는 만들지 않는다.
  - 키는 하드코딩하지 않는다.
- 실패 구분:
  - 헤더 없음, 서명 불일치, 맞는 키 없음, 클레임 불일치, 만료, 이메일 불일치 → 401 `unauthorized`.
  - JWKS를 받아 오지 못함(네트워크, 타임아웃) → 503 `jwks_unavailable`. 인증 실패로 분류하지 않는다. 프론트가 이것을 세션 만료로 오해해 로그인을 다시 시키지 않게 하기 위해서다.
  - `vars` 누락 또는 형식 오류 → 500 `misconfigured`. 닫힌 쪽으로 실패한다.
- `jose`는 `^6`으로 고정한다. WebCrypto만 쓰므로 `nodejs_compat` 플래그를 켜지 않는다(전제 11).
- Worker 코드에 개발용 우회 플래그를 두지 않는다.
- 정적 자산은 코드에서 검증하지 않는다. 번들에는 비밀이 없고, 자산 보호는 0.1의 Access가 맡는다. Worker destination이 없는 채로 진행하게 되면(U1의 편차) 자산 쪽 두 번째 겹은 0.1에 적힌 대로 설정 두 줄과 운영 규칙뿐이다.

### D8. API: `GET /api/usage` (통과형)

응답 200:

```jsonc
{ "snapshot": { /* D4의 봉투 그대로. 아직 수집된 적이 없으면 null */ } }
```

`/api/*` 요청의 판정 순서와 결과:

| 순서 | 상황 | 상태 | 본문 |
|---|---|---|---|
| 1 | 설정 누락/형식 오류 | 500 | `{ "error": "misconfigured" }` |
| 2 | JWKS 조회 실패 | 503 | `{ "error": "jwks_unavailable" }` |
| 2 | JWT 검증 실패 | 401 | `{ "error": "unauthorized" }` |
| 3 | `/api/usage`가 아닌 경로 | 404 | `{ "error": "not_found" }` |
| 4 | `/api/usage`에 GET 외 메서드 | 405 | `{ "error": "method_not_allowed" }` |
| 5 | KV 읽기 실패 | 503 | `{ "error": "storage_unavailable" }` |
| 5 | KV 값이 JSON 객체가 아니거나 `schema`가 없음 | 502 | `{ "error": "snapshot_corrupt" }` |
| 5 | 정상(스냅샷 없음 포함) | 200 | 위 형식 |

- 인증이 경로와 메서드보다 먼저다. 인증되지 않은 요청은 어떤 `/api/*` 경로든 401만 본다. 인증에 실패한 요청에서는 KV를 읽지 않는다.
- 이 표의 오류 코드는 Worker 쪽 상태다. 봉투의 `status`(수집기 쪽 상태)와 섞지 않는다.
- 모든 응답에 `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. CORS 헤더는 붙이지 않는다(동일 출처 전용).
- Worker는 봉투의 내용을 해석하거나 가공하지 않는다. upstream 스키마가 바뀌어도 Worker와 수집기는 손대지 않는다.

### D9. 화면: 0.2.1 화면에 실제 데이터와 수집 상태를 연결한다

화면 구성, 분류, 라벨, 단계(80%/100%), 정렬, 리셋 문구, 접근성은 0.2.1 명세(`docs/specs/0.2.1-usage-dashboard.md`의 C1~C13, U1~U12)와 그 구현이 기준이다. 0.2는 이를 다시 정하지 않고 아래만 더한다. 모두 0.2.1이 main에 병합된 뒤 그 위에 얹는 변경이다.

1. 게이트웨이 계약 확장 (`src/domain/usage/gateway.ts`). 성공 결과에 수집 정보와 원문을 더한다.

```ts

  | { ok: true; usage: RawUsage | null; collection: UsageCollectionMeta | null; rawText: string | null }
  | { ok: false; reason: UsageGatewayFailureReason; message: string | null }
```

3. 새 infra 모듈 `src/infra/usage/http-usage-gateway.ts`: `fetch`를 인자로 받아 `fetch('/api/usage', { redirect: 'manual' })`을 호출한다.
   - 200 → 본문을 `snapshot.ts`의 디코더에 넘긴다.
   - `opaqueredirect` → `session_expired`.
   - 401, 5xx(503 `jwks_unavailable` 포함) → `api_error`와 오류 코드.
   - fetch 예외 → `network_error`.
4. app 변경:
   - `load-usage.ts`: `buildUsageView(usage)`에 더해 `collection.ts`의 판정을 결과에 싣는다.
   - `useUsage.ts`: 상태에 `collection` 뷰를 추가한다. `lastSuccessAt`은 브라우저가 조회에 성공한 시각이 아니라 봉투의 `fetchedAt`으로 채운다. 기존 4상태(`loading`, `ready`, `stale`, `error`)는 유지하고 다음처럼 대응시킨다.

| 상황 | UI 상태 |

### D12. 테스트 전략 (TDD/BDD, vitest)

진행 방식은 `layered-tdd` 스킬 그대로다.

- 실패하는 테스트 → 최소 구현 → 리팩터. 레이어는 domain → app → ui/infra 순.
- 서술은 `describe('Given …')` / `it('When … Then …')`.
- `vi.mock`을 쓰지 않는다. 포트에 `tests/fakes/`의 가짜를 주입한다. 전역 `fetch`와 `Date`를 바꿔치기하지 않는다. 가짜 타이머는 폴러에만 쓴다(0.2.1은 `UsageScheduler` 가짜로 이미 대체했다).
- 기본 환경은 node, 프론트 ui 테스트만 jsdom이다. Worker 테스트는 Node 24의 `Request`/`Response`로 돌리고 workerd 풀은 쓰지 않는다.
- 완료 조건: `pnpm test`, `pnpm typecheck`, `pnpm build` 통과.

무엇을 단위 테스트하고 무엇을 가짜로 대체하는가:

## Alternatives

| 결정 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 수집 위치 | Worker가 OAuth 토큰을 secret으로 받아 직접 호출 | access token이 만료되므로 결국 Mac에서 주기적으로 secret을 갱신해 줘야 한다. 로컬 작업은 그대로 남으면서 구독 전체 권한을 가진 토큰이 클라우드에 복제된다. |
| 수집 위치 | Worker가 refresh token까지 받아 스스로 갱신 | refresh token 회전 때문에 Worker가 갱신하는 순간 이 Mac의 Claude Code 자격 증명이 무효가 된다. |
| 수집 위치 | biseo식 pull (Tailscale funnel 너머 로컬 서버를 Worker cron이 폴링) | Mac에 인바운드 공개 경로와 상주 서버, 서비스 간 인증이 필요하다. |
| 수집 위치 | 로컬에서 Worker의 ingest 엔드포인트로 HTTP push + Access Service Token | 비밀의 권한이 zzik의 ingest 하나로 좁아지는 것이 장점이다. 대신 Access에 Service Auth 정책을 추가해야 해서 0.1의 불변 조건이 바뀌고, Worker에 쓰기 엔드포인트와 KV 쓰기 권한, 신원 구분 로직이 생긴다. 계정의 다른 KV에 민감한 값이 없는 동안은 KV 직접 쓰기가 더 단순하다. D3의 수용 조건이 깨지면 이 방식으로 옮긴다. |
| 수집 위치 | ingest 경로를 Access Bypass로 열고 HMAC으로 보호 | 인터넷에 공개된 쓰기 엔드포인트가 생긴다. |
| 수집 위치 | biseo의 스냅샷 파일 재사용 | 가공된 값이라 raw가 아니고, biseo의 실행 여부와 내부 형식에 묶인다. |
| KV 쓰기 수단 | `wrangler kv key put` + 기존 OAuth 로그인 | 대화형 OAuth 세션에 데몬이 의존하게 되고, 그 로그인의 권한이 KV 전용 토큰보다 훨씬 넓다. |
| API 토큰 보관 | Keychain + `-T /usr/bin/security` (v1 설계) | 같은 사용자의 모든 프로세스가 프롬프트 없이 읽는다. 0600 파일과 보호 수준이 같고 잠금 상태에 따른 실패만 더한다(리뷰 H1). |
| API 토큰 보관 | Keychain, ACL 없이(접근마다 프롬프트) | 무인 실행이 불가능하다. |
| API 토큰 보관 | Keychain + 네이티브 모듈로 직접 읽어 ACL을 수집기에 묶기 | 유일하게 ACL이 의미를 갖는 방식이지만 네이티브 의존성과 코드 서명 문제가 따라온다. 의존성 없는 수집기와 맞지 않는다. |
| API 토큰 보관 | 토큰 만료 없이 사용 | 유출된 토큰이 무기한 유효하다. 90일 만료와 화면 경고로 교체를 강제한다. |
| API 토큰 범위 | 토큰에 클라이언트 IP 제한 | 노트북은 네트워크를 옮겨 다니고 가정용 IP는 바뀐다. 수집이 수시로 끊긴다. |
| 토큰 갱신 | 수집기가 만료 시 직접 refresh | 회전 충돌. Keychain과 파일 양쪽을 Claude Code와 같은 형식으로 되써야 하고 실행 중인 세션과 경합한다. |
| 저장 | D1 | 이력이 필요 없는 0.2에는 과하다. 추이 그래프를 만들 때 도입한다. |
| 저장 | 저장 없음(요청 시 실시간 조회) | pull 구조가 전제다. |
| 저장 | 변경이 있을 때만 KV에 쓰기 | 하트비트가 사라져 "값이 그대로인 것"과 "수집기가 죽은 것"을 구분할 수 없다. |
| 주기 | 60초 (biseo와 동일) | KV 쓰기가 하루 1,440회로 Free 한도를 넘고 429 가능성이 커진다. |
| 백오프 | 상한을 최종 대기값에 적용 (v1 설계) | Retry-After가 상한보다 길면 지시보다 일찍 재시도해 429를 반복한다(리뷰 M2). |
| JWT | `ctx.access` 사용 | static assets가 붙은 Worker에서는 라우터가 `ctx.access`를 넘기지 않아 항상 `undefined`다(리뷰 M4). 문서가 바뀌어 전달되기 시작하면 `jose` 제거를 다시 검토한다. |
| JWT | 검증하지 않고 Access만 신뢰 | 데이터 API는 Access 설정이 잘못 바뀌었을 때 바로 유출된다. Worker destination 여부가 미확인인 지금은 더 그렇다. |
| JWT | 모든 경로를 Worker 먼저 실행해 자산까지 검증 | 자산에는 비밀이 없다. 모든 자산 요청이 Worker 호출이 되고, 설정 실수 한 번에 UI 전체가 뜨지 않게 된다. |
| JWT | 로컬 개발용 우회 플래그 | 프로덕션에 켜질 수 있는 우회 스위치가 코드에 남는다. |
| JWT | 요청마다 JWKS 인스턴스 생성 (Cloudflare 예시 코드 방식) | 캐시가 없어 요청마다 JWKS를 받아 온다(리뷰 M3). |
| API | `serverTime`을 응답에 넣고 그 기준으로 stale 판정 (v1 설계) | 0.2.1이 카운트다운과 판정을 브라우저 시계 포트 하나로 구현했다. 기준을 둘로 나누면 30초마다의 재계산에 오프셋 관리가 필요해진다. 판정 기준이 분 단위(15분, 24시간)라 기기 시계 오차의 영향이 없다. |
| API 순서 | 인증 → 메서드 → 경로 (리뷰 L10 권고) | 405는 경로가 있을 때만 의미가 있다. 인증을 맨 앞에 둔다는 요점은 같다. |
| 정규화 위치 | Worker에서 창/지표로 가공해 반환 | upstream 스키마 변경에 Worker와 UI를 함께 고쳐야 한다. |
| 화면 | v1의 자체 분류·라벨·단계(70/90%) 규칙 | 0.2.1이 같은 일을 명세와 테스트까지 갖춰 구현했다. 규칙을 두 벌 두지 않는다. |
| 화면 | Raw를 `rawText` 원문으로만 표시 | 0.2.1의 U7 테스트가 `JSON.stringify(raw, null, 2)`를 고정했다. 원문은 파싱 실패 시의 폴백으로 쓴다. |
| 개발 환경 | vite dev 미들웨어로 `/api/usage` 흉내 (v1 설계) | 0.2.1의 fixture 게이트웨이가 같은 역할을 하고 `?fixture=`로 시나리오 전환까지 된다. |
| 개발 환경 | `@cloudflare/vite-plugin`으로 dev에서 Worker 실행 | dev에는 Access가 없어 JWT 문제가 그대로 남는다. |
| 구조 | `tests/web/…` (v1 설계), 평면 파일 `src/domain/usage-*.ts` (리뷰 M6-a) | main 규칙은 `tests/`가 `src/`를 미러링하는 것이고, 0.2.1 구현은 레이어 아래 `usage/` 폴더를 쓴다. 이미 있는 구조를 따른다. |
| 구조 | 봉투 타입을 `src/domain`에 두고 Worker가 가져다 쓰기 | Worker가 프론트 소스 트리에 의존하게 된다. |
| 수집기 런타임 | TypeScript(Node 타입 스트리핑), bun, 셸(curl + jq) | 빌드나 추가 런타임, 실험 기능 경고를 피한다. 타입 검사는 `checkJs`로 얻는다. |
| 스케줄러 | cron, 상주 데몬 | launchd가 절전 복귀 처리와 중복 실행 방지를 해 준다. |
| 라이브러리 | Hono, TanStack Query | 라우트 하나, 조회 하나에는 필요 없다. |
| 테스트 | `@cloudflare/vitest-pool-workers` | 로직이 포트 뒤에 있어 Node에서 전부 돌릴 수 있다. 자산 라우팅은 `wrangler dev` 확인(V5)이 어차피 필요하다. |
| 테스트 | 수집기 테스트를 `.test.mjs`로 작성 | vitest include를 바꿔야 하고 타입 검사 밖에 놓인다. `.test.ts`가 `.mjs`를 import하면 둘 다 해결된다. |
| 레이어 강제 | eslint 규칙이나 dependency-cruiser | 0.2.1이 넣은 vitest 구조 테스트를 넓히는 것으로 충분하다. |

## Consequences

긍정적:
- Claude OAuth 토큰이 Mac을 떠나지 않고, Worker에는 비밀이 없다.
- 0.2가 새로 요구하는 Access 변경과 공개 진입점이 없다.
- 사용량 데이터는 Worker의 JWT 검증을 지나야만 나온다. 라우팅 설정이 틀어져도 인증 없이 데이터가 나가는 경로가 없다.
- `/api/*`에 Access JWT 검증이 들어가 0.1의 후속 과제 하나가 해소된다. Worker destination이 없더라도 데이터 쪽은 코드로 막힌다.
- 0.2.1의 화면, 분류 규칙, 테스트를 그대로 쓴다. 프론트의 0.2 변경은 계약 확장과 수집 상태 표시뿐이다.
- 세 루트가 같은 레이어 규칙과 같은 테스트 방식을 쓴다. 외부 의존이 infra에만 있어 로직 전부를 네트워크 없이 테스트한다.
- 수집 실패, 토큰 만료, 수집기 중단, API 토큰 만료가 서로 다른 상태로 화면에 드러난다. 오래된 값은 24시간과 7일 기준으로 흐려지고 숨겨진다.

부정적 / 리스크:
- Cloudflare API 토큰이 계정의 모든 KV namespace를 읽고 쓰고 지울 수 있고, 평문 파일로 Mac에 상시 놓인다. 같은 사용자 권한의 프로세스가 읽을 수 있다. 완화는 90일 만료, 교체 절차, FileVault 확인, 백업 제외, 수용 조건(전제 8)이다.
- 이 Mac이 꺼져 있거나 잠자는 동안에는 갱신되지 않는다.
- 이 Mac에서 Claude Code를 쓰지 않는 동안 토큰이 만료되면 `token_expired`로 멈춘다. 하루 중 max(0, 24 − A − T)시간으로 추정되며 그동안 다른 기기의 사용량이 반영되지 않는다. 해소 수단은 사용자가 Claude Code를 실행하는 것뿐이다(U7).
- 문서화되지 않은 엔드포인트에 의존한다. 응답 형식이나 헤더 요구가 바뀌면 수집이 멈출 수 있다.
- 브라우저에서 "지금 수집"을 시킬 수 없다. 최신성은 최대 5분 + KV 전파 지연이다.
- stale 판정이 브라우저 시계에 의존한다. 기기 시계가 크게 틀리면 판정도 틀린다.
- 관리할 로컬 구성 요소가 생긴다(LaunchAgent, 토큰 파일, App Support 디렉터리). 90일마다 토큰 교체가 필요하고, node 경로가 바뀌면 재설치가 필요하다.
- 0.1의 Worker destination 여부가 아직 미확인이다. 0.2 배포가 U1에 걸려 있다.
- 프론트 작업(구간 B)은 0.2.1 병합을 기다려야 한다. 0.2.1의 게이트웨이 계약과 `useUsage` 상태를 고치므로 0.2.1의 테스트 일부(게이트웨이 결과 형태, `lastSuccessAt`의 의미)를 함께 고쳐야 한다.
- fixture 게이트웨이가 `tests/fixtures`를 `src/`에서 import한다. 프로덕션 번들에서 빠지는지는 빌드 결과로 확인해야 한다(V7).
- 0.1의 "assets-only, 스크립트 없음" 전제가 끝난다. `worker/` 코드와 `jose` 의존성이 추가된다.
- 조립 루트 세 곳, 셸 스크립트, wrangler 라우팅은 단위 테스트 밖이다. 배선 실수는 V5와 배포 후 검증에서만 잡힌다.
- team domain, AUD, 이메일이 `wrangler.jsonc`의 `vars`로 레포에 들어간다(비밀은 아니다).
- 이력이 없어 추이를 볼 수 없다.

후속 과제:
- D1에 시계열을 쌓아 추이 그래프 표시
- 토큰 만료 공백을 안전하게 줄이는 방법 조사(추론 호출 없이 Claude Code가 갱신하게 하는 수단이 있는지)
- 다른 프로바이더 추가(봉투의 `provider`, KV 키 `usage:<provider>`)
- 한도 임박 알림
- `package.json`의 `preview` 스크립트와 0.1 ADR의 불일치 정리

## Verification

판정 원칙은 0.1과 같다. 미인증 응답에 앱 데이터(`rawText`, `utilization`)가 한 번이라도 나오면 전체 실패다. 어떤 출력에도 토큰 값이 나오면 실패다.

### 단위 테스트와 타입 검사 (`pnpm test`, `pnpm typecheck`. 범위는 D12 표)

- V1. 프론트: 0.2.1의 기존 테스트가 계약 확장 뒤에도 통과한다. 디코더가 봉투 없음, 타입 오류, `schema` 불일치, `rawText` 파싱 실패를 예외 없이 처리한다. 수집 판정이 D4의 두 표와 경계값에서 맞는다. `useUsage`가 D9-4의 대응표대로 상태를 낸다. 게이트웨이가 `opaqueredirect`를 `session_expired`로, 503을 `api_error`로 돌려준다.
- V2. Worker: 정상 JWT는 통과하고, 헤더 없음 / 서명 불일치 / `aud` 불일치 / `iss` 불일치 / 만료 / RS256 외 알고리즘 / 다른 이메일은 401이다. 키 조회 예외는 503 `jwks_unavailable`이다. `vars`가 비거나 team domain에 스킴이 들어 있으면 500이다. D8 표의 모든 줄이 순서, 상태 코드, 본문, 공통 헤더까지 맞는다. 인증에 실패한 요청에서 저장소 가짜의 읽기 횟수가 0이다.
- V3. 수집기: Retry-After 7200초가 3600으로 잘리지 않는다. Retry-After가 없으면 600, 1200, 2400, 3600, 3600이다. 0, 음수, 과거 시각, 쓰레기 값은 없는 것으로 처리된다. 성공 시 초기화된다. 만료된 토큰이면 호출하지 않는다. 401 뒤에는 1시간 또는 `expiresAt` 변경까지 호출하지 않는다. `expiresAt`이 늦은 쪽 자격 증명이 선택된다. 실패 봉투가 이전 성공의 `rawText`, `fetchedAt`, `httpStatus`를 유지한다. 봉투와 로그에 입력 토큰이 없다. dry-run이 아닌 모든 경로에서 KV 기록기 가짜가 정확히 한 번 호출된다. 토큰 파일 권한이 0644면 읽지 않는다.
- V4. 구조와 타입: `tests/arch/layers.test.ts`가 세 루트에서 금지 방향 import와 루트 사이 import가 없음을 확인한다. 일부러 위반을 하나 넣어 실패하는 것을 한 번 본다. `pnpm typecheck`가 세 tsconfig 모두 통과한다. 수집기에서 봉투 필드 이름을 일부러 틀리게 쓰면 `tsconfig.collector.json` 검사가 실패하는 것을 한 번 본다.

### 로컬 통합

- V5. `pnpm run preview:worker`(build 후 `wrangler dev`):
  - 번들이 `nodejs_compat` 없이 만들어진다(전제 11).
  - 헤더 없는 `GET /api/usage`, `POST /api/usage`, `GET /api/nope`가 모두 401이고 본문에 데이터가 없다.
  - `/assets/<실제파일>.js`가 200이다.
  - `/`와 `/any/path`(헤더 없음, `Sec-Fetch-Mode: navigate` 있음 둘 다)가 `index.html`을 200으로 준다. 판정은 결과만 본다.
  - 관측 기록: `/any/path` 요청 때 Worker가 호출됐는지를 `wrangler dev` 로그로 보고 전제 5의 (a)/(b)를 ADR에 적는다. (a)면 `router.ts`의 위임 코드에 "실행되지 않음" 주석을 단다.
- V6. 수집기 dry-run:
  - 기본: status가 `ok`이고 출력에 키 목록과 본문 sha256만 있다. 출력에 `sk-ant-`나 `Bearer`가 없다. KV와 상태 파일이 바뀌지 않는다.
  - `--credentials-file tests/fixtures/credentials.expired.json --no-keychain`: status가 `token_expired`이고 `called`가 false다(네트워크 호출 없음).
  - `--credentials-file /nonexistent --no-keychain`: status가 `no_credentials`이고 종료 코드가 0이다.
  - (선택, 1회만) 만료되지 않은 가짜 토큰 파일: status가 `auth_required`다. 가짜 값으로 upstream을 한 번 호출하므로 반복하지 않는다.
  - `--credentials-file`을 `--dry-run` 없이 주면 거부한다.
- V7. UI:
  - `pnpm dev`에서 `?fixture=`의 기존 시나리오와 새 수집 상태 시나리오(`collector-down`, `token-expired`, `rate-limited`, `no-snapshot`, `long-stale`)가 D9-5 표대로 보인다.
  - 320px: 실제 브라우저(Chrome DevTools 기기 툴바, 너비 320)에서 페이지 가로 스크롤이 없다(`document.documentElement.scrollWidth <= 320`). jsdom으로는 확인할 수 없다.
  - `pnpm build` 뒤 `dist/`에 fixture 고유 문자열(`thirty_day`)이 없다.

### 수집기 설치 후

- V8. `launchctl print gui/$(id -u)/dev.qus0in.zzik.usage-collector`에서 마지막 종료 코드가 0이다. 5분 간격으로 로그에 줄이 늘어난다. 로그와 `usage-state.json`에 토큰 문자열이 없다. 토큰 파일을 포함해 파일 권한이 0600, 디렉터리가 0700이다. 화면을 잠근 채 한 주기를 넘긴 뒤 로그를 보고 잠금 중 동작(전제 2)을 기록한다.
- V9. KV 값 확인(`wrangler kv key get usage:claude --remote` 또는 대시보드): 봉투의 `status`가 `ok`이고 `runAt`이 5분 안쪽이며 `kvTokenExpiresAt`이 들어 있다. `rawText`의 키 목록이 같은 시점 `--dry-run`의 키 목록과 같다.

### 배포 후

- V10. 미인증 차단(쿠키 없는 curl): `https://zzik.qus0in.dev/api/usage`가 Access 로그인으로 가는 302이고 본문에 `rawText`나 `utilization`이 없다. 0.1의 V3~V6을 다시 수행해 모두 통과한다. 배포 출력에 `zzik.qus0in.dev` 외의 URL이 없다.

```bash
curl -s -D - -o /tmp/zzik-api.txt https://zzik.qus0in.dev/api/usage | grep -iE '^(HTTP/|location:)'
grep -qE 'rawText|utilization' /tmp/zzik-api.txt && echo "FAIL: data leaked" || echo "OK"
```

- V11. 인증 후 화면(브라우저, U6): `Hello Young-In`이 그대로 보인다. 상태 배지가 "정상"이고 마지막 수집 시각이 5분 안쪽이다. 창 2개와 모델별 항목이 보인다. Raw 보기의 최상위 키 수와 화면 항목 수(창 + 항목 + 기타)가 같다. DevTools Network에서 `/api/usage`가 200, `Cache-Control: no-store`다. 이 200이 곧 실제 JWKS 조회와 실값 `vars`(team domain, AUD)의 확인이다.
- V12. 대조: Raw 보기의 `five_hour.utilization`, `seven_day.utilization`이 같은 시각 Claude Code `/usage` 화면의 값과 수집 주기 오차 안에서 맞는다. `seven_day_fable` 등 응답에 있는 모델별 키가 모두 카드로 나온다.
- V13. stale 동작: `launchctl bootout`으로 수집기를 멈추고 15분 넘게 기다리면 "수집 중단" 배지가 나오고 마지막 값과 Raw 보기는 유지된다. 다시 `bootstrap`하면 다음 실행 뒤 "정상"으로 돌아온다.
- V14. 설정 대조와 기록:
  - Access 앱과 정책이 0.1 V9와 같다(Bypass와 Service Auth 0개). Worker destination이 있다. 없이 진행했다면 편차 기록이 ADR에 있다.
  - Worker에 secret이 없다(`wrangler secret list`가 비어 있음).
  - Cloudflare API 토큰 요약 화면의 권한 항목, 대상 계정, 만료일을 ADR 구현 기록에 글로 옮겨 적는다. 권한이 Workers KV Storage Edit 하나가 아니면 실패다.
  - 계정의 KV namespace 목록과 민감 값 유무(전제 8)를 적는다.
- V15. 며칠 관측: 로그에서 `status` 분포와 `token_refreshed` 간격을 세어 T와 A를 구하고, D3의 추정식과 비교해 ADR에 기록한다. `rate_limited`가 잦으면 주기를 늘리고, `token_expired` 비율이 불편한 수준이면 후속 과제의 우선순위를 올린다.
- V16. 교체 리허설(1회): D3의 교체 절차를 실제로 한 번 수행한다. Roll 직후의 실행이 KV 쓰기 실패로 기록되고, `set-token.sh` 뒤의 실행이 성공하며, 화면이 "정상"으로 돌아온다. 이전 토큰 값으로 `tokens/verify`가 실패한다.

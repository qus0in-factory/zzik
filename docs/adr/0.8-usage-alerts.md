# ADR 0.8 — 수집 주기의 사용량 변화 알림 (#63)

상태: 구현. 운영 반영·수집기 재시작은 별도 승인 뒤 진행한다.

## 판정과 저장

- `collector/domain/usage/alert-report.mjs`가 `shared/usage-scan`으로 성공한 원문에서 모든 창·metric을 읽는다. 원문·자격 증명은 이벤트에 넣지 않는다. 실패·게이트 건너뜀·판독 실패는 회복으로 보지 않고 이전 알림 상태를 보존한다. 누락된 창도 자동 정상 해제로 해석하지 않는다.
- 대시보드의 `barLevelOf`·`getUsageStatus`·`elapsedPercent` 및 요약 창 선택을 `shared/usage-policy.ts`로 옮겨 화면과 수집기가 같은 함수를 사용한다. 주의는 기간 경과율보다 빠른 사용(주기를 모르면 70% 이상), 위험은 90% 이상, 한도 도달은 100% 이상이다. 0%와 여유는 정상이다. 기존 화면의 판정과 공개 시그니처는 유지한다.
- app의 순수 `diffAlerts(prevState, nextReport)`가 진입·악화·정상 해제·리셋 이벤트를 만든다. 시계는 report.nowMs로 주입한다. `nextAlertState`는 마지막 관측 값·레벨 및 마지막 알림 시도 레벨·시각을 만든다.
- 최상위 주기 한도는 요약 칩과 같이 월간(28~31일)이 있으면 월간, 없으면 주간, 동률이면 사용률이 높은 창이다. Claude scoped metric은 요약 창에서 제외하고 Antigravity는 Gemini 창만 선택한다. 선택한 이전 창의 리셋 시각이 지났고 사용률이 양수에서 정확히 0%로 내려가면 리셋을 보고한다. 같은 주기의 최고 사용 창이 바뀌어도 이전 선택 창의 리셋을 놓치지 않는다. 리셋 이벤트가 정상 해제도 함께 설명해 같은 해제를 두 번 알리지 않는다.
- 만료된 양수는 재진입·회복으로 보지 않는다. 만료된 0%는 실제 리셋 판정에 사용한다. 리셋 이전의 0%, 단순 감소, 5시간 등 최상위 주기가 아닌 창은 리셋 알림을 만들지 않는다(일반 상태 변화는 대상).
- 첫 성공 판독은 현재 상태를 기준선으로만 저장한다. 이후 새 창은 정상에서 시작한 것으로 비교한다. 재시작 시 기존 `usage-state.<provider>.json`의 `alerts`(version=1)를 읽는다. 없는/손상된 알림 상태는 첫 기준선을 다시 만든다. 기존 previous·인증 게이트와 함께 저장하며 추가 상태 파일은 없다.
- 같은 창의 알림 후 30분 이내 진입·해제 반복은 억제한다. 정상 해제가 계속되면 30분 뒤 한 번 보고한다. 이미 보고한 주의→위험→한도 도달의 악화는 즉시 보고한다. 억제 시 관측 상태는 갱신하되 마지막 알림 시도 레벨을 유지해 지속되는 변화를 놓치지 않는다.

## 전송과 실패 경계

- 제공자별 성공 저장 뒤 기준선을 체크포인트하고 `runCycle`이 모든 제공자의 이벤트를 한 메시지로 묶어 infra Discord 포트에 전달한다. DB 저장에 실패하면 알림 기준선을 진전시키거나 이벤트를 전송하지 않는다. 상태 파일 저장 실패도 전송 전 실행을 중단한다.
- `.env`의 선택값 `DISCORD_WEBHOOK_URL`을 조립 루트가 주입한다. 없으면 전송 없이 건수만 로그에 남긴다. 웹훅 기본 이름 `피짱`을 쓰며 payload의 `username`은 생략한다. 본문은 제공자·한도 라벨·이전→현재 레벨·사용률/기간 경과 예상·리셋 남은 시간·대시보드 링크다. 멘션은 차단한다. Discord 한 메시지 길이를 넘으면 나머지 건수와 대시보드 확인 안내로 줄인다.
- HTTP timeout은 5초, redirect는 따라가지 않고 재시도하지 않는다. 예외·비정상 HTTP·로깅 실패가 수집 주기를 실패시키지 않는다. 웹훅 URL·응답/오류 원문은 로그에 넣지 않는다.
- **중복 방지를 우선한 한 번의 전송 시도**다. 전송 전 체크포인트하므로 성공 직후 재시작해도 반복하지 않는다. 반대로 체크포인트 직후 중단되거나 전송에 실패하면 해당 이벤트는 재전송하지 않는다. Discord 전달 보장/영속 outbox는 이번 범위 밖이다. 운영 로그의 `alerts=failed`를 확인해야 한다.
- dry-run은 DB·상태·운영 로그 파일을 쓰거나 웹훅을 호출하지 않는다. 표준 출력에 값·라벨·리셋 시각을 가린 이벤트 미리보기만 남긴다.

## 검증

기존 실데이터 기반 6제공자 픽스처와 카드/요약 parity, 진입·해제·악화·리셋·첫 기준선·재시작·플래핑, 저장/수집/전송 실패, 웹훅 미설정, 한 주기 일괄 전송, 실제 5초 abort 및 dry-run을 가짜 포트로 검증한다. 테스트에서 실제 웹훅·agy·운영 수집기는 실행하지 않는다.

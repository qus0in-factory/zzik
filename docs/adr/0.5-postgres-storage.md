# ADR 0.5: Neon PostgreSQL + drizzle 저장소 전환

상태: P1/P2 구현 완료, 운영 전환 관측 대기. 운영 재시작·배포·Worker secret 주입은 별도 승인 후 진행. G0은 공식 문서·DB 대조 완료, 프로젝트 API 설정 세부 확인/월 CU-h 관측은 후속(아래 기록 참조).

# 설계안 A: 저장소 전환 — Cloudflare KV → PostgreSQL(Neon 프리티어, drizzle) (ADR 0.5 골자)

- 입력: 0.4/antigravity 워크트리의 `collector/`(run-once·run-cycle·wrangler-kv-writer·ports), `worker/`(store 포트·KvSnapshotStore·usage-route·stored-snapshot), `shared/usage-contract.ts`, `wrangler.jsonc`, `ecosystem.config.cjs`, ADR 0.2/0.3/0.4. `.env`는 존재만 확인(값·키 목록을 읽지 않음).
- 사용자 결정(고정): 연결 문자열은 `.env`의 `DB_URL`; ORM drizzle; **Worker→Postgres는 직접 TCP 드라이버**(Hyperdrive·HTTP 프록시 없음); DB는 **Neon Free**; 1인 사용이라 비밀 주입은 단순하게.
- 원칙: **봉투 계약(schema 1, `UsageEnvelope`)과 Worker 응답(`{ snapshot }`)은 바꾸지 않는다.** 바뀌는 것은 infra 어댑터 둘(수집기 쓰기·Worker 읽기)과 조립 루트·운영 설정. 프론트 `src/`는 주기 상수 외 변경 없음.
- Neon Free 수치는 Neon 요금 문서(2025 개정) 기준으로 적었다: 월 100 CU-시간, 최소 컴퓨트 0.25 CU, 5분 무활동 시 scale-to-zero(Free는 고정), 프로젝트 저장 0.5 GB, 직접 엔드포인트 max_connections ≈ 112(0.25 CU), 풀러(`-pooler`) 엔드포인트 PgBouncer 트랜잭션 모드 최대 10,000 클라이언트, 콜드스타트 통상 0.5~1초. **구현 전 콘솔에서 재확인(G0)** — 숫자가 다르면 3절 표만 다시 계산한다.

## 2. 스키마 (`shared/db/schema.ts`, drizzle `pgTable`)

```
usage_snapshot                       -- 제공자별 최신 봉투. Worker가 읽는 유일한 표
  provider           text PK          -- USAGE_PROVIDERS 값(목록 정본은 코드, CHECK 없음)
  envelope           jsonb NOT NULL   -- UsageEnvelope 통째(rawText는 문자열 그대로). 정본
  status             text NOT NULL    -- envelope.status 사본(운영 질의용)
  run_at             timestamptz NOT NULL
  fetched_at         timestamptz NULL
  raw_sha256         text NULL        -- rawText sha256. 이력 변경 판정용
  collector_version  text NOT NULL
  updated_at         timestamptz NOT NULL DEFAULT now()

usage_event                          -- (status, raw_sha256) 변경 또는 6시간 하트비트에 1행
                                     -- → ADR 0.7에서 변경됨
  id          bigint GENERATED ALWAYS AS IDENTITY PK
  provider    text NOT NULL
  run_at      timestamptz NOT NULL
  status      text NOT NULL
  raw_sha256  text NULL
  envelope    jsonb NOT NULL
  INDEX usage_event_provider_run_at (provider, run_at DESC)
```

- "변경" 판정은 수집기 domain 순수 함수 `collector/domain/usage/snapshot-change.mjs`가 **로컬 상태 파일의 previous**와 비교한다(DB 읽기 없음, 쓰기 경로 단방향). **#70:** 값이 같아도 상태 파일의 `lastEventAt`이 없거나 6시간 이상 지났으면 이벤트 1건을 쌓는다. 추가 SELECT 없이 `changed || heartbeat`로 판정하고 트랜잭션 저장 성공 후에만 `lastEventAt`을 진전한다. 기존 상태의 필드 누락·잘못된 시각은 보수적으로 첫 이벤트를 기록한다(기존 DB 행 유무는 조회하지 않으므로 이행 시 1건이 더 생길 수 있음). 30일 보존·하루 1회 정리는 그대로다. 정상 하트비트는 기존 ok 표본과 같아 동일 사용률의 평평한 선이 된다.
- `envelope.rawText`는 펼치지 않고 문자열로 둔다 → `rawRedacted`·`rawOmitted` 의미와 Worker 응답 바이트가 지금과 같다.
- `shared/usage-contract.ts`의 `USAGE_KV_KEYS`는 P3에서 삭제. 그 전까지 유지.

## 3. Neon Free 한도 안에 들어오는 수치

### 3.1 컴퓨트 시간 — 수집 주기 결정

Neon Free는 5분 무활동 뒤 멈추고(고정), 어떤 쿼리든 들어오면 깨어 다시 5분을 센다. 수집기가 주기 T마다 한 번 쓰면 한 주기 중 깨어 있는 시간 ≈ 5분 + 기동 수 초. 월 소비 ≈ 0.25 CU × 720h × (5.1분 / T).

| 주기 T | 월 CU-시간(수집기만) | 판정 |
|---|---|---|
| 300초(현행) | 항상 깨어 있음 → 180 | **한도 초과**(100). 월 중순에 컴퓨트 정지 → 대시보드 다운 |
| 600초 | 92 | 위험(조회 포함 시 100 근접) |
| **900초** | **61** | **채택.** 조회(아래) 더해도 70 미만, 여유 30% |
| 1200초 | 46 | 후보. 15분 지연이 불편하면 역방향으로 조정하지 않고, 한도 압박 시 이쪽으로 |

- 결정: `ZZIK_INTERVAL_SEC=900`(ecosystem), `shared/usage-contract.ts`·`run-once.mjs`의 기본 `USAGE_INTERVAL_SEC`도 900으로. 봉투 `intervalSec`가 900으로 나가므로 프론트 `collector_down`/`stale` 판정(3×interval=45분)은 코드 변경 없이 따라간다. 5시간 창 기준 지연 15분(5%)은 용인.
- 대시보드 조회: 컴퓨트가 자고 있을 때 열면 5.1분 깨움 = 0.021 CU-h/회. 월 200회여도 4 CU-h. 깨어 있는 창(수집 직후 5분)에 열면 0.
- 수집기 연결은 주기 끝에 닫는다(`idle_timeout: 5`). 열어둔 연결이 Neon의 "활동"으로 잡혀 영구 각성시키는 일을 막는다.
- "변경 시에만 쓰기"는 **채택 안 함**: 쓰기 횟수는 더 이상 비용이 아니고, 불규칙한 쓰기는 각성 횟수만 늘린다. 한 주기의 6제공자 쓰기는 같은 연결로 연속 실행(각성 1회).

### 3.2 저장 용량 0.5 GB — 이력 보존 30일

- `usage_snapshot`: 6행 × ≤ 64 KB = 무시.
- `usage_event` 최악(매 주기 변경): 96회/일 × 6제공자 × 평균 8 KB(claude 원문이 가장 큼) ≈ 4.6 MB/일 → 30일 ≈ 140 MB. 인덱스·TOAST·Neon PITR 이력(Free 6시간)을 더해도 0.5 GB 안. 보존을 90일로 하면 420 MB로 한도 근접 → **30일**.
- 정리: 수집기가 주기 끝에 `DELETE FROM usage_event WHERE run_at < now() - interval '30 days'`를 **하루 1회**(상태 파일 `lastPruneAt`로 판정, 자정 아님 — 마지막 정리 24시간 뒤 첫 주기) 같은 연결에서 실행. 별도 cron·pg_cron 없음. `ZZIK_EVENT_RETENTION_DAYS`(기본 30)로 조정.

### 3.3 연결 수

- Worker: 요청당 1연결, 열고 닫음. 대시보드 1회 로드 = 제공자 수만큼 병렬 요청(0.6 뒤 6) → 동시 6연결. 직접 엔드포인트 한도 112 안이지만, 짧은 연결의 정석은 풀러이므로 **Worker secret `DB_URL`은 Neon의 `-pooler` 호스트 문자열을 권장**(U2). 풀러(PgBouncer 트랜잭션 모드) 호환을 위해 `prepare: false`. 직접 엔드포인트 문자열을 넣어도 동작한다(단일 쿼리라 차이 없음).
- 수집기: `max: 1`, 직접 엔드포인트(`.env`의 `DB_URL` 그대로). 풀러여도 동작.
- 합계 최대 ≈ 7 동시 연결.

### 3.4 콜드스타트와 화면

- 자고 있을 때 첫 요청: 기동 0.5~1초 + TLS/인증 ≈ 1~2초 뒤 응답. 6개 병렬 요청이 모두 같은 기동을 기다리므로 섹션 6개가 거의 동시에 채워진다. 프론트는 이미 로딩 상태를 그린다 → 변경 없음.
- Worker `connect_timeout: 10`(기동 지연 흡수). 초과 시 기존 503 `storage_unavailable` → 프론트 기존 오류 처리·재시도.
- 콜드스타트를 숨기려고 Worker cron이나 keep-alive를 두지 않는다(컴퓨트 시간을 태운다).

## 4. 수집기 쓰기 경로 (Node 22+, PM2)

- 포트 개명: `CollectorPorts.kv` → `CollectorPorts.store`: `{ write(envelopeJson, meta) }`, `meta = { provider, status, runAt, fetchedAt, rawSha256, collectorVersion, changed, heartbeat }`. run-once가 채운다(sha256은 `envelope.mjs`에 있음, 변경 판정은 `snapshot-change.mjs`). 반환형 이름 `StoreWriteResult`. 로그 필드 `kvOk/kvReason`은 **이번엔 이름 유지**(운영 스킬 grep 호환, 부채로 기록).
- 어댑터 `collector/infra/usage/postgres-envelope-writer.mjs`: `execute(text, params)` 함수 주입(드라이버 중립). 운영은 postgres.js `sql.unsafe`, 테스트는 PGlite `query`. SQL: `BEGIN; INSERT … usage_snapshot … ON CONFLICT (provider) DO UPDATE …; [changed OR heartbeat] INSERT … usage_event …; COMMIT;`. 실패는 `{ ok:false, message }`(예외 없음), 쿼리 타임아웃 10초. `message`에는 `error.code`·`error.name`만(postgres.js 오류 문구에 호스트가 섞일 수 있음).
- 정리 `prune(retentionDays)`는 같은 어댑터의 두 번째 메서드. run-cycle 끝에서 `shouldPrune(lastPruneAt, now)`(순수)가 참일 때만 호출, 결과는 로그 한 줄(`status: 'prune'`, 삭제 행 수). 실패해도 주기 종료 코드에 영향 없음.
- 연결: 조립 루트가 `postgres(process.env.DB_URL, { max: 1, idle_timeout: 5, connect_timeout: 10, prepare: false })` 하나를 프로세스 수명 동안 보유. postgres.js가 유휴 5초 뒤 닫고 다음 주기에 다시 연다.
- `createFanoutWriter(writers)`(P1 전용): 순서대로 실행, 모두 ok면 ok, 아니면 메시지 합침.
- 조립(`main.mjs`): `ZZIK_STORE=postgres|kv|both`(P1 기본 `both`, P3에서 플래그·kv 분기 삭제). `DB_URL` 없는데 postgres 필요 → 종료 78. PM2 `ecosystem.config.cjs`: `node_args: ['--env-file=' + path.join(__dirname, '..', '.env')]`, `ZZIK_INTERVAL_SEC: '900'`.
- 주기 예산 240초 유지(DB 쓰기는 wrangler보다 훨씬 짧음).

## 5. Worker 읽기 경로

- `wrangler.jsonc`: `compatibility_flags: ["nodejs_compat"]`(postgres.js가 `node:net`/`node:tls` 사용). Hyperdrive 없음. `kv_namespaces`는 P3에서 삭제.
- `Env`: `DB_URL?: string`(secret). `worker/infra/usage/db.ts`: `createDb(env)` → `DB_URL` 없으면 null. `worker/index.ts`: `fetch(request, env, ctx)`로 확장, 요청마다 `postgres(url, { max: 1, prepare: false, connect_timeout: 10 })` → `drizzle(sql)` → 라우터에 store 주입 → `ctx.waitUntil(sql.end({ timeout: 1 }))`.
- `worker/infra/usage/postgres-snapshot-store.ts`가 기존 `SnapshotStore` 구현: `db.select({ value: sql<string>\`${snapshot.envelope}::text\` }).from(snapshot).where(eq(snapshot.provider, provider)).limit(1)` → `{ ok:true, value: string|null }`; 예외·store null → `storage_unavailable`(503, 라우트 매핑 기존). `stored-snapshot.ts`(provider 일치 검사)·`usage-route.ts`·프론트 변경 없음.
- 미채택: Hyperdrive(사용자 결정), `@neondatabase/serverless` HTTP 드라이버(호스트 종속·drizzle 드라이버 분기), Worker 전역 연결 재사용(격리체 수명 불확실), Worker에서 쓰기.

## 6. 마이그레이션·도구

- 의존성: `drizzle-orm`, `postgres`(deps); `drizzle-kit`, `@electric-sql/pglite`(devDeps). 네이티브 빌드 없음(`pg`·`better-sqlite3` 미채택).
- `drizzle.config.ts`: `schema: './shared/db/schema.ts'`, `out: './drizzle'`, `dialect: 'postgresql'`, `dbCredentials: { url: process.env.DB_URL! }`.
- 스크립트: `db:generate` = `drizzle-kit generate`; `db:migrate` = `node --env-file=.env node_modules/drizzle-kit/bin.cjs migrate`(dotenv 패키지 없음). 사람이 이 Mac에서 실행(U1). Worker·수집기는 마이그레이션을 실행하지 않는다.
- `drizzle/`(SQL+meta) 커밋. 변경은 generate → 커밋 → migrate 순.

## 7. 레이어 규칙

- Worker: `domain/usage/store.ts` 포트 불변. infra에 `db.ts`·`postgres-snapshot-store.ts` 추가, `kv-snapshot-store.ts`는 P3 삭제. `index.ts`만 어댑터 교체.
- 수집기: `domain/usage/ports.mjs` 개명 + `snapshot-change.mjs`·`prune-schedule.mjs`(import 없음). infra `postgres-envelope-writer.mjs`·`fanout-writer.mjs`. app(run-once·run-cycle)은 meta 전달·정리 호출만.
- `shared/db/schema.ts`는 수집기(쓰기)↔Worker(읽기) 계약. `src/**`는 `shared/db`를 import하지 않는다(테스트로 금지).
- 드라이버 객체는 조립 루트에서만 생성. infra는 주입된 `execute`/`db`만 쓴다.

## 8. 전환·롤백

| 단계 | 수집기 | Worker | 롤백 |
|---|---|---|---|
| P0 | deps·스키마·`drizzle/`·`pnpm db:migrate`(U1) | — | 표 drop |
| P1 이중 쓰기(24~48h) | `ZZIK_STORE=both`, 주기 900, PM2 `restart --update-env` | KV 읽기 그대로 | 수집기 이전 커밋 재시작 |

## P2 사전 대조에서 발견한 JSONB 인코딩 수정 (2026-11-13)

- 실제 postgres.js `unsafe(text, params)`는 이미 JSON 문자열인 봉투를 `$2::jsonb`에 전달하면 JSONB 타입 추론에 따라 다시 직렬화한다. PGlite 주입 테스트에서는 재현되지 않았고, 운영 사전 대조에서 snapshot 6개의 `jsonb_typeof(envelope)='string'`을 확인해 Worker 배포를 중단했다.
- snapshot과 event 모두 `::text::jsonb`로 전달해 드라이버는 텍스트를 보내고 PostgreSQL이 JSON 객체로 파싱하게 한다. 실제 postgres.js 회귀 테스트는 `zzik_test_*` 임시 스키마에 마이그레이션을 적용하고 INSERT/UPSERT, 두 테이블의 object 타입, Worker store→parseStoredSnapshot→decodeUsageSnapshot을 확인한 뒤 스키마를 삭제한다. `DB_URL`이 없으면 skip하며, 명시적으로 환경을 주입한 실행에서만 Neon에 접근한다. 원문 운영 봉투는 사용하지 않는다.
- Worker는 JSON 문자열 봉투를 계속 `snapshot_corrupt`로 거부한다. 자동 이중 파싱으로 저장소 오류를 숨기지 않는다. 리뷰 통과 후 release 반영·수집기 재시작, 손상 event 삭제 및 다음 주기 snapshot upsert로 복구하고 6개 모두 object임을 확인한 뒤 P2를 재개한다. 이 수정 커밋에서는 운영 데이터·프로세스·배포를 변경하지 않는다.

## #37 Workers 인증 연결 및 오류 안내 수정 (2026-11-13)

- 운영 인증 화면에서 6개 API가 모두 네트워크 오류로 표시됐다. 준비가 확인된 tail에서는 요청 6개의 Canceled outcome을 관측했으나 TCP 예외/HTTP 503을 직접 관측한 것은 아니다. 기존 프론트는 ky의 10초 TimeoutError까지 network_error로 분류했다.
- 같은 로컬 풀러 URL(sslmode=require, channel_binding=require)은 Node postgres.js에서 약 1.2초에 SELECT 1이 성공했다. postgres.js 4.1.1의 workerd 소켓은 peer certificate를 제공하지 않아 SCRAM-PLUS 강제와 호환되지 않는다. 실제 workerd에서 기존 Worker→6개 snapshot→decode 경로는 약 12.4초 후 전부 503/디코딩 실패로 재현됐다. 별도 최소 재현에서도 require는 CONNECTION_CLOSED, prefer는 약 1.6초에 성공했다. 운영 secret 값은 읽을 수 없으므로 로컬 URL과 동일함을 주장하지 않는다.
- Worker DB factory에서 channel_binding=prefer를 명시해 사용 가능한 경우 PLUS를 쓰고, Workers에서는 TLS 위의 일반 SCRAM으로 인증하게 한다. URL의 TLS 설정과 인증서 검증은 끄지 않고 URL도 그대로 전달한다. Node 수집기의 require 설정은 변경하지 않는다. 이는 채널 바인딩 강제를 Worker에 한해 완화하는 선택이며 직접 TCP·풀러·prepare:false·요청당 max1을 유지한다. 연결 제한은 브라우저 10초보다 짧은 5초로 조정한다.
- ky TimeoutError는 api_error/request_timeout으로 분리해 '응답 시간이 초과되었습니다'로 안내한다. 실제 fetch 실패는 기존 network_error이며 저장소 503은 기존 storage_unavailable 안내다. 수집기 오류와 브라우저 네트워크 오류를 혼동하지 않는다. 6개 제공자의 기본 안내는 '수집기가 15분마다 자동으로 갱신합니다'로 바꾸고 Ollama 수집 오류는 수집기 Mac 연결을 확인하도록 안내한다.
- tests/worker/infra/usage/db.workerd.test.ts는 DB_URL이 명시적으로 주어진 경우에만 실제 workerd에서 생산 Worker·Postgres 어댑터·디코더로 6개 snapshot을 읽는다. 로컬 테스트의 인증 포트만 가짜로 주입하며 이 인증 구성은 배포하지 않는다. DB 쓰기·마이그레이션·외부 제공자 수집 호출은 없고 반환/단언은 제공자명·HTTP 상태·디코딩 boolean뿐이다. 원문 봉투·DB_URL은 메모리에만 둔다. Miniflare/esbuild는 기존 전이 의존성과 같은 버전을 개발 의존성으로 명시한다.
- 수정 후 같은 workerd 회귀 테스트에서 6개 모두 200·decode 성공, 전체 약 1.6초를 확인했다. 운영 배포·인증 화면 재검증은 리뷰/병합 후 수행해야 한다. 이 작업 브랜치에서는 dev 병합·push·배포·secret 변경·PM2 재시작을 하지 않는다.

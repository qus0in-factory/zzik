## 3. 사건

### 사건 1. ship이 deploy-verify에 `--release`를 넘기지 않음
- **현상**: `scripts/ship.mjs`로 릴리스한 뒤 배포 검증 단계가 실패했다.
- **원인**: ship이 `deploy-verify.mjs --deploy`만 호출하고 `--release <경로>`를 넘기지 않았다. ship 작성 시 단계 순서와 변경 범위 판정에 집중했고, deploy-verify의 필수 인자 대조가 빠졌다. 테스트가 계획 문자열 위주였다(추정).
- **조치**: deploy-verify 호출에 `--release`를 전달하도록 고쳤다(`ba7be81`, Refs #106). 최초 구현은 `2cf9bd2`, 테스트는 `76bdbf0`, 보고는 `/tmp/hyd-ship.md`다.
- **재발 방지**: 현재 `scripts/ship.mjs`의 배포 단계 계획에 `--release` 인자가 포함돼 있다. 테스트가 `--release` 전달을 고정한다(`tests/scripts/ship.test.ts:145`). 자식 스크립트를 부르는 래퍼는 자식의 필수 인자를 테스트로 고정한다.

### 사건 2. release-prep의 ci_wait가 PR 체크 등록 전에 실행됨
- **현상**: PR을 만든 직후 CI 대기 단계가 실행되어 체크가 아직 없는 상태를 통과나 실패로 잘못 판단했다.
- **원인**: PR 생성과 GitHub 체크 등록 사이에 지연이 있는데, 대기 단계가 체크 존재를 전제했다.
- **조치**: CI 대기 전에 체크 등록을 기다리는 단계를 추가했다(`a14fe80`, Refs #106, `scripts/release-prep.mjs`·`tests/scripts/release-prep.test.ts`).
- **재발 방지**: 외부 상태를 폴링하는 단계는 "대상이 존재하는가"를 먼저 확인한다. 이 규칙은 코드에만 반영돼 있고 문서화는 하지 않았다.

### 사건 3. 한글 띄어쓰기 검사가 같은 기준(dev 대 dev)으로 비교해 변경을 못 잡음
- **현상**: 릴리스 중 띄어쓰기 검사가 변경 파일을 찾지 못하고 통과했다.
- **원인**: 검사 스크립트의 기본 기준이 `dev`다. 릴리스는 `dev`에서 실행되므로 `dev...HEAD` 차이가 비어 있었다.
- **조치**: 릴리스 단계에서 `--base origin/main`을 넘기게 했다(`ec8d65f`, `702367c`, Refs #106). 릴리스 준비 스크립트에서 `check_hangul_spacing` 단계가 `--base origin/main`을 쓴다. 같은 시기에 PG 제거 문서의 띄어쓰기 누락이 뒤늦게 드러나 복원했다(`d722554`, Refs #93, `/tmp/ds-doc-spacing.md`).
- **재발 방지**: 릴리스 경로는 `origin/main` 기준으로 고정했다. 단 스크립트 기본값은 지금도 `dev`이므로 수동 실행 때는 `--base`를 지정하거나 파일 경로를 직접 준다. 기본값 변경은 코드 수정이라 이 문서에서 하지 않았다.

### 사건 4. 트렌드 cron이 D1 바인딩 100개 한도를 넘겨 미적재
- **현상**: 요금제(plan) 관측이 많아지자 트렌드 cron의 D1 쓰기가 실패해 섹션이 적재되지 않았다.
- **원인**: 항목별 바인딩을 쓰는 upsert가 항목 수에 비례해 바인딩이 늘어, 한 문장의 100개 바인딩 한도를 넘었다.
- **조치**: `json_each(?)`로 JSON 한 개를 바인딩하는 방식으로 바꿔 바인딩 수를 고정했다(`d50ba2c`). 실패 요청의 안전한 크기 진단(`5e76a3c`), 출처 실패·대형 요금제 예약 실행 검증(`4a6c4cc`, `a8a4406`), 일회성 갱신 스크립트(`fbf7dda`)를 더했고 `02e2a7f`로 병합했다(Refs #116). 리뷰는 `/tmp/fable-review-trend-042.md`가 바인딩 한도 회귀 테스트(`trend-large-plan.workerd.test.ts`)가 구 구현에서 실제로 실패함을 확인했다.
- **재발 방지**: 대형 입력 회귀 테스트를 Miniflare(workerd)에서 돌린다. 계획 upsert는 `json_each` 바인딩 6개 고정이다. 운영 수동 채우기 절차는 `docs/harness/operations.md`에 있다. 같은 리뷰가 metrics 쓰기의 D1 batch 문 수 한도를 문서로 확인하라고 남겼다(미확인).

### 사건 5. models.dev 304 때 보강 메타 소실
- **현상**: models.dev가 304(Not Modified)면 catalog가 null이 되어 free-models·new-models가 creator·출시일 없이 다시 저장됐다. 리뷰 시점의 운영 free-models 50건 전부 creator가 빈 값이고 출시일이 null이었다.
- **원인**: 304를 "신선하지 않음"으로 처리해 `catalog=null`을 넘겼고, 빌더가 관측 폴백 항목을 만들면서 직전 payload의 보강 값을 쓰지 않았다. 304 경로 테스트는 있었지만 "보강 유지"는 검증하지 않았다(`/tmp/fable-review-trend-042.md` P1).
- **조치**: `carryEnrichment`(`worker/domain/trend/sections/carry-metadata.ts`)로 직전 값을 이월한다(`18dad41` 테스트, `bf44420` 수정). 재리뷰에서 `name` 우선순위와 "200이면서 미매칭" 테스트를 보강했다(`b4419b1`, `/tmp/fable-review-p1.md`, `/tmp/hyd-trend-p1.md`). 병합은 `abb2308`(Refs #116)이다.
- **재발 방지**: 304·200 미매칭·이월 테스트가 고정돼 있다. 이월은 만료 시점이 없다. 재리뷰가 이를 수용했고, 그동안 `sources`에 stale이 표시된다. 업스트림 실제 응답 형태 fixture가 손으로 쓴 객체뿐이라는 한계는 남아 있다.

### 사건 6. 0.6.44 배포 뒤 옛 payload가 새 투영 검증에 실패
- **현상**: 0.6.44 배포 직후 화면의 일부 섹션이 "다시 시도"만 표시했다(`shared/messages/ko.ts`의 `trend.*.retry`). 즉시 재적재가 필요했다.
- **원인(추정)**: 0.6.44 구간의 계약·enum 정리(`0e77a4d`)와 `checkedAt` 추가(`bf44420`, `b4419b1`)로 투영이 바뀌었고, 배포 전에 저장된 payload가 새 검증을 통과하지 못했다. 직접 근거 파일이 없어 커밋은 확정하지 못했다.
- **조치**: 수동 채우기(`node scripts/trend-refresh-once.mjs`로 dry-run을 본 뒤 `--apply`)로 재적재했다. 절차는 `docs/harness/operations.md`에 있다. 근거 커밋 미확인.
- **재발 방지**: 계약이나 투영이 바뀌는 배포는 배포 직후 수동 refresh를 절차에 넣는다. 더 근본적으로는 투영이 옛 payload를 받아도 섹션 전체를 거부하지 않게 하는 방향이다. AA 인용은 이미 "필드만 제외하고 섹션은 유지"(`/tmp/hf-aa-cite.md`)로 바꿨다. 일반화는 후속이다.

### 사건 7. AA 인용 괄호 거부와 공개 캐시 지연
- **현상**: AA 인용 문장이 생성되지 않았다. 고친 뒤에도 공개 응답 캐시 때문에 수정 반영이 늦게 보였다(#131 댓글).
- **원인**
  - 인용 검증(`8474fd9`)이 모델명의 괄호를 직렬화 패턴으로 보고 거부했다. 실제 1위 이름은 `"Claude Fable 5.2 (Max, Default Fallback)"` 형태였다(`/tmp/hf-aa-fix.md`). 또 dry-run 출력에 AA 상태가 없어 이유를 볼 수 없었다.
  - 공개 응답이 `public, max-age=300, stale-while-revalidate=3600`이어서 데이터를 다시 채운 뒤에도 오래된 응답이 최대 5분(재검증 중에는 최대 1시간까지) 남을 수 있었다(#131).
- **조치**
  - 괄호 허용과 진단 토큰 `aaStatus`·`aaReason` 추가(`71eb52a`, 병합 `299e133`, Refs #116). 대괄호·따옴표·개행·길이 상한은 계속 거부한다.
  - 공개 캐시를 `max-age=60, stale-while-revalidate=300`으로 단축했다(`faaf7f2`, 기본값은 `820f5c7`, Refs #131).
- **재발 방지**: 문자열 검증은 실제 응답 형태로 회귀 테스트를 둔다(괄호 이름 10건 추가). 스키마·계약 변경 뒤 확인은 캐시 시간(현재 60초+300초)을 감안해 기다리거나 헤더로 확인한다. 배포 직후 데이터가 비었을 때 먼저 캐시를 의심한다.

### 사건 8. AA 속도 필드 경로 오독
- **현상**: `/usage`의 AA 속도 패널 값이 비어 보였다(저장 50행 전부 null).
- **원인**: 디코더가 최상위 `median_output_tokens_per_second`를 읽었는데 실제 응답은 `performance.*` 중첩 구조이고, 최상위 경로는 없었다. 디코더 입력이 손으로 쓴 객체여서 필드 경로 드리프트를 못 잡았다(`/tmp/fable-review-trend-042.md`의 fixture 지적과 같은 구조).
- **조치**: `performance.median_*` → `performance_v3.mean_*` → 최상위 순으로 읽도록 고쳤다. TTFT 라벨 정정, 지능 탭 20, 작업당 비용 표, 인용 7개 모델도 함께 했다(`ba0be3b`, 병합 `d4ece7e`, Refs #116, `/tmp/hf-aa-speed.md`).
- **재발 방지**: 외부 응답은 키·값을 노출하지 않고 필드 이름과 타입만 확인하는 진단을 먼저 돌린다. 업스트림 실응답 구조 fixture 도입은 후속 과제다(미반영).

### 사건 9. OpenRouter 점유율 트리맵의 소형 셀이 빈 칸처럼 보임
- **현상**: 작은 칸에 라벨이 없어 빈 칸처럼 보였다. 사용자가 "제대로 라이브러리 넣어서 써"라고 요청했다(#131).
- **원인**: 직접 만든 squarify 트리맵이 면적 기준으로 라벨을 생략했다.
- **조치**: Recharts `Treemap`으로 교체하고 작은 칸은 툴팁·`aria-label`·화면 밖 목록으로 표시한다(`bf19ad9`, 병합 `d5742ac`, Refs #131, `/tmp/ds-treemap-lib.md`). 1차 구현은 `f7b7483`·`c770a79`(병합 `ae8396a`, `/tmp/ds-or-treemap.md`)다.
- **재발 방지**: 차트는 표준 라이브러리를 우선 검토한다. 번들 영향은 Treemap 전용 비동기 청크로 격리했다. 소형 칸 라벨 생략 테스트를 유지한다.

### 사건 10. "무료 모델" 범위 오해
- **현상**: 요금제(plan) 모델 전체를 무료처럼 표시했다.
- **원인**: "무료"의 기준을 가격 0으로 좁히지 않고 요금제에 포함된 모델까지 넓게 읽었다. 첫 수정에서도 OpenCode Zen, Ollama Cloud 공지로 범위가 흔들렸다.
- **조치**: OpenCode Go 무료(가격 0) 항목만 남겼다. `f44d109`(Zen 가격 0) → `2a0643d`(Go와 Ollama 공지) → `afe4d05`(Ollama Cloud 제거, Go 무료만, Refs #116). 요금제 항목은 별도 섹션으로 분리했다(`0ee42be`, `d0d5582`, `85551a0`). 근거는 `/tmp/hyd-free-fix.md`, `/tmp/ds-trend-free.md`다.
- **재발 방지**: "무료"는 `cost` 입력·출력 가격이 모두 0인 항목으로 정의하고 계약 상수 `TREND_FREE_MODELS_RULE`에 고정했다. 사용자와 용어를 합의한 뒤 구현한다. 정의가 모호하면 구현 전에 확인한다.

### 사건 11. AA Data API 약관을 배포 뒤에 확인
- **현상**: AA 지능 순위·점수 표를 공개 `/trend`와 `/pub/trend/metrics`에 먼저 올렸다. 약관은 무료 티어를 "Internal use only"로 하고 표·JSON 재배포를 막는다는 사실을 뒤늦게 확인했다.
- **원인**: 외부 데이터를 공개하기 전에 약관·라이선스를 확인하는 단계가 없었다. 설계는 점수·순위 표 공개를 전제했다.
- **조치**: 약관 검토(`/tmp/fable-terms.md`, Data Platform Terms §2.3(전 티어 허용 범위, 짧은 인용은 (c))·§2.4(b)(c)(재배포 금지), 플랜 페이지 "Internal use only with attribution")에 따라 공개 AA 호출·표시를 제거했다(`85551a0`). AA 상세는 Access 뒤 `/usage` 전용 `/api/trend/aa` 패널로 옮겼다(`036f631`). 공개 `/trend`에는 순위 없는 한 문장 인용과 링크만 남겼다(`1d56e2f`, `8474fd9`, `b70502f`). 문장 공개는 사용자가 선택한 결정이며 약관 허가 판정을 대신하지 않는다고 운영 문서에 기록했다(`/tmp/hf-aa-cite.md`). 스크린샷 파이프라인에서 내부 패널을 제외했다(`7ab0082`).

## 4. 운영 방식 회고
1. **총괄이 한 워커에 후속 요청을 쌓음**: 진행 중인 워커에 요청을 덧붙이면 범위가 커지고 완료 판정이 흐려졌다. 맡기는 일은 5분(최대 15분) 조각으로 쪼개고, 진행 중 워커에 덧붙이지 않는다. 몰리면 재분배한다(`.agents/skills/herdr-orchestration`, `715efb9`).
2. **총괄이 스크린샷·curl·충돌 해결을 직접 봄**: 총괄 컨텍스트를 소모했다. 이제 워커와 서브에이전트에 위임한다. z-fable은 Sonnet 서브에이전트(explorer·test-runner·ui-checker·ops-probe·doc-sync)를, z-astra는 Codex Terra를 쓴다(`docs/harness/agents.md`, `63eac78`). 운영 점검은 읽기 전용 보고로 받는다(`/tmp/sol-0646-check.md`, `/tmp/sol-ops-0647.md`).
3. **Monitor 대신 worker-watcher**: 워커 대기는 Monitor가 아니라 worker-watcher 서브에이전트(워커 1명당 1개)가 맡는다(`f7f0e72`).
4. **watcher의 완료 오인 위험**: watcher가 이전 턴의 done 출력을 이번 작업의 완료로 오인할 수 있다. 결과 파일의 수정 시각이 작업 시작 시각 이후인지를 완료 기준으로 쓴다.
5. **Codex 샌드박스의 거짓 실패**: Codex 샌드박스는 localhost 바인딩에서 EPERM이 나서 workerd(Miniflare) 테스트가 거짓으로 실패한다. 샌드박스 밖에서 실행하거나 test-runner에 위임한다. 이번 구간의 `scripts/d1-status.mjs`도 기본 샌드박스에서는 네트워크 실패였고 승인된 읽기 전용 실행에서 통과했다(`/tmp/sol-ops-0647.md`).
6. **Herdr 에이전트 이름 통일**: Herdr 에이전트 이름은 `z-` 접두를 붙여 부른다(hf가 아니라 z-hf).
